## 첫 카드와 등록 사진

등록 마치기에서 보낸 카드 작업은 서버에서 최초 등록 사진의 준비를 기다린다. 홈과 카드 화면은 `photoPreparation`의 완료 수를 표시하고, 앱 재진입 때 같은 작업을 이어받는다. 앱을 닫아도 서버 작업은 계속된다.

사진 분석 실패, 시간 초과 또는 동의 철회가 있으면 `사진 분석 다시 시도`와 `완료된 사진으로 카드 만들기`를 보여준다. 준비된 사진이 없으면 `사진 없이 카드 만들기`다. 자동으로 사진을 생략하거나 새 카드 작업을 만들지 않는다. 선택 요청이 실패하면 선택 화면을 유지한다. 작은 화면에서 글자를 키우면 홈의 안내와 선택 영역을 스크롤할 수 있다.

API와 배포 조건은 [사진 분석 연결](../backend/docs/photo-analysis.md#첫-카드의-사진-대기)에 있다. 기존 앱에는 이 선택 화면이 없으므로 BE와 FE를 함께 적용해야 한다. 첫 카드가 이미 완성된 프로필에는 소급 적용하지 않는다. `test/first_card_photos_test.dart`는 API 대역으로 상태 복원, 오류, 중복 입력과 화면 크기별 동작을 검사한다.

## 실행과 테스트

`app/`에서 실행한다. 푸시 전에는 정적 검사와 테스트를 모두 실행한다.

| 명령 | 용도 |
| --- | --- |
| `flutter pub get` | 의존성 설치 |
| `flutter run` | 연결된 기기에서 실행. 테스트는 별도 실행 |
| `flutter analyze` | 정적 검사 |
| `flutter test` | 테스트와 목 데이터 원본 비교 |
| `flutter build apk --debug` | 디버그 APK 빌드 |

`test/flutter_test_config.dart`가 모든 테스트보다 먼저 돌아 홈 마스코트의 떠 있기와 둘러보기를 끈다(`Mascot.motion`). 끝나지 않는 움직임이 있으면 `pumpAndSettle`이 끝나지 않기 때문이다. 마스코트 자체는 `test/mascot_test.dart`가 움직임을 켜고 확인한다.

화면 테스트는 동작(누르면 어디로 가는지, 무엇이 보이고 사라지는지, 서버에 무엇을 보내는지, 화면 낭독기가 무엇을 읽는지, 글자를 키워도 오류가 나지 않는지)만 확인한다. 색, 위치, 간격, 크기, 그림자처럼 모양을 고정하는 테스트는 디자인을 바꿀 때마다 깨져 2026-11-06에 지웠고 새로 두지 않는다. 모양은 미리보기와 실기기에서 눈으로 확인한다. 다만 #180, #208에서 정한 접근성 하한(누르는 자리 48dp, 그림 대비 3:1, 글자를 키워도 겹치거나 화면 밖으로 나가지 않음, 쉬운 모드의 보조 글자 대비, 바깥 영역을 한국어로 읽음)은 자리나 색 값 자체가 아니라 하한만 확인하는 테스트로 남긴다(2026-11-07 PR #255 리뷰).

구글 로그인을 실제로 눌러 보려면 `flutter run` 에 [구글 로그인](#구글-로그인)의 `--dart-define` 둘을 함께 넘긴다. 넘기지 않은 디버그 빌드에서는 버튼을 누르면 구글을 부르지 않고 바로 환자 정보 입력(`/profile/create`)으로 넘어간다(임시, `skipGoogleLoginProvider`). BE의 구글 클라이언트 ID와 SHA-1 등록이 준비될 때까지 화면을 확인하기 위한 길이며, 서버 세션이 없어 로그아웃과 탈퇴는 동작하지 않는다. 릴리스 빌드에서는 꺼지고 설정 오류를 알린다. 설정이 준비되면 지운다.

기존 검증 기록: 2026-09-06, Windows 11과 Galaxy S23+ (SM S916N), Android 15 (API 35), arm64 실기기에서 위 명령과 앱 실행을 확인했다.

### 앱 전체 여정 테스트

화면별 위젯 테스트와 별도로, 실제 앱(`SaerokApp`, `buildRouter`, 앱의 Riverpod provider)을 띄우고 보호자가 누르는 순서대로 핵심 흐름을 지나가는 테스트를 둔다. 여정 본문은 [test/journey/app_journey.dart](test/journey/app_journey.dart) 하나이고 두 곳에서 부른다.

| 명령 | 실행 위치 |
| --- | --- |
| `flutter test` (또는 `flutter test test/app_journey_test.dart`) | 호스트, 화면 없음. develop과 main으로 가는 PR마다 GitHub Actions `Product tests`의 `Flutter analyze and tests`가 `flutter test` 전체를 돌린다 |
| `flutter test integration_test/app_journey_test.dart` | 연결한 Android 기기나 에뮬레이터. `integration_test` 패키지를 쓴다 |
| `flutter test test/journey_contract_test.dart` | 호스트. 가짜 서버 응답과 앱 요청 본문(6-1, 7-4, 5-1, 2-7)의 필드 이름을 `backend/app/schemas/*.py`와 비교하고, 6-2 multipart 이름은 BE 라우트의 `File`, `Form` 인자와 비교한다. `CI=true`에서 `backend/`를 찾지 못하면 건너뛰지 않고 실패한다 |

다루는 흐름은 다음과 같다.

- 로그인 세션이 보관된 보호자가 앱을 켠다 → 스플래시가 세션을 확인한다 → 서버의 어르신을 불러온 홈 → 카드 두 장 선택 → 사진 없이 시작 → 녹음 전 안내의 `네, 좋아요` → 녹음과 만남 끝내기 → 소감 → 평가(6-1) 후 녹음(6-2) 제출 → 홈의 `리포트를 만들고 있어요` → `리포트가 도착했어요` → 리포트 → 이야기 제안의 내용을 고쳐 승인(7-4)
- 다음 대화 준비: 지난 묶음이 평가까지 끝났으므로 카드 화면이 새 묶음을 받는다. 가짜 서버는 1번 카드를 가장 최근 이야기로 만들므로, 여기서는 가짜 서버가 넣어 준 그 카드를 앱이 보여주는지 확인한다. BE나 AI가 승인한 이야기를 실제로 카드에 넣는지는 검증하지 않는다. 그 뒤 일대기에서 이야기 제목과 내용을 차례로 두 번 정정하면 각 정정은 바로 저장되고 묶음은 다시 만들지 않는다. 홈의 `오늘의 대화카드 받기`를 누르면 `어르신 정보가 바뀌어서` 안내와 함께 두 정정을 모아 묶음 생성 요청(`POST card-generations`)을 한 번만 보내 묶음 전체를 다시 만들고(#222), 두 번째 면회는 새 묶음으로 회차(5-1)를 만든다. 고친 묶음을 카드 화면에서 감추는 것은 `card_refresh_screen_test.dart`가 따로 확인한다
- 분석 실패: 홈의 `리포트를 만들지 못했어요` → 기기에 녹음이 남아 있으므로 `분석 다시 요청하기`와 `녹음 파일 공유`를 고르는 시트 → `분석 다시 요청하기`(6-5) → 리포트 도착
- 화자 정보 부족: 라벨이 부족한 경우를 가정한 서버 대역도 일반 리포트, 카드 요약과 이야기 후보를 반환한다. 변경 사항 화면의 `AI 제안 이유 보기`를 누르면 누구의 경험인지 확인이 필요하다는 합성 문구를 볼 수 있고, 승인 전에는 일대기에 반영하지 않는다. 실제 STT와 모델의 화자 추론 및 문구 생성 품질은 이 앱 테스트에서 검증하지 않는다
- 녹음 전 승인: `네, 좋아요`를 누르기 전에는 마이크 대역의 `start`가 한 번도 불리지 않는다

바꾸는 것은 서버와 기기 경계뿐이다([journey_harness.dart](test/journey/journey_harness.dart)). 서버 HTTP는 상태를 가진 가짜 서버([journey_server.dart](test/journey/journey_server.dart))가 받고, 앱의 실제 API 코드가 JSON과 multipart를 주고받는다. 보안 저장소, 구글 SDK, 마이크(임시 폴더에 합성 무음 WAV), 카메라, 갤러리, 화면 켜짐 채널은 대역이다. 분석과 카드 생성을 다시 묻는 간격만 200ms로 줄였다. 자료는 모두 합성이다.

확인하지 않는 것: 실제 마이크 녹음과 권한 창, 실제 STT, 화자 분리와 리포트 모델의 품질, 실제 BE와 DB, 운영 서버, 푸시 알림, 면회 사진 촬영과 업로드(여정은 `사진 없이 시작할게요`를 고른다), TalkBack 낭독과 실제 화면 크기별 배치. 가짜 서버는 BE 규칙을 줄여 옮긴 것이라 BE 구현을 검증하지 않는다. 필드 이름 비교는 타입과 enum 값을 보지 않는다. 가짜 서버의 이야기 고치기(2-7)는 받은 본문을 그대로 합치며 BE의 값 검사를 옮기지 않았다.

앱에 없는 단계: 회차마다 받는 녹음 동의 체크는 없다. 녹음과 음성 처리 동의는 가입 때 받고(2026-10-13 팀 결정), 여정은 녹음 전 안내의 `네, 좋아요`를 녹음 전 승인으로 확인한다. 따로 `다음 대화 준비하기` 버튼은 없다. 받아 둔 묶음이 정정 뒤 `needsRefresh`이면 홈의 `오늘의 대화카드 받기`가 묶음을 다시 만들고, 평가를 마친 직후에는 카드 화면이 새 묶음을 자동으로 요청한다.

### Play 업로드용 빌드

Play Console에 올리는 AAB는 업로드 키로 서명한다. 키는 릴리스 담당자만 가지며, 키 파일과 비밀번호는 저장소와 메신저에 두지 않는다. 담당자가 키를 저장소 밖에 두고 `android/key.properties`에 위치를 적는다. 두 파일 모두 `.gitignore` 대상이다.

    storePassword=<키스토어 비밀번호>
    keyPassword=<키 비밀번호>
    keyAlias=upload
    storeFile=<키 파일의 절대 경로, 예: C:/Users/<사용자>/keys/saerok-upload.jks>

    flutter build appbundle --release --dart-define-from-file=.env

GitHub Actions의 `Release build`에는 APK와 AAB를 만드는 단계가 있지만, 앱 서버 주소와 구글 클라이언트 ID(`SAEROK_API_BASE_URL`, `SAEROK_GOOGLE_SERVER_CLIENT_ID`)가 저장소 변수와 시크릿에 모두 없으면 앱 빌드를 건너뛰고, 둘 중 하나만 있으면 앱 빌드 작업이 설정 오류로 실패한다. 2026-11-09 기준 두 값이 없어, 11/7과 11/8에 손으로 실행한 Release build(예: run 42485330291)는 APK와 AAB 없이 백엔드 이미지 기록, OpenAPI 스키마와 릴리스 요약만 남겼다. 11/9 승인 배포 앞의 Release build run 42567070594(develop `59190ba7`)도 `Android release build` 작업은 통과했지만 `Build APK and AAB` 단계를 건너뛰어 APK와 AAB를 남기지 않았다. 두 값을 넣더라도 업로드 키 시크릿(`ANDROID_UPLOAD_*`)이 없어 디버그 키로 서명되므로 Play에 올릴 수 없다. 앱 빌드가 돌면 푸시 설정은 11/8 등록한 시크릿 `GOOGLE_SERVICES_JSON_BASE64`에서 들어간다. Play에 올리는 빌드는 릴리스 담당자가 이 절의 방법으로 만든다.

`key.properties`가 없으면 release도 디버그 키로 서명되며, 그 결과물은 Play에 올릴 수 없다. `.env`의 `SAEROK_API_BASE_URL`은 https여야 하고 `SAEROK_GOOGLE_SERVER_CLIENT_ID`는 비어 있으면 안 된다. 릴리스 빌드는 평문 통신을 막는다. 둘 중 하나라도 맞지 않으면 릴리스 앱은 켜자마자 로그인 대신 설정 오류 화면을 띄우고 고칠 설정 이름을 보여 준다([릴리스 설정 검사](#릴리스-설정-검사)). 구글 로그인을 하려면 업로드 키의 SHA-1과 Play App Signing의 앱 서명 키 SHA-1을 Google Cloud Console에 등록해야 한다. 버전은 `pubspec.yaml`의 `version`(`이름+versionCode`)을 따르며, 올릴 때마다 versionCode를 올린다.

### 앱과 실제 서버 E2E

`flutter test`의 앱 테스트는 서버 응답을 가짜로 바꾼다. [e2e/server_journey_test.dart](e2e/server_journey_test.dart)는 화면 없이 앱의 실제 API 코드(`AuthApi`, `ProfileApi`, `ServerCardApi`, `ServerVisitApi`, `ReportApi`, `ApiClient`)로 실제 BE와 PostgreSQL을 HTTP로 부른다.

```bash
cd backend
SAEROK_TEST_DATABASE_URL=postgresql://<생성과 삭제가 허용된 테스트 DB 계정>/postgres uv run --locked python scripts/run_app_server_e2e.py --flutter <flutter 실행 파일>
```

스크립트가 빈 DB에 `alembic upgrade head`를 적용하고, 같은 프로세스에서 BE(uvicorn), 카드 생성 worker, 음성 분석 worker를 띄운 뒤 테스트를 실행한다. 끝나면 DB를 지운다. 스크립트 없이 이 파일만 돌리면 건너뛴다. `flutter test`의 기본 범위(`test/`)에는 들어가지 않는다. PR마다 GitHub Actions `Product tests`의 `App and backend E2E (synthetic boundaries)`가 아래 합성 기본값으로 이 스크립트를 돌린다(#258).

다루는 흐름

- 가입: 첫 로그인의 동의 요구(1-1), 동의 제출(1-2), 계정 확인(1-3)
- 푸시 기기: 알림 수신 동의 전 등록 거절(`PUSH_NOTIFICATION_CONSENT_REQUIRED`), 동의(1-6) 뒤 등록(1-7), 동의를 거둔 뒤 다시 거절, 해제(1-8). 실제 FCM 발송은 하지 않는다
- 프로필: 생성과 세부 정보, 이야기 추가와 삭제(2-1~2-9), 프로필 사진(3-1, 3-2)
- 카드: 생성 실패 뒤 원인을 지우고 다시 요청, 12장 생성(4-1~4-3), 쓰지 않은 묶음이 있을 때 `CARD_SET_READY`
- 사실 정정: 이야기 정정(2-7) 뒤 `needsRefresh`, 그 묶음으로 회차를 만들면 `CARD_SET_NEEDS_REFRESH`, 묶음 전체 재생성
- 면회: 카드 세 장으로 회차 시작(5-1), 회차 사진(5-2), 보충 카드 추가(5-3), 면회 중 생성 요청의 `VISIT_IN_PROGRESS`, 평가 제출과 재제출(6-1)
- 녹음과 리포트: 녹음 제출(6-2), 분석 상태(6-3), 서버에 6-5가 있으면 첫 리포트 생성 실패 뒤 남은 전사로 다시 요청, 리포트 목록과 리포트, 회차 사진(7-1, 7-2), 이야기 제안을 고쳐 승인하고 주제 제안 수락(7-3, 7-4)
- 다음 대화 준비: 승인한 이야기가 다음 카드 생성 자료에 출처 `visit`으로 들어감, 그 묶음으로 두 번째 면회와 두 번째 리포트
- 계정: 로그아웃 뒤 세션 거절(1-4), 다시 로그인하면 같은 계정, 탈퇴(1-5) 뒤 다시 동의 요구

기본값은 서버 밖으로 나가는 경계만 합성으로 바꾼다.

- 구글 로그인: 스크립트가 실행마다 만든 RSA 키로 서명한 ID 토큰과 로컬 JWKS 주소
- 카드 생성 모델: 실제 worker와 작업 큐를 쓰고 생성 함수만 합성 카드 12장을 돌려준다. 받은 이야기마다 카드 한 장에 그 제목과 출처를 적는다.
- S3: 녹음과 사진 모두 메모리 저장소. 분석이 끝난 뒤 녹음이 지워지지 않으면 실패로 끝난다.
- STT 서버: 화자 두 명의 합성 전사. 녹음은 0.1초 무음 WAV다.
- 리포트 모델: 평가에서 쓴 카드 하나의 요약과 제안을 담은 합성 결과. 서버의 결과 검사(`parse_result`)는 그대로 거친다.

경계마다 실제로 바꿔 돌릴 수 있다. 실제 모드에서 넣는 자료도 모두 합성이다.

| 옵션 | 하는 일 |
| --- | --- |

면회 중 카드 E-3, E-4는 녹음 화면의 팝업이다. 사진에서 나온 카드는 메인 질문의 소제목 위에 그 사진을 둔다. 소제목과 메인 질문을 제 크기로 놓고 남는 높이만 쓰며(120 이하), 남는 높이가 48보다 작으면(작은 화면, 큰 글자) 질문을 줄이지 않도록 두지 않는다. 412 x 917 기준 화면의 두 줄 질문은 글자 1배에서 사진이 보이고, 1.5배에서는 질문이 자리를 다 써서 사진을 두지 않는다. 사진 주소는 면회 동안 녹음 화면이 들고 있어 시트를 여닫을 때마다 다시 읽지 않고, 만료 전에 새로 받는다(위 `/cards`). 녹음 화면 아래 카드 자리를 위로 끌면 시트가 손가락을 따라 올라온다. 손을 뗐을 때 시트의 3할보다 많이 올라왔거나 위로 빠르게 그었으면(초당 700px) 끝까지 열리고, 아니면 다시 내려간다. 눌러서 열 수도 있고 화면 낭독기는 `대화 카드 꺼내기` 버튼으로 연다. 시트를 띄우면 Flutter가 진행 중인 손가락 입력을 끊으므로, 끄는 동안에는 녹음 화면 위에 같은 모양(`VisitCardsSheetPreview`)을 그리고 손을 떼면 그 높이에서 진짜 시트로 이어 받는다. 녹음을 시작한 뒤 만남을 끝내기 전(잠시 멈춤 포함)에 뒤로 가면 `녹음을 그만둘까요?` 확인 창을 띄운다(`그만두고 나가기` / `계속 녹음하기`, 바깥을 누르면 머문다). 나가면 녹음이 멈춘다. 같은 카드 묶음으로 회차를 다시 만들 수 없어(`CARD_SET_ALREADY_USED`) 녹음을 처음부터 다시 하거나 같은 파일에 이어 녹음하지는 못한다. 대신 카드 화면과 홈이 그 회차의 `평가 이어서 하기`를 보여주고, 누르면 그 회차의 소감과 평가로 간다(#244, 아래 [면회 녹음](#면회-녹음)).

시트 위쪽에는 길이가 정해진 막대를 고른 카드 수만큼 나눠 둔다(칸 사이 6, 막대 높이 8, 누르는 자리 높이 48). 시트 손잡이와 헷갈리지 않게 손잡이에서 조금 떨어뜨렸다. 번호 칩을 늘어놓았더니 화면이 요란해 막대로 바꿨다. 칸을 누르면 그 카드로 바로 가고, 지금 카드 칸만 초록(`HomeColors.accent`)이며 탄력 있게 6만큼 올라간다(0.65초, `ElasticOutCurve`). 다른 칸은 면회 중에 더한 카드까지 모두 연한 세이지(`HomeColors.bubbleLine`)이다. 색을 나누니 요란해 보여 하나로 맞췄다. 소제목과 메인 질문 묶음은 막대와 이전·다음 버튼 사이의 가운데에 온다. `대화 카드 추가`에서 카드를 더하고 돌아오면 0.25초 뒤부터 0.11초 간격으로 새 칸이 하나씩 자라 들어오고, 그만큼 앞 칸들이 좁아진다. 추가 화면에 있는 동안에는 새 칸을 숨겨 두었다가 돌아온 뒤에 자라게 한다. 화면 낭독기는 칸을 `n번 카드`(더한 카드는 `, 추가한 카드`) 버튼으로 읽는다. 메인 질문을 옆으로 미는 동작은 50~60대에게 어려울 수 있어 두지 않고, 두 영역 경계에 `‹ 이전`(초록 테두리)과 `다음 ›`(초록 면) 알약 버튼(높이 64)을 나란히 둔다. 끝이 없이 돌아, 마지막 카드의 다음은 첫 카드, 첫 카드의 이전은 마지막 카드다. 카드가 한 장이면 둘 다 흐리게 둔다. 카드를 옮겨도 화면 상태만 바뀌고 서버에는 알리지 않는다. 아래 꼬리 질문을 누르면 앞 질문이 조금 왼쪽으로 밀리며 사라진 뒤 다음 질문이 오른쪽에서 들어온다(합쳐 0.4초). 두 질문이 함께 움직이면 글자가 겹쳐 어지러워 한 번에 하나만 보이게 했다. 아래 점은 지금 질문 자리만 길게 늘어난다. 카드를 바꿀 때는 이 효과 없이 바로 바뀐다. 움직임 줄이기를 켜면 막대와 꼬리 질문 모두 바로 바뀐다. HOME과 HOME-1은 리포트 알림 유무, B-3의 녹음 완료와 B-4의 인식 실패는 음성 입력 상태, C-1 ~ C-3은 카드 펼침과 추가 상태를 나타낸다.

B-7 사진 올리기는 기기 앨범에서 최대 5장을 고르고, 고른 사진은 X로 뺄 수 있다. 앨범은 [photo_picker.dart](lib/features/profile_setup/photo_picker.dart)의 `PhotoPicker` 뒤에 두어 테스트에서 바꿔 끼운다. 안드로이드 시스템 사진 선택기를 쓰므로 저장소 권한을 받지 않는다. 고른 사진은 단말 경로로만 들고 있다가 `마치기`를 누를 때 한 장씩 올린다. 그래서 그 전에는 X로 빼도 서버에 남지 않는다. 올리는 중에만 더하거나 빼지 못한다. 모두 올렸거나 실패한 사진을 뺀 뒤에도 5장 미만이면 더 골라 올릴 수 있고, 이미 올라간 사진은 다시 올리지 않는다. 서버에는 사진 삭제 API(3-4, #240)가 있지만 앱이 아직 부르지 않으므로 올라간 사진에는 X를 두지 않는다.

올리는 동안에는 빼기, 추가와 뒤로 가기를 막는다. 사진마다 `완료` 또는 `실패`를 표시하고, 모두 올리면 `홈으로`를 눌러 넘어간다. 사진 분석은 기다리지 않는다. 실패한 사진은 다시 올리거나 빼고 마칠 수 있다. 용량 초과와 형식 오류처럼 다시 올려도 안 되는 실패에는 `다시 올리기`를 보여주지 않는다. 올라간 사진은 앱이 삭제 API(3-4)를 부르지 않아 X를 숨긴다. 업로드는 [photo_uploader.dart](lib/features/profile_setup/photo_uploader.dart)의 `PhotoUploader` 뒤에 둔다. 로그인했으면 `ServerPhotoUploader`가 기본 정보를 마칠 때 만든 서버 프로필(2-2)에 3-1(`image` 필드의 multipart)로 올린다. 서버의 `errorCode`를 그대로 실패 문구로 옮기고, 서버가 `retryable`로 알렸거나 서버에 닿지 못했을 때만 `다시 올리기`를 둔다. 로그인 없이 들어오면 목 업로더가 0.8초 뒤 성공한다. BE(#278, 11/9 14:42 KST 승인 배포부터 운영)는 3-1 본문이 상한(사진 상한 + 1 MiB, 기본 21 MiB)을 넘으면 본문을 다 받기 전에 413 `IMAGE_TOO_LARGE`로 끊는다. #278 PR 본문은 이때 앱이 413 대신 연결 오류를 받을 수 있다고 적었고, 앱은 연결 오류에 `다시 올리기`를 두므로 이 경우에도 `다시 올리기`가 보일 수 있다. 앱은 프로필 사진을 올리기 전에 줄이지 않는다([photo_picker.dart](lib/features/profile_setup/photo_picker.dart)).

**사진 분석 동의.** 서버는 계정이 AI 사진 분석(선택 동의 `photoAnalysis`)에 동의한 사진만 분석한다(#257). 사진을 올리는 데에는 동의가 필요 없다. 동의하지 않은 계정이 사진을 올리려고 하면(처음 등록의 사진 단계, 프로필 갤러리의 사진 추가) 올리기 전에 가입 화면과 같은 동의문을 시트로 띄운다([photo_consent_prompt.dart](lib/features/profile/photo_consent_prompt.dart)). `동의하고 올리기`는 1-6으로 동의를 저장하고 올린다. `동의하지 않고 올리기`와 시트를 그냥 닫는 것은 거절이라 지금까지처럼 분석 없이 올린다. `다시 띄우지 않기`는 거절하고, 이 휴대폰에서 그 계정에는 다시 묻지 않는다(보안 저장소에 켜짐 여부만 둔다). 거절하면 앱이 켜져 있는 동안 다시 묻지 않는다. 동의는 설정의 계정 약관 동의에서 바꾼다. 동의를 저장하지 못해도 알리고 사진은 올린다. 동의하지 않은 계정의 갤러리는 "분석 중" 대신 안내와 직접 쓰는 칸을 보여준다(#261). 11/9 14:42 KST 승인 배포(#288)부터 설정에서 동의를 끄면 서버가 저장된 AI 설명을 지우고 그 사진을 `pending`으로 되돌리므로, 갤러리는 동의하지 않은 계정처럼 안내와 직접 쓰는 칸을 보여준다(11/9 실기기 확인, 팀 운영 기록). 보호자가 쓴 설명은 남는다(서버 코드 기준, 실기기에서는 확인하지 않았다).

B-3 ~ B-6 세부 정보의 음성 입력은 `듣고 있어요` → `다 말했어요` → `말씀을 글로 옮기고 있어요` 순서로 나눠 보여준다. 옮기는 중에는 마이크와 방법 바꾸기를 누를 수 없다. 이를 위해 [speech_input.dart](lib/features/profile_setup/speech_input.dart)의 `SpeechInput`을 녹음 시작(`start`)과 녹음 끝(`SpeechRecording.finish`)으로 나눴다.

로그인했으면 실제로 녹음해 BE의 짧은 음성 전사 API로 보낸다(`ServerSpeechInput`, 이슈 #138). 로그인하지 않았으면 목이 1.2초 뒤 결과를 돌려준다.

- 녹음은 면회 녹음과 같은 WAV, 16kHz, 16-bit, mono이고 최대 5분이다. 5분에 닿으면 `다 말했어요`를 누른 것처럼 끝내고 보낸 뒤, 알아들은 문장 위에 `5분이 지나 녹음을 멈췄어요`와 글로 이어 쓰는 방법을 알린다.
- `듣고 있어요` 동안에는 화면이 저절로 꺼지지 않게 한다. `다 말했어요`를 누르거나 5분에 닿아 끝나면, 녹음을 시작하지 못했거나 화면을 벗어나면 바로 놓는다. 글로 옮기는 중에는 녹음하지 않으므로 켜 두지 않는다. 방식은 [녹음 중 화면 켜짐](#녹음-중-화면-켜짐)과 같다.
- 녹음 파일은 임시 폴더의 `speech_inputs/`([speech_recorder.dart](lib/features/profile_setup/speech_recorder.dart))에 둔다. 면회 녹음과 달리 남기지 않는다. 결과를 받거나, 다시 녹음하거나, 방법을 바꾸거나, 화면을 벗어나면 지운다. 녹음 장치는 항목들이 함께 쓴다. 전사 중에 건너뛰어 앞 항목의 결과가 늦게 와도 그 파일만 지우고, 다음 항목에서 시작한 녹음은 멈추지 않는다. 앱이 꺼져 남은 파일은 다음 녹음을 시작할 때 지우되, 아직 보내는 중인 파일은 남긴다. 캐시 폴더라 자동 백업에 들어가지 않는다.
- `text`가 빈 문자열이면 알아듣지 못한 것이다. 한 번이면 `목소리를 잘 듣지 못했어요.` 아래에 `마이크를 눌러 다시 말씀해주세요.`를 보여준다. 버튼을 따로 두지 않고 할 일을 마이크 하나로 둔다. 기존대로 두 번이면 직접 입력으로 넘어간다.
- 서버에 닿지 못했거나 서버가 처리하지 못한 실패는 알아듣지 못한 횟수에 세지 않는다. 다시 보낼지는 오류 코드가 아니라 응답의 `retryable`로 정한다(연결 실패와 시간 초과도 다시 보낼 수 있는 것으로 본다). 다시 보낼 수 있으면 녹음을 남기고 `연결이 원활하지 않아 말씀을 글로 옮기지 못했어요`와 `재시도`를 보여준다. 다시 말하지 않고 같은 녹음을 보낸다. 할 일을 하나로 두려고 이때는 마이크를 누를 수 없다. 재시도가 두 번 실패하거나 다시 해도 안 되는 실패(동의 없음, 형식 오류 등)면 녹음을 지우고 직접 입력으로 넘어간다. 마이크 권한을 받지 못해도 직접 입력으로 넘어간다. 넘어온 이유는 입력칸 위에 알린다.

  | 넘어온 이유 | 안내 | 화면 아래 버튼 |
  | --- | --- | --- |
  | 두 번 알아듣지 못함 | 목소리를 잘 듣지 못했어요. / 글로 적어 보시겠어요? | 다시 녹음하기 |
  | 재시도 두 번 실패 | 지금은 연결이 원활하지 않아요. / 글로 적어 보시겠어요? | 다시 녹음하기 |
  | 마이크 거부 | 마이크가 꺼져 있어요. / 휴대전화 설정에서 새록의 마이크를 켜 주세요. | 다시 녹음하기 |
  | 다시 해도 안 되는 실패, 녹음 장치를 열지 못함 | 지금은 말씀을 글로 옮기기 어려워요. / 글로 적거나 건너뛰어도 괜찮아요. | 없음. 다시 해도 같은 결과다. 세부 정보는 선택 사항이라 글을 쓰기 어려우면 화면 아래 `건너뛰기`로 넘어간다 |

  처음부터 글로 답하기를 고르면 안내가 없고 버튼은 `말로 답할게요`다.
- 알아들은 문장은 체크 아래 흰 상자에 담는다. 화면이 스크롤하지 않아 500자쯤에서 넘쳤으므로 상자를 4줄 높이로 정하고 안에서 스크롤한다(막대를 늘 보인다). 짧은 답도 같은 높이다. 5분에 닿아 멈춘 경우는 `다시 녹음하기`를 숨긴다. 한 번 눌러 5분 말한 결과를 버리지 않게 하려는 것이며, 다시 녹음하려면 `글로 답할게요` → `말로 답할게요`로 간다.
- 마이크 원은 대기, `듣고 있어요`, `말씀을 글로 옮기고 있어요` 모두 지름 120, 테두리 2, 안의 아이콘이나 도는 표시 48로 같고 색만 바뀐다. 원과 첫 줄 안내는 한 묶음으로 위의 예시 상자와 아래 알약 사이 한가운데에 둔다. `다 말했어요` 버튼이나 둘째 줄 안내 같은 보조 내용은 원 아래 빈 공간의 맨 위에 두어 높이 계산에 넣지 않고, 듣는 중과 옮기는 중에 숨기는 화면 아래 `글로 답할게요`도 자리는 남겨, 상태가 바뀌어도 원과 글자가 오르내리지 않는다. 보조 내용 영역은 최소 높이를 알려 두어 좁거나 글자가 커도 등록 화면이 스크롤되어 버튼이 늘 눌린다. 알아들은 뒤의 체크와 결과 상자도 위아래 여백을 같게 두어 한가운데에 온다. 알아들으면 예시 상자 아래에 띄워 체크를 작게 시작해 통 튀어나오게 보이고(0.52초), 체크와 결과 상자 사이도 띄운다. `다시 녹음하기`는 결과 상자 아래 글자 대신 화면 아래 `글로 답할게요` 옆의 같은 알약으로 둔다(한 줄에 안 들어가면 두 줄).
- 처음에 `말로 답하기`, `글로 답하기`를 누르면 바탕이 진해지고 테두리가 검어지며 살짝 눌린 모습을 0.18초 보인 뒤 넘어간다. 위쪽 진행 막대는 단계를 넘길 때 0.4초 동안 미끄러지듯 자란다. 움직임 줄이기가 켜져 있으면 둘 다 바로 바뀐다.
- 알아들은 뒤 `글로 답할게요`를 누르면 알아들은 문장을 입력칸에 채운다. 틀린 곳을 고치거나 이어 쓸 수 있다.
- 입력칸에 글이 있을 때 `말로 답할게요`(실패 뒤에는 `다시 녹음하기`)를 누르면 먼저 `말로 다시 답할까요?` / `적은 내용이 지워져요.` 확인 창을 띄운다(2026-11-10 UX 점검 20). `말로 답하기`를 누를 때만 글과 저장본을 지우고 마이크 화면으로 간다. `계속 적기`나 창 바깥을 누르면 쓰던 화면에 그대로 남는다. 입력칸이 비었거나 빈칸만 있으면 묻지 않는다. 앞서 적어 둔 답으로 열린 입력칸도 같다. 창은 프로필 지우기와 같은 모양의 `showChoiceDialog`다.
- 글로 쓰는 중 키보드가 올라오면 질문과 입력칸만 남기고 예시, 실패 안내와 `말로 답할게요`를 숨긴다. 남은 높이에서 입력칸 아래 버튼이 고정된 `다음`과 겹쳤기 때문이다. `Scaffold` 본문의 `MediaQuery`는 키보드 높이가 0이라 창의 값(`View.of(context).viewInsets`)을 읽는다.
- 결과를 기다리는 시간은 2분(`speechTranscriptionTimeout`)이다. BE의 별도 시간 제한은 실제 처리 시간과 대기열 혼잡을 잰 뒤 정하므로(이슈 #138) 잠정값이다. 서버는 5분을 넘는 녹음을 `AUDIO_TOO_LARGE`(413)로 거절하되, 앱의 5분 타이머가 멈추는 데 걸리는 시간만큼 302초까지 받는다(#267). 못 알아들음은 빈 `text`로만 판정하며 따로 점수 기준을 두지 않았다([BE 안내](../backend/docs/short-speech-transcription.md)).
- 이 API의 명세(6-6)와 서버 구현은 #214로 `develop`에 병합됐고 11/5 운영 배포(develop `6cebcf72`, [#187의 11/5 운영 배포 기록](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/issues/187#issuecomment-6652039046))부터 운영 서버에 있다. 11/8 운영 안정성 시험에서 운영의 이 API로 정답 대본이 있는 낭독과 강연 음성을 전사했다([기록](../backend/docs/stability-test-20261108.md)). 302초까지 받는 수정(#267)은 11/8 승인 배포(develop `9c2b8276`, Deploy run 42485750502)로 들어갔다. 11/9 승인 배포(#285)부터 서버는 한 계정의 전사를 동시에 기본 2건까지 처리하고, 넘는 요청은 429 `SPEECH_TRANSCRIPTION_IN_PROGRESS`(`retryable: true`)로 거절한다. 앱은 전사 중에 `건너뛰기`로 다음 항목을 보낼 수 있어 이 한도에 닿을 수 있으며, 이 응답을 다시 보낼 수 있는 실패로 보고 `재시도`를 보여 준다. 실제 사용자 음성으로 쓰기 전에 가입 때 받는 음성 처리 동의가 이 용도에도 해당하는지 PM 확인이 필요하다.

`/cards`는 서버의 카드 묶음만 보여준다(API 4절). 홈의 `오늘의 대화카드 받기`는 카드 화면으로 가기 전에 홈에서 쓸 묶음을 준비한다(아래 홈 버튼 표). 첫 카드는 명세 4-1대로 정보 입력의 `마치기`에서 생성을 요청한다. 가입 직후에는 홈부터 보여주고 정보는 홈의 `오늘의 대화카드 받기`를 누를 때 물으므로, 이 요청도 보호자가 카드를 받으려 한 뒤에 나간다. 서버가 카드 생성 요청이 한 번이라도 있어야 등록을 마친 것(`completed`)으로 계산해서, 요청하지 않으면 앱을 다시 켰을 때 그 분이 `입력 중`으로 남기 때문이다(2026-10-14 결정). `마치기`는 세부 정보 저장(2-4)이 성공한 뒤 4-1을 요청한다([setup_controller.dart](lib/features/profile_setup/setup_controller.dart)). 4-1이 실패해도 등록은 마치고, 홈 버튼을 누르면 상태를 보고 다시 요청한다. 등록 완료를 카드 생성 여부로 계산하는 방식은 홈에 들어오기 전부터 카드를 만들게 되어 어색하다는 의견이 있어 BE와 다시 맞출 일로 남긴다. [card_generation_controller.dart](lib/features/cards/card_generation_controller.dart)가 4-2로 상태를 묻는다. 이 흐름은 화면에 묶이지 않고 어르신(서버 `profileId`)마다 따로 있어, 기다리는 동안 다른 화면으로 가거나 다른 분으로 바꿔도 이어서 묻는다. 로그아웃과 탈퇴(`forgetCareProfiles`) 때 지운다.

홈 버튼을 누르면(`prepare`). 4-2를 묻는 짧은 동안은 버튼 모양을 바꾸지 않는다. 이미 준비됐으면 곧 카드 화면으로 가므로 바꾸면 깜빡인다:

| 4-2 상태 | 홈 |
| --- | --- |
| `ready`, `inVisit` | 바로 카드 화면으로 간다 |
| `none`, `failed` | 4-1로 생성을 요청한다. 버튼은 면이 조금 흐려지고(도는 중 초록 `#677A60`, 흰 글자 대비 4.6:1) 도는 표시와 함께 `대화 카드를 만들고 있어요`로 바뀐다. 중장년 보호자가 글로도 진행 중임을 알 수 있게 한다. 다시 눌러도 4-1을 또 보내지 않는다 |
| `running` | 위와 같은 버튼으로 3초마다 4-2를 다시 묻는다 |
| `ready` + `needsRefresh` | 옛 카드를 보여주지 않고 4-1로 12장을 모두 새로 만든다. 4-2가 `ready`여도 받아 둔 4-3 묶음이 `needsRefresh`면 같다. 그러지 않으면 카드 화면과 홈을 오가기만 한다. 만드는 동안 버튼 아래 그림자 없는 오프화이트 상자에 i 기호와 `카드를 받은 뒤 어르신 정보가 바뀌어서` / `대화 카드를 새로 만들고 있어요.`를 둔다. 낱말 가운데서 줄이 바뀌지 않게 끊을 곳을 정했다 (2026-11-01 #171에서 PM 확인, 상자 모양은 같은 코멘트의 예시 화면) |
| 기다린 뒤 `ready` | 알림창 `○○ 어르신의 대화 카드가 준비됐어요.` 기다리는 동안 다른 화면에 있어도 보이게 알림창을 쓴다. 카드 화면으로 데려가지 않는다. 그동안 다른 화면에 있을 수 있어서다. 다시 누르면 들어간다 |
| 기다린 뒤 `failed` | 버튼 아래 빨간 글(`AppColors.danger`) `○○ 어르신의 대화 카드를 만들지 못했어요.` / `다시 누르면 새로 만들어요.` |
| 연결 실패, 서버 거절 | 버튼 아래 빨간 글로 이유를 알리고 홈에 남는다 |

실패 안내는 알림창(SnackBar)으로 띄우지 않는다. 알림창이 버튼과 같은 자리에 떠서 버튼을 가렸고, "다시 누르면"이라고 하는 동안 누를 버튼이 보이지 않았다(합성 데이터 화면 캡처로 확인). 글은 저절로 사라지지 않아 다른 화면에 다녀와도 남고, 버튼을 다시 누르면 지운다. 안내는 어르신마다 둔다(`cardNoticeProvider`). 준비됐다는 알림은 알림창으로 두어 다른 화면을 보는 중에도 알 수 있게 한다.

홈 가운데에는 안내 문구 `오늘은 ○○ 님과 무슨 주제로 대화를 나눠볼까요?` 아래로 말풍선과 화분 마스코트를 둔다(디자인 리뉴얼 진행 중, [home_talk.dart](lib/features/home/home_talk.dart)). 말풍선은 처음에 시간대(5~11시, 11~17시, 그 밖) 인사말을 한다. 면회를 마치고 위로 화면의 `홈으로`(또는 뒤로 가기)로 돌아오면 이야기 대신 면회 뒤 인사말(10개 중 무작위)을 한다. 다른 화면에서 홈으로 돌아올 때, 마스코트를 눌러 반응할 때, `오늘의 대화카드 받기`를 누를 때 일대기 이야기(세부 정보 네 항목과 담은 이야기) 하나를 무작위로 골라 위에는 제목 상자(길면 한 줄로 줄임, 오른쪽 화살표), 아래에는 무작위 한마디를 보여준다. 대화 카드를 기다리며 이야기를 한 번 보도록 권하는 말이다. 한마디에는 `이 이야기 재밌겠네요!` 같은 밝은 말이 있어서, 아픈 기억일 수 있는 이야기(`LifeFact.sensitive`)는 고르지 않는다(2026-11-10 PM 결정, 11/10 E2E 문제 5). 보여 주던 이야기에 표시가 붙으면 인사말로 돌아간다. 이야기가 없거나 아직 읽는 중이면 인사말을 바꾼다. 같은 이야기와 같은 말은 연달아 고르지 않는다. 이야기 말풍선을 누르면 그 이야기 화면으로 간다. 카드를 실제로 만들어 다 되면 말풍선이 `대화 카드가 완성됐어요!`로 바뀌고, 이 말풍선이 떠 있는 동안 마스코트는 `><` 얼굴로 떠 있으며 둘러보지 않는다. 다음 이벤트에 다시 이야기와 평소 얼굴로 바뀐다. 다른 화면에 있는 동안 다 되면 홈으로 돌아와도 이 말을 그대로 둔다. 어르신을 바꾸거나 다시 로그인하면 인사말부터 시작한다. 문구는 [home_phrases.dart](lib/features/home/home_phrases.dart)에 모아 두었다(시간대별 인사말 10개씩, 한마디 10개).

홈 본문은 평소에는 스크롤하지 않고 남는 높이에 맞춰 마스코트가 줄어든다. 글자를 1.3배보다 크게 키웠거나 남는 높이가 300보다 낮으면 안내 문구와 말풍선만으로 넘치므로, 마스코트를 140으로 정해 두고 본문을 스크롤한다. `test/home_large_text_test.dart`가 412x917, 360x800에서 글자 1.0, 1.3, 2.0배를 확인한다.

대화 카드 화면(C-1 ~ C-3)은 처음 3장을 보여준다. 목록 끝에는 작은 고리(18px)와 `끝까지 당기면 3장 더 나와요`를 한 줄로 둔다. 끝을 넘겨 당기면 목록이 고무줄처럼 버티며 늘어나고(`BouncingScrollPhysics`), 고리는 당긴 만큼(96px) 채워진다. 손가락을 떼지 않은 채 고리가 한 바퀴 다 차야 0.6초 돌며 `카드를 불러오고 있어요`를 보인 뒤 3장이 더 나온다. 살짝 밀거나 다 차기 전에 놓으면 늘지 않는다. 당길 수 없는 화면 낭독기는 고리를 `대화 카드 3장 더 보기` 버튼으로 읽고 누르면 바로 불러온다. 움직임 줄이기를 켜면 돌지 않고 바로 나온다. 이 목록은 마우스와 트랙패드로도 끌 수 있게 열어 웹 미리보기에서도 당겨 볼 수 있다. 카드 오른쪽 선택 표시는 카드 전체 높이의 가운데에 두며, 펼치면 펼친 카드의 가운데로 옮겨 간다. 원만 누르기 어려워 카드 오른쪽 3분의 1 전체 높이를 고르는 자리로 두었다(`SelectableCard`). 그 안을 누르면 글자 위라도 펼치지 않고 고른다. 원의 자리와 글자 폭은 예전과 같다. 면회 중 카드 추가 화면(E-5)도 같은 카드 모양과 선택 표시를 쓴다.

대화 카드를 만드는 동안 서버는 카드에 쓰는 정보를 고치거나 지우는 요청을 거절한다(`CARD_GENERATION_IN_PROGRESS`). 그래서 이야기 화면의 연필과 휴지통은 이때 누르는 순간 `대화 카드를 만들고 있어요` 안내창을 띄우고 고치는 화면이나 지우기 확인으로 넘어가지 않는다. 다 쓰고 저장할 때 실패하지 않게 하려는 것이다.

마스코트는 [mascot.dart](lib/widgets/mascot.dart)에 있다. 평소에는 천천히 둥실 떠 있고 아래 그림자가 함께 커졌다 작아진다. 5~10초에 한 번 왼쪽이나 오른쪽을 천천히 돌아본다. 누르면 눈웃음으로 꾹 눌렸다가 통 튀고 하트가 한두 개 떠오른다. 반응 중에 다시 눌러도 겹치지 않는다. 위 표에서 실제로 만든 뒤(`making`, `remaking`) `ready`나 `inVisit`가 되면 `><` 얼굴로 천천히 세 번 통통 뛰며 반짝이는 성공 움직임(약 2.6초)을 보여주고, 카드 완성 말풍선이 떠 있는 동안 3.5초씩 쉬며 같은 움직임을 되풀이한다(다른 반응 중이거나 다른 화면이 위에 있으면 미룬다). 이미 있던 묶음을 확인만 했거나 실패했으면 보여주지 않는다. 다른 화면에 있는 동안 끝나면 홈으로 돌아왔을 때 이어서 보인다. 그림을 바꿀 때는 새 그림을 위에 겹쳐 서서히 보이게 해 끊겨 보이지 않게 한다. 기기의 `움직임 줄이기`가 켜져 있으면 몸은 움직이지 않고 표정만 바뀐다. 장식이라 화면 읽기에서는 뺀다.

카드 화면은 들어올 때(`start`) 상태를 다시 묻고 아래 표대로 보여준다. 홈 버튼이 바로 준비된 경우만 들여보내므로 보통은 `ready`다.

| 4-2 상태 | 화면 |
| --- | --- |
| `none`, `failed` | 4-1로 생성을 요청하고 `오늘의 대화 카드를 만들고 있어요` |
| `running` | 3초마다 4-2를 다시 묻는다. 화면을 떠나도 다 될 때까지 묻는다 |
| `ready` | 4-3으로 묶음을 받아 카드 고르기 |
| 기다리다 `failed` | `대화 카드를 만들지 못했어요.` + 다시 시도. 4-2가 실패 이유를 주지 않아 정보 부족과 그 밖의 실패를 가르지 못한다 |
| `inVisit` | 카드 고르기와 `대화 시작하기`를 두지 않는다. `아직 마치지 않은 면회가 있어요. 평가를 마치면 새 대화 카드를 받을 수 있어요.`와 `평가 이어서 하기`를 둔다. 누르면 그 회차의 평가(`visitReviewOf`)로 간다. 회차는 이번 실행에서 시작한 면회면 면회 상태가, 앱을 다시 켰으면 4-3을 새로 받아 `usedBySessionId`로 안다. 4-3이 쓸 묶음이 없다고 하면(404) 상태를 다시 묻고, 받지 못하면 다시 시도를 둔다(#234) |
| `ready` + `needsRefresh` | 옛 카드를 보여주지 않는다. 고르거나 면회를 시작할 수 없다. `카드를 받은 뒤 어르신 정보가 바뀌었어요. 홈에서 오늘의 대화카드 받기를 누르면 새로 만들어요.`와 `홈으로 가기`를 둔다. 카드 화면에서는 만들지 않는다. 4-3 묶음의 `needsRefresh`가 `true`여도 같다 |

`needsRefresh`는 카드를 받은 뒤 프로필이나 일대기를 고친 묶음이다(BE #161). 사진 설명 수정(3-3, #205)과 사진 삭제(3-4, #240), 7-4에서 주제 결정을 승인할 때(#277)도 같고, 설정에서 AI 사진 분석 동의를 꺼(1-6) 보호자 설명이 없는 사진의 AI 설명이 지워질 때도 표시한다(#288). 보호자 설명이 없는 사진의 AI 분석이 끝날 때 표시하던 것은 #275로 없앴다. 세 변경은 11/9 14:42 KST 승인 배포부터 운영에 있다. 그 전 운영(develop `9c2b8276`)에서는 AI 사진 분석에 동의한 계정의 온보딩 `마치기` 첫 묶음이 사진 분석 뒤 `needsRefresh`가 될 수 있었다. 앱은 [card_api.dart](lib/data/card_api.dart)에서 `ready`와 따로 `CardGenerationStatus.needsRefresh`로 받고, 값이 없으면 `false`로 본다. 고칠 때마다 다시 만들지 않고 보호자가 홈 버튼을 누를 때 만든다(PM 기준 사실 정정과 다음 면회 카드 반영). 카드 화면을 연 뒤 고쳐서 5-1이 `CARD_SET_NEEDS_REFRESH`로 거절하면 녹음 안내 화면에 홈에서 새로 받으라고 알리고, 뒤의 카드 화면은 상태를 다시 물어 옛 카드를 감추고 `홈으로 가기`를 보여준다. 카드를 만드는 중에 2-4, 2-7, 2-9가 `CARD_GENERATION_IN_PROGRESS`로 거절하면 `profileFailureMessage`가 카드가 준비된 뒤 다시 하라고 안내한다. 고친 정보를 근거로 한 카드만 표시하거나 다시 만드는 것은 PM과 BE가 정하는 중이라 넣지 않았다.

연결 실패와 서버 거절은 오류 안내와 `다시 시도`를 보여준다. 카드 provider는 Riverpod의 자동 재시도를 끈다. 다시 시도하면 4-1을 또 보내므로 버튼으로만 다시 한다. 목 묶음은 테스트에서만 쓰며(`test/fake_card_api.dart`), 실제 실행에서는 서버에 저장한 프로필(`profileId`)로 카드를 받는다. 로그인하지 않은 목 모드는 세션이 없어 요청을 보내지 않으므로(`ApiSignedOutFailure`) 카드를 받을 수 없다.

H 일대기는 [life_story](lib/features/life_story/)에 있다. 화면은 `LifeFact`를 직접 보지 않고 표시용 `LifeStory`만 본다. 이야기는 세부 정보 네 항목(하시던 일→일, 고향, 취미, 가족)에서 만든 것과 담은 이야기(`lifeFacts[]`)를 합친다. 담은 이야기는 로그인해 서버에 저장한 분이면 서버의 것(2-3, `serverLifeFactsProvider`)이고, 로그인하지 않은 목 모드면 `assets/mock/profile.json`의 합성 이야기 열 편이다. `LifeFact`는 `LifeStory.fromLifeFact` 한 곳에서 바꾸며, 모르는 분류는 `기타`에, 범위 밖 그림 번호는 1~5 안에 둔다. 아픈 기억일 수 있는 이야기(`sensitive`, 없으면 `false`)는 첫 장의 최근 이야기와 목차에서는 제목 아래, 이야기 화면에서는 제목 위에 카드와 같은 `조심스러운 이야기` 표시(`SensitiveCardBadge`)를 단다(2026-11-10 PM 결정). 변경 사항 확인에서 승인한 이야기는 AI가 붙인 표시를 서버가 그대로 옮긴다(7-4). 이야기 수정 화면에는 표시를 바꾸는 칸이 없고, 고쳐도 2-7에 `sensitive`를 보내지 않아 표시는 그대로다. 분류(`storyCategory`)와 그림 번호(`imageNumber`)의 필드 이름은 임시다(api-spec 미정 사항 11). 정렬은 생애 시기 대신 담은 날짜순이며, 세부 정보 이야기는 날짜가 없어 목차 맨 앞에 두고 날짜를 표시하지 않는다. 기본 이미지는 분류마다 다섯 장(`assets/images/life-story-<분류>-<1~5>.webp`)이고 파일이 없으면 분류 아이콘과 `가족 3` 같은 이름으로 자리를 채운다. 세부 정보 이야기의 이미지 번호는 저장할 곳이 없어 어르신 ID와 항목 이름으로 계산한다(`detailImageNumber`). 추가, 수정, 삭제는 `lifeStoryStoreProvider` 한 곳을 거친다. 서버에 저장한 분이면 2-6, 2-7, 2-9로 보내고 응답으로 목록을 바로 고치며, 실패하면 안내하고 쓰던 내용과 이야기를 그대로 둔다. 서버가 없는 이야기(`LIFE_FACT_NOT_FOUND`)라고 답하면 목록을 다시 읽는다. 변경 사항 확인에서 이야기를 승인하면 서버가 일대기에 담지만 7-4 응답에 그 이야기가 없으므로, 승인이 성공하면 `LifeStoryStore.reload`로 다음에 일대기를 열 때 다시 읽게 한다. 지우기 확인창은 이 이야기로 이미 만든 대화 카드와 리포트가 그대로 남는다고 알린다(2-9는 이야기 행만 지운다). 목 모드에서는 어르신 목록처럼 **앱이 켜져 있는 동안만** 어르신별로 기억한다(`lifeStoryEditsProvider`). 로그아웃과 탈퇴 때 `forgetCareProfiles`가 함께 지운다.

하단 탭은 왼쪽부터 일대기, 리포트, 홈, 마이페이지, 설정이다([app_scaffold.dart](lib/widgets/app_scaffold.dart)). 탭 화면(일대기 표지 `/album`, 리포트 기록 `/reports`, 홈, 프로필 설정 `/profile`, 설정)과 알림은 라우터의 `ShellRoute`(`_TabShell`)로 묶어 하단 탭을 한 번만 그리고, 화면이 바뀌어도 탭은 그대로 둔 채 위 내용만 바꾼다. 알림은 `홈` 탭을 고른다. 마이페이지는 메뉴를 띄우지 않고 프로필 설정으로 바로 간다. 리포트 기록은 리포트 탭으로 옮겼다. 홈에서는 탭 화면을 위에 쌓고, 다른 탭 화면에서는 그 자리를 바꿔 끼워 뒤로 가기는 늘 홈으로 돌아온다. 일대기와 리포트는 어르신이 있어야 열고 없으면 등록부터 안내한다. 고른 탭 위에 짧은 초록 막대를 두고, 고른 탭이 바뀌면 그 자리로 0.3초 동안 미끄러진다. 화면마다 탭을 따로 그리면 새 화면이 나타나는 동안 막대 움직임이 가려져서 이렇게 했다. 막대는 탭이 바뀐 프레임을 다 그린 뒤 다음 프레임부터 움직인다. 프로필 설정, 설정처럼 처음 그릴 것이 많은 화면은 그 한 프레임이 길어, 바로 움직이면 그사이 시간이 다 지나 순간이동처럼 보였다. 움직임 줄이기가 켜져 있으면 바로 옮긴다. 탭 높이는 기본 64이고 글자를 키우면 그만큼 높아져 글자가 잘리지 않는다. 책을 펼친 뒤의 일대기 화면은 이 위에 쌓여 하단 탭이 없다. 탭 화면과 알림은 상단바에 뒤로가기와 화면 이름을 한 줄로 둔다. 일대기는 첫 화면(표지)에만 `일대기`를 두고, 책을 펼친 뒤의 화면은 이름 없이 뒤로가기만 둔다. 일대기 첫 화면(앨범 표지)은 2026-11-06 디자인 리뉴얼에서 처음 색을 입혔다. 바탕과 상단바는 홈과 같은 오프화이트(`#FBFAF6`), 표지는 빈티지 초록 천(`#385443`, 처음 버건디에서 바꿈)에 책등, 오른쪽 위아래 가죽 모서리, 금박 테두리를 두고, 오른쪽과 아래로 종이 줄과 그림자를 보여 두께감을 내고. 동그란 금 액자의 프로필 사진(`ProfileAvatar`), `○○○ 님의`와 `앨범` 두 줄, 짧은 금색 밑줄을 한 묶음으로 금박 테두리 한가운데에 둔다. 표지 밑에는 첫 장(`_InnerPage`)이 있어 표지가 넘어가는 동안 테이프로 붙인 흑백 풍경 사진과 손글씨 같은 잔물결 줄 몇 개가 보인다. 둘 다 장식이고 실제 이야기를 담지 않는다. 이름 줄은 넘치면 글자를 줄여 긴 이름에도 깨지지 않는다. `지금까지 n편의 이야기가 담겨 있어요`의 `n편`은 굵은 초록이다. 바탕에는 초록 꽃잎 여섯 장이 오른쪽에서 왼쪽으로 살랑이며 지나가고(한 바퀴 44초), 책이나 글자 뒤로 지나갈 뿐 어디에도 내려앉지 않는다. 움직임 줄이기를 켜면 꽃잎을 그리지 않고, 테스트는 `AlbumPetals.motion`을 끈다. 하단 탭은 어느 탭에서든 고른 탭을 초록으로 칠한다. 화면 낭독기는 책을 `앨범 펼치기`로 읽는다. 탭과 상단바 이름은 `일대기` 그대로다.

설정([settings_screen.dart](lib/features/settings/settings_screen.dart))은 프로필 설정에 있던 계정 항목을 옮겨 왔다(2026-11-06). 2026-11-08 위에서부터 `알림 설정`, `도움말`, `계정 약관 동의` 세 구역으로 나누고, 동의 항목은 한 단계 들어간 화면으로 옮겼다. 세 구역 모두 제목과 작은 회색 글을 한 묶음으로 두고 그 오른쪽 가운데에 알림 설정은 켜고 끄는 스위치를, 나머지 둘은 꺾쇠(`>`)를 스위치의 누름 영역(48)과 같은 폭에 둔다. 제목과 글 사이 간격은 8이고 스위치의 누름 영역이 간격을 벌리지 않게 묶음 옆에 둔다. 알림 설정의 글은 `만남 리포트가 완성되면 알려드려요.`다. `도움말`(`새록 소개를 다시 볼 수 있어요.`)을 누르면 처음 오셨네요의 새록 소개 창을 그대로 띄운다. 다시 볼 때는 마지막 장의 버튼이 `시작하기` 대신 `닫기`이고 닫으면 설정에 남는다. `계정 약관 동의`(`함께하는 모든 분에게 똑같이 적용돼요.`)를 누르면 `/settings/consents`([consent_settings_screen.dart](lib/features/settings/consent_settings_screen.dart))로 들어간다. 그 아래 한 줄에 밑줄 글자의 `로그아웃 · 회원탈퇴`를 가운데 점으로 나눠 둔다(글자를 키워 넘치면 두 줄).

계정 약관 동의 화면은 상단바에 뒤로가기와 `계정 약관 동의`를 두고, 회색 글 아래에 다섯 항목(필수인 개인정보 처리와 건강 민감정보 처리, 선택인 알림 수신, 서비스 개선 활용, AI 사진 분석)과 전체 동의, 저장하기를 둔다(`consent_terms.dart`의 `consentTerms`). 알림 항목의 쓰임새 문구는 빼 설정의 알림 설정에만 둔다. 체크박스와 항목 이름은 한 줄에서 세로 가운데를 맞추고 `자세히 보기`는 이름과 같은 왼쪽 선 아래에 둔다. 알림 수신 동의 줄을 감싼 강조 상자는 평소에 바탕을 비워 커서를 올렸을 때의 회색 표시가 다른 줄처럼 보인다. 설정과 이 화면은 360dp, 글자 1.3배와 2.0배에서 넘치지 않는지 위젯 테스트로 확인했다(`test/consent_settings_test.dart`). 글자를 키운 넘침은 실기기에서 확인하지 않았다. 11/9 승인 배포 뒤 Galaxy S22에서 운영 서버로 이 화면의 다섯 항목 표시는 확인했다(팀 운영 기록).

- 알림은 서버에 저장된 `[선택] 알림 수신 동의`가 있어야 켤 수 있다. 꺼진 스위치를 켜려 하면 켜지 않고 빨간 글로 `아래 계정 약관 동의에서 알림 수신 동의에 체크하고 저장해야 알림을 켤 수 있어요.`를 알린다. 이 안내가 떠 있는 동안 계정 약관 동의에 들어가면 `알림 수신 동의에 체크하고 저장하면 알림이 켜져요.`를 빨간 글로 보이고, 그 동의 줄을 보이는 자리로 끌어와 연한 빨간 바탕과 테두리로 두 번 깜빡인 뒤 표시를 남긴다. 움직임 줄이기가 켜져 있으면 깜빡이지 않고 표시만 한다. 체크하면 표시가 사라지고, 저장하기로 저장하면 설정의 스위치도 켜진다. 안내 없이 들어가면 강조하지 않는다. 동의 항목이 같은 화면에 있던 예전에는 체크만 한 채 스위치를 켤 수 있었지만, 이제 동의는 들어간 화면의 저장하기로 저장한다.
- 알림 스위치는 서버에 저장된 알림 수신 동의(1-6 `pushNotification`)를 그대로 보여주고, 켜고 끄면 그 동의만 바로 저장한다(저장하기를 기다리지 않는다). 리포트 완료 알림은 이 동의로만 정해지기 때문이다. 동의가 있으면 앱이 기기를 등록하고([푸시 알림](#푸시-알림)), 동의를 거두면 서버가 그 계정의 기기 등록을 같은 트랜잭션에서 지운다. 따로 저장하는 알림 설정은 없다(2026-11-07 PR #255 리뷰). 끄면 계정 약관 동의의 알림 수신 동의 체크도 빠지고, 저장하지 못하면 알리고 켜진 채로 둔다. 로그인하지 않은 목 모드는 화면에서만 바꾼다. 계정 약관 동의에서 체크를 바꿔 저장하기로 저장해도 스위치가 따라 바뀐다.
- 동의 저장(1-6)은 예전 규칙 그대로다. 바꾼 선택 동의만 보내고, 필수 동의를 빼면 저장할 수 없다. 저장한 뒤에도 계정 약관 동의 화면을 닫지 않는다. 저장하는 동안 설정으로 돌아가 회원탈퇴 등 다른 화면을 열어도 저장을 마쳤을 때 그 화면을 닫지 않는다. 바꾼 것이 없으면 `바꾼 동의가 없어요.`를 알린다.
- 프로필 설정은 이제 지금 어르신의 사진, 기본 정보, 세부 정보, 갤러리만 보여준다. 맨 위 사진과 이름은 바탕 위에 바로 두고 그 아래에 덩굴 모양 꾸밈 선(양 끝으로 잦아드는 물결 선 두 줄기와 가운데 잎 한 쌍, `_VineDivider`)을 그어 아래 구역과 나눈다. 연초록 면을 깔았더니 어색해 2026-11-06 뺐다. 사진에는 흰 테, 얇은 선과 그림자를 준다. 갤러리 사진을 누르면 설명 칸이 높이가 늘며 아래에서 살짝 떠오르듯 펼쳐지고(0.28초), 다 펼쳐진 뒤 끝까지 스크롤해 칸을 화면 맨 아래에 붙인다(갤러리가 마지막 구역이라 사진은 그 위에 보인다). 이미 끝이면 그대로 두고, 접으면 펼치기 전 자리로 돌아간다(`test/profile_gallery_scroll_test.dart`). 기본 정보 수정과 세부 정보 수정은 화면 이름을 본문의 큰 제목 대신 상단바 뒤로가기 옆에 둔다. 처음 등록할 때의 `기본 정보 입력` 제목은 그대로다. 프로필 설정과 세부 정보 수정은 `ScreenBody`의 `scrollable`(내용 높이를 미리 재는 `IntrinsicHeight`) 대신 그냥 스크롤한다. 여러 줄 입력칸(갤러리 사진 설명, 세부 정보)은 그 값이 실제보다 작게 나와 맨 아래 저장하기 쪽이 넘쳤다(웹에서 1픽셀, 작은 화면에서 25~33픽셀).

`/notifications`는 홈의 리포트 알림 상태(`ReportNotice`)를 그대로 다시 보여주는 화면이라 지금은 한 번에 한 건만 뜬다. 날짜별로 여러 건이 쌓인 이력을 보여주려면 데이터 모델을 넓혀야 한다. 알림은 내용 높이만큼의 테두리 상자 하나에 왼쪽 편지 아이콘(연초록 원에 초록 아이콘), 날짜(작은 회색), 제목(크고 굵게), 오른쪽 끝 안내와 화살표로 보여준다. 쓰임새가 없던 오른쪽 위 메뉴 아이콘은 뺐다.

설정(`/settings`)의 로그아웃과 `/profile/delete`의 탈퇴하기는 서버에 연결했다([로그아웃과 탈퇴](#로그아웃과-탈퇴)). `/profile`의 갤러리는 올린 사진을 세 칸씩 보여주고, 분석이 끝나지 않은 사진에는 `분석 중`, 실패한 사진에는 `분석 실패`를 붙인다. 사진을 누르면 그 아래에 AI가 만든 설명(`ProfilePhoto.description`)이 `AI가 만든 설명`이라는 이름표와 함께 펼쳐지고, 보호자가 고쳐 저장하면 이름표가 `사진에 대한 설명`으로 바뀐다. 분석 중인 사진은 설명 대신 상태만 알린다. 분석에 실패한 사진은 실패를 알리고 보호자가 직접 설명을 적어 저장할 수 있으며, 저장하면 `분석 실패` 표시를 뗀다. AI 사진 분석(선택 동의 `photoAnalysis`)에 동의하지 않은 계정의 사진은 worker가 분석하지 않아 `pending`으로 남는다. 이때는 `분석 중`을 붙이지 않고, 사진을 누르면 기다리라는 안내 대신 동의하지 않아 자동으로 만들지 않는다는 안내와 입력칸을 바로 보여준다(`photoAnalysisWantedProvider`). 3-2로 상태를 다시 묻지도 않는다. 보호자가 적은 설명은 분석 상태와 관계없이 카드 생성 입력에 들어간다(BE `card_sets.py`). 로그인한 계정의 설명 수정은 [photo_description_store.dart](lib/features/profile/photo_description_store.dart)가 API 3-3에 저장하며, 성공 응답을 받은 뒤 화면에 반영한다. 서버는 보호자의 수정과 AI 원문을 따로 보관하므로 늦게 끝난 분석이 수정한 설명을 덮어쓰지 않는다. 앱을 다시 열어도 `descriptionSource=caregiver`인 설명을 표시한다. 저장하지 못하면 작성 중인 내용을 유지한다. 로그인하지 않은 목 모드는 앱 안에서만 저장한다. 목 사진의 `imageUrl`은 계약 예시 주소라 `MockRepository`가 읽을 때 앱에 든 합성 그림으로 바꾼다. 사진은 어르신마다의 `photos[]`다. 로그인해 서버에 저장한 분은 `serverProfilePhotosProvider`가 2-3 응답의 `photos[]`를 읽고, 분석이 끝나지 않은 사진은 갤러리를 보는 동안 3-2로 5초마다 물어 끝나면 설명이나 `분석 실패`로 바꾼다. 사진 목록을 읽는 중에 갤러리를 닫으면 늦게 온 응답으로 묻기 시작하지 않는다. 읽지 못하면 사진이 없다고 하지 않고 `다시 시도`를 둔다. 조회 주소(`imageUrl`)는 수명이 짧아 갤러리를 다시 열 때 새로 받는다. 로그인 없이 들어온 분은 `profileProvider`가 목 사진을 고른 어르신의 것으로 붙인다. 고친 설명은 계정, 어르신, 사진마다 따로 두어 다른 계정이나 다른 어르신에게 보이지 않고, 저장 응답은 저장한 사진에만 반영한다. 로그아웃과 탈퇴로 어르신 정보를 지울 때 함께 지운다.

갤러리 머리글에는 기본 정보, 세부 정보와 달리 `수정하기`를 두지 않는다. 설명은 사진을 눌러 그 자리에서 고치고, 사진 삭제는 서버 API(3-4, #240)만 있고 앱 화면은 아직 없기 때문이다. 보관 동의 철회 동선은 미정 사항 7로 남아 있다.

서버에 저장한 분은 갤러리 아래 `사진 추가하기`로 등록 뒤에도 사진을 더 올린다(`/profile/photos/add`, 3-1). 피그마 설계가 없어 B-7 화면을 그대로 쓰며, 이미 올린 장수를 빼고 합쳐 5장까지 고르게 한다. 올리는 중, 실패, 다시 올리기, 올리지 못한 사진은 빼고 마치기는 B-7과 같고 업로드 순서도 같은 함수(`uploadPendingPhotos`)로 처리한다. 올리는 중에는 뒤로 가지 못한다. 다 올리면 `갤러리로 돌아가기`를 두고, 갤러리는 서버의 사진(2-3)을 다시 읽는다. 5장을 채웠으면 버튼을 막고 "사진은 5장까지 올릴 수 있어요."를 알린다. 로그인 없이 보는 목 사진에는 올릴 곳이 없어 버튼을 두지 않는다.

`/profile/delete`의 탈퇴 이유 설문은 계약이나 법률 문서에 속한 값이 아니라 화면 문구다. 탈퇴 후 재가입 가능 여부는 `docs/legal/` 어디에도 정해진 내용이 없어 화면에 적지 않았다.

## 현재 사용자 흐름

동의와 프로필 입력 → 대화 카드 선택 → 면회 사진과 녹음 화면 → 보호자 소감 및 평가 → 보호자 위로 → 홈에서 리포트 준비 상태 확인 → 리포트 → 변경 제안 확인. PR #42에서 별도 처리 중 화면을 제거했다. 로그인했으면 리포트 상태, 리포트와 변경 제안을 서버에서 읽는다(아래 "리포트 상태와 조회"). 로그인 없이 들어오면 리포트 생성을 목 타이머로 표시한다. 소감 화면의 `리포트 만들기`는 평가(API 6-1)를 저장한 뒤 녹음과 참여자 수(6-2)를 보내고, 둘 다 서버가 받아야 넘어간다([submission_controller.dart](lib/features/review/submission_controller.dart)). 실패하면 화면에 남아 다시 누르게 하며, 저장한 평가는 다시 보내지 않고 녹음만 보낸다. 서버가 녹음을 받으면(`202`) 기기의 녹음을 다시 보낼 목록에서만 빼고(파일은 남긴다) 받은 `analysisId`로 리포트 알림을 시작한다. 받은 `analysisId`는 `submissionProvider`에도 둔다. 이미 끝났거나 실패로 끝난 회차라는 거절(`ANALYSIS_ALREADY_COMPLETED`, `ANALYSIS_ALREADY_FAILED`)도 다시 보낼 목록에서만 빼고 알림 없이 마친다. 녹음 파일이나 참여자 수가 없으면 보내지 않고, 소감은 저장했으며 녹음이 없어 리포트를 만들 수 없다고 안내한다([면회 녹음](#면회-녹음)). 서버의 6-2는 평가를 저장한 회차만 받는다. 보호자 위로 화면은 Q1 대화 만족도(1~5)에 맞춘 고정 문구 5개 중 하나를 보여주고, 서버와 AI를 부르지 않는다. 맨 위에는 눈을 감고 잠든 마스코트([sleeping_mascot.dart](lib/widgets/sleeping_mascot.dart), `assets/images/mascot/sleep.webp`)가 바닥 그림자 위에서 천천히 둥실 떠 있다(한 번 4.8초). 마스코트를 누르면 몸이 살짝 눌렸다 돌아온다. 움직임 줄이기를 켜면 그림자와 함께 가만히 있다. 2026-11-07 예전 포옹 그림(`comfort_hug.webp`)을 바꿨다. 문구는 [comfort_messages.dart](lib/features/review/comfort_messages.dart)에 있다. 화면별 상세 경로는 위 표를 따른다.

알림 수신은 선택이며 거부해도 가입과 기본 기능을 차단하지 않는다. PR #49에서 BE도 같은 선택 동의 기준으로 맞췄다. 앱 재실행 시 로그인 복원과 만료 후 자동 재인증은 아래 "세션 보관"에 구현했다. 만료 후 자동 재인증은 실기기에서 확인했다(아래 "사용 중 세션 만료"). PR #50에 함께 요청한 약관의 서버 관리는 서버가 약관 본문을 내려주어야 해서 아직 하지 않았다.

## 함께하는 소중한 분

한 보호자가 어르신을 최대 3분까지 등록해 바꿔 가며 쓰는 부가기능이다. 첫 분은 홈의 `오늘의 대화카드 받기`에서 등록하고(아래 "가입 직후 홈 먼저 보여주기"), 추가는 그 뒤에 한다. 다른 어르신의 대화 카드로 면회하는 실수를 막으려고 지금 어르신의 이름을 여러 곳에 보여준다.

| 자리 | 동작 |
| --- | --- |
| 홈 상단 | 알약(성별 기본 사진과 `○○님 (관계)`). 관계는 기본 정보에서 보호자가 적은 값이며, 적지 않았거나 이 휴대폰에 없으면 `○○님`만 보인다(`careDisplayName`). 누르면 `/profiles`. 두 분 이상이면 오른쪽 원형 화살표로 다음 분에게 바로 넘어가고 `지금부터 ○○님과 함께해요`를 띄운다 |
| 홈 안내 | `오늘은 ○○ 님과 무슨 주제로 대화를 나눠볼까요?` |
| `/profiles` | 상단바 제목은 `프로필 전환`, 본문 큰 제목은 `함께하는 소중한 분`이다. 슬롯에는 홈 알약과 같은 `○○님 (관계)`를 쓰고, 버튼은 `프로필 추가`, `프로필 정보 지우기`다. 슬롯 3개. 누르면 전환, 빈 슬롯은 추가, 등록하다 나간 분은 `입력 중`으로 남아 이어서 입력. 다시 열면 가 본 가장 먼 단계에서 시작하고(기본 정보를 비웠으면 기본 정보부터), 적어 둔 생애 정보는 그 항목의 글 입력칸에 채워 보여준다. 꾹 눌러 끌면 순서를 바꾸고 이 순서가 화살표 순서다. 맨 아래 버튼으로 지울 분을 골라 확인 후 지운다. 마지막 한 분도 같은 확인창으로 지우며 계정은 남는다 |
| 어르신 추가 | 처음 오셨네요를 건너뛰고 기본 정보부터 입력한다. 마치면 새 분으로 바뀌고 `지금부터 ○○님과 함께해요`를 띄운다. 사진을 올리고 마쳤으면 띄우지 않는다. 홈 아래에 뜨는 사진 준비 안내의 아랫줄을 알림 띠가 가렸고(2026-11-10 E2E), 새 분의 이름은 홈 제목과 위 알약에 바로 보인다 |
| 프로필 설정 | 지금 어르신의 기본 정보와 세부 정보를 보여준다. 사진 아래 이름은 홈 알약과 같은 `○○님 (관계)`이고, 관계를 적지 않았거나 이 휴대폰에 없으면 `○○님`이다. 기본 정보의 `수정하기`나 이름 옆 연필은 `/profile/edit/basic`을 연다. 처음 입력할 때의 기본 정보 폼을 그대로 쓰고, 고친 값은 그 어르신에게만 남으며 세부 정보는 그대로다. 이름은 50자까지다(온보딩도 같다). 기본 정보는 이름, 성별, 관계, 생년월일, 현재 상태 순서이고, 관계는 `예) 어머니, 아버지`를 안내 글자로 둔 20자 이하의 선택 자유 입력이다. 관계는 서버에 보내지 않는다(아래 "관계는 단말에만 둔다"). 적지 않았으면 프로필 설정에 관계 줄이 없다. 사진 올리기 제목은 `○○님과 관련된 사진을 올려주세요`다. 세부 정보의 `수정하기`는 `/profile/edit/details`를 열어 직업, 고향, 취미, 가족을 글로 고치고, 비운 항목은 지운다(`null`). 계정 약관 동의, 로그아웃과 회원탈퇴는 2026-11-06 설정으로 옮겼고 동의는 2026-11-08 `/settings/consents`로 들어갔다(#271). 동의는 로그인했으면 서버(1-3 `GET /auth/me`)에서 읽고, `저장하기`는 바꾼 선택 동의(알림 수신, 서비스 개선, AI 사진 분석)만 1-6 `PATCH /auth/me/consents`로 보낸다([account_api.dart](lib/data/account_api.dart)). 나머지 저장 규칙은 위 설정 설명을 따른다. 설정은 계정 정보를 읽지 못해도(예: 세션 만료로 401) `로그아웃`을 남겨, 로그아웃한 뒤 다시 로그인할 수 있다. 로그아웃 응답을 기다리는 동안 세션이 지워져 설정 화면이 다시 그려져도, 한 번 누르면 로그인 화면까지 간다 |
| 회원 탈퇴 | 계정 전체를 지우므로 특정 어르신 이름을 부르지 않는다 |

입력 흐름의 `어르신` 문구도 바꿨다. 이름 안내 글자는 `함께하는 분의 성함을 입력해주세요`, 하시던 일 질문은 `예전에 어떤 일을 하셨나요?`, 등록을 마친 알림은 `지금부터 ○○님과 함께해요`다.

어르신마다 나뉘는 것은 기본 정보, 세부 정보 네 항목(직업·고향·취미·가족), 홈 리포트 알림, 대화 카드 선택이다. 로그인했으면 리포트 상태와 리포트 기록도 서버가 어르신마다 내려준다(5-4, 7-1). 서버에 저장한 분은 일대기 이야기(2-3의 `lifeFacts[]`)와 프로필 사진(2-3, 3-1)도 서버에서 읽는다. 로그인하지 않은 목 모드에서는 생애 정보와 사진을 목 데이터 한 벌로 함께 쓴다. 대화 카드는 로그인 여부와 관계없이 서버(4-1~4-3)에서 받으며, 목 카드 묶음은 테스트에서만 쓴다(`test/fake_card_api.dart`).

**로그인 세션이 있으면 어르신 목록은 서버가 기준이다**([profile_api.dart](lib/data/profile_api.dart), `api-spec.md` 2절). 세션이 생기면 2-1로 목록을, 2-3으로 한 분씩 기본 정보와 세부 정보를 불러온다. 서버의 `inProgress`(첫 카드 생성 전)는 `입력 중` 슬롯으로 두고, 누르면 서버 값에 단말 초안(아래 "등록하다 멈춘 세부 정보")을 더해 멈춘 단계부터 이어서 입력한다. 초안이 없으면 서버 값으로 세부 정보 첫 항목부터 연다. 프로필 입력은 기본 정보의 `다음`에서 2-2로 만들고(다시 오면 2-4로 고침), `마치기`에서 세부 정보 네 항목을 2-4로 저장한다. 프로필 설정의 수정은 2-4, 함께하는 소중한 분의 지우기는 2-8로 먼저 저장한 뒤 화면에 반영한다. 저장하는 동안 버튼을 막고, 실패하면 이유(연결 실패, 3분 초과, 프로필 없음, 로그인 풀림)를 알리고 그대로 둔다. 목록을 불러오는 동안과 실패했을 때 홈, 프로필 설정, 함께하는 소중한 분과 어르신이 필요한 화면은 등록 안내 대신 로딩과 다시 시도를 보여준다(`CareProfilesLoading`). 슬롯 순서는 서버에 저장하지 않아 다시 불러오면 만든 순서로 돌아간다. 카드 생성(4-1)은 서버 `profileId`(`Profile.profileId`, 서버에 저장한 분은 `CareProfileEntry.remoteId`)를 쓴다.

로그인 세션이 없으면(구글 설정이 없는 디버그 빌드의 임시 건너뛰기) 서버를 부르지 않고 **앱이 켜져 있는 동안만 기억한다.** 단말 보관 범위가 정해지지 않아(이슈 18) 어느 쪽이든 목록은 단말 저장소에 쓰지 않는다. 로그아웃 또는 탈퇴하면 목록을 비운다(`forgetCareProfiles`).

**등록하다 멈춘 세부 정보는 단말에 초안으로 둔다**(2026-11-10 UX 점검 15, [setup_draft_store.dart](lib/data/setup_draft_store.dart), [setup_draft_keeper.dart](lib/features/profile_setup/setup_draft_keeper.dart)). 하시던 일, 고향, 취미, 가족은 사진 단계의 `마치기`(2-4)에서만 서버에 저장하므로, 그 전에 앱이 꺼지면 항목마다 길게 말한 답이 사라졌다. 기본 정보의 `다음`으로 서버에 프로필을 만든 뒤(2-2)부터 입력이 바뀔 때마다 계정 ID와 서버 프로필 ID를 키로 세션과 같은 보안 저장소에 초안을 쓴다. 첫 등록과 더 등록하는 분 모두 같다(입력 흐름의 `SetupController`가 쓰고 화면을 거치지 않는다). 담는 값은 글로 된 답(말로 답해 알아들은 문장 포함), 가 본 가장 먼 단계, 이 분에게 올린 사진 수뿐이다. 녹음 파일, 고른 사진의 경로와 기본 정보는 두지 않는다(기본 정보는 서버에 있다). 글자마다 바뀌어도 프로필마다 한 줄로 세워 마지막 값만 쓴다. 앱을 다시 켜고 `입력 중`인 분을 누르면(홈의 `오늘의 대화카드 받기` 포함) 서버의 기본 정보에 초안의 답을 채워 멈춘 단계부터 연다. 앱이 켜져 있는 동안 남긴 입력(`pendingSetupsProvider`)이 있으면 그것을 먼저 쓴다. 사진 단계에서는 올린 사진 수만큼 덜 고르게 하고 `2장을 올렸어요. 3장 더 올릴 수 있어요.`처럼 알린다. 고른 사진이 없으면 아래 버튼은 `건너뛰기` 대신 `홈으로`이고, 다섯 장을 다 올렸으면 `사진 5장을 모두 올렸어요.`만 두고 고르는 자리를 숨긴다. 사진 장수는 서버(2-3의 `photos`)에 다시 묻지 않고 초안의 수를 쓴다. 등록을 마치면(2-4 성공) 초안을 지우고, 2-4가 실패하면 남겨 다시 이어 간다. 함께하는 소중한 분에서 `입력 중`인 분을 지우면(2-8 성공 뒤) 그 초안을, 탈퇴하면 그 계정의 초안을 모두 지운다. 로그아웃해도 남기며 다른 계정의 초안은 읽지 않는다. 로그인 없이 들어온 경우는 남기지 않는다. 단말에 세부 정보 초안을 두는 것도 개발과 테스트를 위한 가정이며 단말 보관 범위를 확정한 것이 아니다. 검증은 `test/setup_draft_test.dart`(가짜 저장소로 앱을 다시 켜는 것을 새 컨테이너와 화면으로 대신함)와 `google_login_test.dart`의 탈퇴 테스트다.

**관계는 단말에만 둔다**([profile_relationship_store.dart](lib/data/profile_relationship_store.dart)). 관계는 앱에서 `○○님 (어머니)`처럼 부를 때만 쓰는 별명이라 서버 계약(2-2, 2-4)과 DB에 넣지 않는다. 계정 ID와 서버 프로필 ID를 키로 세션과 같은 보안 저장소에 두고, 서버 목록(2-3)을 불러올 때 읽어 기본 정보에 붙인다. 기본 정보 입력에서 서버에 만든 직후(2-2), 등록을 마칠 때와 기본 정보를 고칠 때 저장하고, 비우면 지운다. 기본 정보 수정은 서버 응답에 관계가 없어 고친 값을 그대로 붙인다. 프로필을 지우면 그 관계를, 탈퇴하면 그 계정의 관계를 모두 지우며, 로그아웃해도 남긴다. 다른 휴대폰이나 앱을 다시 설치한 뒤에는 이름만 보인다. 로그인 없이 들어온 경우는 앱이 켜져 있는 동안만 쓴다. 단말에 관계를 두는 것도 개발과 테스트를 위한 가정이며 단말 보관 범위를 확정한 것이 아니다.

**마지막으로 고른 어르신은 계정마다 단말에 기억한다**(이슈 144, [selected_profile_store.dart](lib/data/selected_profile_store.dart)). 앱을 다시 켜면 첫 분으로 돌아가 모르고 다른 어르신으로 면회를 기록할 수 있어서다. 보관하는 값은 계정 ID를 키로 한 서버 프로필 ID 하나이며 세션과 같은 보안 저장소에 둔다. 서버 목록과 기억한 분을 모두 읽은 뒤에 목록을 내보내 첫 분이 잠깐 골라지지 않게 한다. 기억한 분이 지워졌거나 입력 중이면 고를 수 있는 첫 분으로 열고, 남은 분이 없으면 기억을 지운다. 목록을 불러오는 중이거나 실패했을 때는 기억을 건드리지 않는다. 다른 계정의 기억은 읽지 않고, 로그아웃해도 남겨 다시 로그인하면 그 분으로 연다. 탈퇴하면 그 계정의 기억을 지운다. 로그인 없이 들어온 경우는 기억하지 않는다. 단말에 프로필 ID를 두는 것은 개발과 테스트를 위한 가정이며 단말 보관 범위를 확정한 것이 아니다. 세부 정보는 `Profile`의 `occupation`, `hometown`, `hobby`, `family`로 다루며 건너뛴 항목은 `null`이다. 등록을 마친 분의 사진은 서버에 저장한 분이면 서버에서(`serverProfilePhotosProvider`), 로그인하지 않았으면 목 데이터에서 읽고, 입력 화면의 음성 예시는 `profileSampleProvider`로 목 데이터를 읽는다. 코드는 [providers.dart](lib/data/providers.dart)의 `careProfilesProvider`와 [setup_controller.dart](lib/features/profile_setup/setup_controller.dart)의 `pendingSetupsProvider`다.

홈 리포트 알림은 계정과 어르신마다 따로 둔다. 로그아웃해도 지우지 않으며, 다른 계정으로 들어오면 보이지 않고 원래 계정으로 다시 들어오면 다시 보인다. 로그아웃한 사이 도착한 리포트도 기다리던 계정에 남는다. 탈퇴하면 그 계정의 알림만 지운다. 이 알림도 앱이 켜져 있는 동안만 기억한다. 로그인한 계정은 다시 들어오면 서버에서 같은 어르신을 불러오므로 알림도 다시 보인다. 로그인 없이 들어온 경우는 로그아웃하면 어르신 목록이 비어 알림을 띄울 어르신이 없다.

### 리포트 상태와 조회

로그인했으면 [report_api.dart](lib/data/report_api.dart)로 서버를 부른다. 로그인 없이 들어오면 목 데이터를 쓴다.

| 자리 | 서버 호출 | 동작 |
| --- | --- | --- |
| 홈 알림 | 5-4, 6-3 | 서버에 저장한 어르신을 처음 볼 때 가장 최근 회차를 묻는다. `processing`이면 `리포트를 만들고 있어요`를 띄우고 분석 작업(6-3)을 5초마다 물어 `completed`이면 도착, `failed`이면 `리포트를 만들지 못했어요`로 바꾼다. `completed` 회차는 도착, `failed` 회차는 실패로 띄운다. 실패면 6-3의 `errorCode`(5-4는 이유를 주지 않아 실패 회차의 6-3을 한 번 더 묻는다)가 `EMPTY_TRANSCRIPT`일 때 `녹음에서 말소리를 찾지 못했어요.`, `AI_SERVER_TIMEOUT`일 때 `녹음이 너무 길거나 서버가 바빠 시간 안에 끝내지 못했어요.`를 제목 아래에 한 줄 덧붙인다. 홈 배너와 알림 화면이 같다. 다른 이유와 묻지 못한 경우는 원래 문구만 둔다(2026-11-10 E2E, `analysisFailureReason`). 앱을 다시 켜면 같은 회차를 다시 묻는다. 띄운 알림이 없을 때 묻지 못하면 `리포트 상태를 확인하지 못했어요`를 띄우고, 누르면 다시 묻는다 |
| 면회 이어가기 | 5-4 | 앱을 떠난 사이 평가 전(`evaluationPending`)이면 `평가 이어서 하기`, 음성 접수 전(`audioPending`)이면 `음성 다시 보내기`를 띄운다. 누르면 `AppRoutes.visitReviewOf`(`/visit/review?session=회차ID`), `visitUploadOf`(`/visit/upload?session=회차ID`)로 간다. 회차 ID로 화면을 여는 일과 `/visit/upload` 화면은 면회 흐름이 맡는다 |
| 리포트 | 7-2, 6-4, 5-4 | 회차 ID로 리포트와 카드별 답을 읽는다. 대화 카드별 반응에는 쓰고 평가한 카드의 요약만 보여주고(7-2의 `cardSummaries`), 쓰지 않았다고 답한 카드와 답하지 않은 카드는 `다루지 않은 카드 N장, 평가하지 않은 카드 N장`으로 장 수만 알린다. 고른 카드는 5-4에서, 답은 6-4에서 읽으며, 읽지 못한 쪽은 세지 않는다. 요약이 없을 때 `이번 만남에서 다룬 카드가 없어요.`는 고른 카드마다 쓰지 않았다고 답했거나 고른 카드가 없을 때만 쓰고, 답하지 않은 카드가 있거나 고른 카드를 모르면 `이번 리포트에는 카드별 요약이 없어요.`를 쓴다. 평가 화면의 카드 질문은 넘어가도 되므로 답하지 않은 카드는 썼을 수 있다(2026-11-10 E2E). 면회 사진은 서버 주소로 열고, 사진 없이 한 면회는 사진 자리를 두지 않는다 |
| 리포트 기록 | 7-1 | 최근 면회부터 보여주고 회차 ID로 연다. 면회 사진은 `photo.imageUrl`로 썸네일을 열고, 사진이 없거나 열지 못하면 사진 자리 아이콘을 둔다. 7-1은 사진 주소를 만들지 못한 항목도 `photo: null`로 주므로 올리기 실패라고 알리지 않는다(PR #145) |
| 변경 사항 확인 | 7-3, 7-4 | 리포트의 `변경 사항 확인하기`는 확인 전(`pending`) 제안이 남았을 때만 둔다. 홈 알림과 리포트 기록 어디서 들어와도 같다. 제안을 읽지 못했으면 버튼을 두어 변경 사항 화면에서 다시 시도하게 한다. 서버의 제안을 보여주고 반영 결과를 보낸 뒤 알림을 지운다. 이야기를 하나라도 승인했으면 일대기 목록을 다시 읽게 한다. 보내지 못하면 이유를 알리고 그 화면에 남는다. 운영 BE(#277, 11/9 14:42 KST 승인 배포)는 카드를 만드는 중에 주제 결정을 승인한 확인을 409 `CARD_GENERATION_IN_PROGRESS`로 거절하고 아무것도 저장하지 않는데, `reportFailureMessage`가 이 코드를 따로 다루지 않아 `처리하지 못했어요. 잠시 뒤 다시 시도해주세요.`를 보여준다. 같은 배포의 #282로 승인한 이야기를 더해 이야기가 300개를 넘을 때의 409 `LIFE_FACT_LIMIT_EXCEEDED`와 고친 내용이 5,000자를 넘을 때의 422 `INVALID_REQUEST`(새 버전 확인도 부름)도 같은 문구다. 이야기 수정 화면은 내용 글자 수를 막지 않는다 |

면회 흐름은 음성을 보낸(6-2) 뒤 `reportNoticeProvider.notifier.startGenerating(analysisId: ...)`를 부른다. 작업 ID를 넘기지 않으면 가장 최근 회차(5-4)에서 찾는다. 서버에 닿지 못하면 알림을 지어내지 않고, 만드는 중이었으면 잠시 뒤 다시 묻는다.

남은 제한

- 서버가 리포트 확인 여부를 저장하지 않는다(`api-spec.md` 미정 사항 2). 도착 알림은 변경 사항 확인을 마치면 지운다. 확인할 제안이 없는 리포트는 확인을 마칠 버튼이 없으므로, 리포트(7-2)와 제안(7-3)을 모두 읽으면 지운다. 어느 하나라도 읽지 못했으면 지우지 않는다. 지난 리포트를 열어도 다른 리포트의 도착 알림은 지우지 않는다. 확인한 리포트는 이번 실행에서만 다시 띄우지 않으므로, 앱을 다시 켜면 같은 리포트가 다시 도착으로 뜬다. 그 리포트를 다시 열면 다시 지워진다. 서버 저장은 #236에서 한다.
- 리포트를 만들지 못했으면 실패 알림을 눌러 분석을 다시 요청한다(6-5, #213, 아래 [분석 실패 후 다시 요청하기](#분석-실패-후-다시-요청하기)). 이 기기에 녹음이 남았으면 그 자리에서 녹음 파일을 공유할 수도 있다. 자동으로 다시 요청하지는 않는다.
- 홈은 어르신마다 서버에 한 번만 묻는다. 다만 이번 실행에서 녹음을 시작해 회차를 만들면 서버에 다시 묻지 않고 그 회차의 `평가 이어서 하기`로 바꾸므로, 앱을 켠 채로 녹음 화면을 떠나 홈으로 돌아와도 배너가 뜬다(#244, 아래 [면회 녹음](#면회-녹음)).
- 쓰지 않은 카드와 답하지 않은 카드는 제목을 받을 API가 없어 장 수로만 보여준다. 제목까지 보여주는 것은 BE 조회 응답과 함께 출시 뒤 후속 개발로 남겼다(PM 결정). 고른 카드는 최근 100회차 안에서만 찾는다.
- 면회 사진 주소가 만료되면 리포트는 `사진을 열지 못했어요`를, 리포트 기록은 사진 자리 아이콘을 보여주며, 다시 받아오지 않는다.

### 등록한 어르신이 없을 때

가입 직후에는 정보를 묻지 않고 홈부터 보여주므로, 새 계정은 첫 분을 등록하기 전까지 이 상태다. 보호자가 마지막 분을 지운 때도 같다. 프로필 삭제는 계정 탈퇴가 아니므로 계정 설정과 로그아웃은 그대로 쓴다. 로그인한 계정은 서버 목록(2-1)이 비었을 때 이 상태다. 입력하다 멈춘 분(`입력 중`)은 등록한 분으로 치지 않는다.

| 자리 | 동작 |
| --- | --- |
| 홈 상단 | 알약 자리에 `＋ 프로필 등록`. 누르면 `/profiles` |
| 홈 안내 | `오늘은 무슨 주제로 대화를 나눠볼까요?` |
| 오늘의 대화카드 받기 | 안내창 없이 기본 정보 입력(`/profile/create?adding=<id>`)을 바로 연다. 입력하다 나간 분(`입력 중`)이 있으면 그 입력을 가 본 가장 먼 단계부터 이어서 연다. 앱을 다시 켠 뒤에는 단말 초안으로 이어 간다(위 "등록하다 멈춘 세부 정보"). 빈자리가 없으면 `/profiles`로 간다([setup_entry.dart](lib/features/profile_setup/setup_entry.dart)) |
| 알림, 일대기, 리포트 | `어르신을 먼저 등록해주세요` 창. `등록하러 가기`는 `/profiles`, `닫기`는 그 자리에 남는다 |
| 프로필 설정 | 어르신 항목 대신 `함께하는 소중한 분을 등록하면 정보를 볼 수 있어요.`와 `등록하러 가기`를 보인다 |
| 설정 | 어르신이 없어도 알림 설정, 도움말, 계정 약관 동의, 로그아웃, 회원탈퇴가 모두 보인다 |
| `/profiles` | 빈 슬롯 3개. 지우기 버튼은 감춘다 |
| 대화 카드, 면회, 리포트, 알림, 일대기 경로 | 주소로 바로 들어오면 화면 대신 등록 안내를 보여준다(`router.dart`의 `_NeedsProfile`) |

### 가입 직후 홈 먼저 보여주기

앱을 둘러보기도 전에 정보를 입력하게 하면 그만둘 수 있어 가입 뒤 순서를 바꿨다(2026-11-08 FE 작업자 제안, PM 확인 전, [PM 기록](../docs/pm/README.md#검토-중인-제품-결정)).

1. 구글 로그인 뒤 보호자 이름과 약관 동의(`/consent`)
2. 처음 오셨네요(`/onboarding`)와 새록 소개 창
3. 홈. 등록한 분이 없어 이름 없이 묻는다
4. `오늘의 대화카드 받기`를 누르면 기본 정보 입력, 세부 정보 네 항목, 사진 올리기
5. `마치기`로 홈에 돌아온다. 카드는 지금처럼 `마치기`의 4-1 요청과 홈 버튼(`prepare`)으로 만든다. 홈에 돌아오는 것만으로 생성 상태를 따로 시작하지 않는다

새록 소개([onboarding_tutorial.dart](lib/features/profile_setup/onboarding_tutorial.dart))는 다섯 장이다. 새록 소개, 알려주신 이야기로 대화 카드를 만든다, 이야기가 쌓이면 일대기 앨범이 된다, 입력한 정보는 동의한 범위 안에서 쓰고 언제든 고치거나 지울 수 있다, 준비가 되면 `대화카드 받기`를 누르면 정보를 묻는다. 의료 효과나 기억 회복처럼 들리는 말은 쓰지 않는다. 개인정보 장의 문구는 [법률 문서](../docs/legal/README.md#현재-확정된-데이터-원칙)의 확정 원칙 안에서만 썼고 법률 검토 문구로 확정한 것은 아니다. `다음`, `이전`과 옆으로 밀기로 넘기고, 화면 읽기는 `5장 중 2장`처럼 읽는다. 첫 장부터 넷째 장까지 오른쪽 위 `건너뛰기`로 닫으면 처음 오셨네요에 남는다. 마지막 장의 `시작하기`는 홈으로 간다. 마지막 장에는 `새록 소개는 설정의 도움말에서 언제든 다시 볼 수 있어요.`를 작은 회색 글로 붙이고, 건너뛰어 남은 처음 오셨네요 아래에도 같은 글을 둔다. 설정의 `도움말`에서 다시 볼 때는 이 글을 빼고 마지막 장의 버튼을 `닫기`로 둔다. 바깥을 눌러서는 닫히지 않는다. 글자를 키우면 창 전체가 스크롤된다(360dp와 412dp, 글자 1.0·1.3·2.0배 위젯 테스트). 처음 오셨네요는 새 계정에서만 지나므로 본 적이 있는지 단말에 저장하지 않는다.

### 확인이 필요한 것

- BE: 최대 3분 허용(2-2의 `PROFILE_LIMIT_EXCEEDED`), 프로필 삭제(2-8), 2-1 목록 응답의 이름과 성별은 PR #104로 명세에 들어갔다. 앱은 2-1 목록과 2-8 삭제를 [profile_api.dart](lib/data/profile_api.dart)로 붙였다. 목록은 [providers.dart](lib/data/providers.dart)의 `careProfilesProvider`가 읽고, 삭제는 프로필 전환 화면([profile_switch_screen.dart](lib/features/profile/profile_switch_screen.dart))에서 부른다. 3분 초과 거절은 `어르신은 세 분까지 등록할 수 있어요.`로 알린다. 푸시 알림의 `profileId`는 합의 전이다.
- BE: 입력 중인 분만 있을 때 로그인 직후 어디로 갈지는 정하지 않았다(`api-spec.md` 미정 사항 9).
- BE, PM: 마지막으로 고른 어르신의 서버 프로필 ID, 보호자가 적은 관계, 등록하다 멈춘 세부 정보 초안(답의 글, 단계, 올린 사진 수)을 단말에 두는 것은 테스트 가정이다. 단말 보관 범위를 정할 때 함께 확인한다(`docs/legal/README.md`의 실제 사용자 자료 사용 전 확인).
- PM: 화면 문구는 FE 초안이다. 다른 어르신의 리포트가 도착했을 때 알리는 방식도 정하지 않았다.

## 구글 로그인

서버 계약은 [`backend/README.md`](../backend/README.md)의 "로그인 API"를, 근거는 ADR-007을 따른다.
동의 문구는 `docs/legal/consent-draft.md`에서 옮긴 `consent_terms.dart`를 쓰고 화면에서 새로 쓰지 않는다.

### 흐름

    A-1 스플래시의 구글 버튼 (로그인이 필요할 때 로고 아래에 뜬다)
    → google_sign_in 으로 ID 토큰을 받는다 (사용자가 취소하면 아무것도 하지 않는다)
    → POST /auth/google
        → status=authenticated   → 세션을 받고 /home
        → status=consentRequired → /consent → POST /auth/consent → /onboarding

    앱을 다시 켤 때 (A-1 스플래시)
    → 보관한 세션 읽기 (없으면 같은 화면에 구글 버튼)
    → 만료 전이면 GET /auth/me 로 확인
        → 200                → /home
        → 401, 403           → 아래 무음 로그인
        → 그 밖의 오류, 연결 실패 → 확인만 못 한 것이므로 세션을 두고 /home
    → 만료됐거나 서버가 거절하면 google_sign_in 무음 로그인으로 새 ID 토큰
    → POST /auth/google
        → status=authenticated   → 새 세션을 보관하고 /home
        → status=consentRequired → 계정이 사라진 경우다. 세션을 버리고 구글 버튼

따로 있던 로그인 화면(A-2)은 스플래시에 합쳤다. 로그인 버튼과 실패 안내는 `GoogleSignInPanel`이고, 스플래시가 복원 확인을 마친 뒤 로고 아래에 띄운다. 로그아웃, 탈퇴, 세션이 풀린 경우는 `/splash?signedOut=true`(`AppRoutes.signIn`)로 돌아가 2초 로고 없이 바로 버튼을 띄운다. 구글 로그인만 있다. 아이디와 비밀번호는 받지 않고 별도 회원가입 화면도 두지 않는다(ADR-007).
구글 인증만으로는 계정이 만들어지지 않는다. `/consent`에서 필수 동의를 제출해야
계정과 동의 이력이 함께 만들어지고, 중간에 나가면 계정이 남지 않는다.

어떤 항목이 필수인지는 서버가 준 `requiredConsents`로 판단한다. 앱 상수로 따로 판단하면
서버의 거절 기준과 어긋날 수 있어 한곳을 본다. 문구는 아직 `consent_terms.dart`에 있다.

앱이 보여주는 약관 버전(`consentVersion`)이 서버가 제시한 것과 다르거나, 서버가 앱에 문구가
없는 항목을 필수로 요구하면 동의를 받지 않는다. 보여주지 않은 문구에 동의를 받는 셈이기 때문이다.

### 세션 보관

세션은 `flutter_secure_storage`에 둔다(안드로이드는 키스토어로 감싼 AES-GCM, iOS는 키체인).
평문 `SharedPreferences`에 두지 않는다. 보관하는 값은 접근 토큰, 만료 시각과 계정이며
구글 ID 토큰과 등록 토큰은 그때만 쓰고 보관하지 않는다.

서버는 리프레시 토큰을 두지 않으므로, 갱신은 앱이 구글 무음 로그인으로 새 ID 토큰을 받아
`POST /auth/google`을 다시 부르는 방식이다(`backend/README.md`의 "세션").

서버에 닿지 못했을 때는 만료 전 세션을 버리지 않는다. 확인하지 못했을 뿐 만료된 것은
아니어서, 여기서 로그인 버튼으로 보내면 오프라인에서 앱을 열 수 없다.

### 로그아웃과 탈퇴

    설정의 로그아웃
    → 단말 세션 삭제 → POST /auth/logout → 구글 쪽 로그아웃 → /splash?signedOut=true

    설정의 회원탈퇴 → /profile/delete 의 탈퇴하기
    → DELETE /auth/me
        → 204                         → 단말 세션 삭제 → 구글 쪽 로그아웃 → /splash?signedOut=true, "탈퇴가 완료됐어요."
        → 401, 404 (세션 풀림, 계정 없음) → 이유를 알리고 "로그인으로 돌아가기"
                                         → 단말 세션 삭제 → 어르신 목록 비움 → /splash?signedOut=true
        → 그 밖의 오류, 연결 실패        → 이 화면에 남아 이유를 알린다. 세션을 지우지 않는다

로그아웃은 `SessionNotifier.signOut()`이다. 단말 세션을 먼저 지우고 서버에 폐기를 알린다.
서버에 닿지 못해도 로그아웃은 된다. 오프라인에서도 로그아웃은 되어야 하고, 단말에서 지운
세션은 다시 쓰일 일이 없다. 서버가 받지 못한 세션은 만료(기본 1시간)까지 서버에서만 유효하다.

탈퇴는 `SessionNotifier.deleteAccount()`다. 로그아웃과 순서가 반대로, 서버가 `204`로 답한
뒤에만 단말 세션을 지운다. 실패했는데 로그아웃된 것처럼 보이면 사용자는 탈퇴됐다고 믿게
된다. 세션 없이 이 화면에 온 경우는 지울 계정을 가리킬 세션이
없으므로 서버를 부르지 않고 로그인 정보가 없다고 알린다.

"로그인으로 돌아가기"도 로그아웃처럼 단말의 어르신 목록, 고른 분과 입력 중이던 값을
비운다(`forgetCareProfiles`). 남겨 두면 다른 계정으로 로그인했을 때 앞 계정의 어르신이
보인다. 리포트 알림은 계정마다 따로 두므로 로그아웃과 같이 지우지 않는다.

탈퇴 이유 설문은 화면에서만 쓰고 서버로 보내지 않는다. 서버가 탈퇴를 확인하면 그 계정의
면회 녹음과 재전송 기록, 어느 계정 것인지 모르는 녹음 파일을 지운다([면회 녹음](#면회-녹음),
PR #117 리뷰). 녹음 파일 공유로 앱 캐시에 남은 사본도 지운다([녹음 파일 공유](#녹음-파일-공유)). 그 밖의 단말 자료의 삭제 범위는 정해지지 않았다(`docs/legal/README.md`의
"열린 쟁점"). `/profile/delete`의 "활동 정보와 개인 정보가 삭제돼요" 문구는 아직 서버의
실제 삭제 범위(계정과 동의 이력)보다 넓다. 범위가 정해지면 문구나 삭제 범위를 맞춘다.

### 설정

클라이언트 ID와 서버 주소는 저장소에 적지 않고 빌드할 때 넘긴다.

    flutter run --dart-define=SAEROK_GOOGLE_SERVER_CLIENT_ID=<웹 클라이언트 ID> --dart-define=SAEROK_API_BASE_URL=http://10.0.2.2:8000

| `--dart-define` | 기본값 | 설명 |
| --- | --- | --- |
| `SAEROK_GOOGLE_SERVER_CLIENT_ID` | 없음 | `google_sign_in`의 `serverClientId`. 비면 구글 창을 띄우기 전에 설정 오류로 막는다 |
| `SAEROK_API_BASE_URL` | `http://10.0.2.2:8000` | 에뮬레이터에서 호스트를 가리키는 주소. 실기기는 PC의 LAN 주소를 넘긴다 |

`serverClientId`가 ID 토큰의 `aud`가 되므로 서버의 `SAEROK_GOOGLE_CLIENT_IDS`와 같아야 한다.
Google Cloud Console에 Application ID `app.saerok.android`와 디버그, 릴리스 SHA-1 등록이 선행되어야 한다.

개발 서버가 http라서 평문 통신을 디버그 빌드에서만 열어 두었다
(`android/app/src/debug/AndroidManifest.xml`). 릴리스 빌드에는 들어가지 않는다.

#### 릴리스 설정 검사

기본 서버 주소가 에뮬레이터용 http라서, 값을 넘기지 않은 릴리스 빌드는 모든 요청이 연결 오류로만 보인다. 이를 막으려고 릴리스 빌드(`kReleaseMode`)는 앱을 켤 때 [release_config.dart](lib/app/release_config.dart)의 `releaseConfigProblems`로 아래를 확인한다.

| 확인 | 막는 값 |
| --- | --- |
| `SAEROK_API_BASE_URL` | 비어 있음(`비어 있어요`), scheme이 https가 아님(`https 주소가 아니에요`), https이지만 형식 오류(`형식이 올바르지 않아요`: 앞뒤 공백, 해석 불가, host 없음, `user@` 사용자 정보, query `?`, fragment `#`) |
| `SAEROK_GOOGLE_SERVER_CLIENT_ID` | 비어 있음 |

서버 주소는 세 문제 중 하나만 알린다. 하나라도 걸리면 `main.dart`의 `rootApp`이 `SaerokApp` 대신 `ReleaseConfigErrorApp`을 고른다. 라우터, 세션 복원과 서버 요청을 시작하지 않고, 화면에는 고칠 설정 이름만 적는다. 넘긴 주소와 ID 값은 화면과 로그에 남기지 않는다. 다시 빌드해야 고쳐지므로 다시 시도 버튼은 없다. 디버그와 프로필 빌드는 검사하지 않아 기존 동작 그대로다. 확인 내용은 `test/release_config_test.dart`에 있다. 이 테스트는 dart-define 없이 실행한 기본값(`http://10.0.2.2:8000`, 빈 클라이언트 ID)을 릴리스로 검사했을 때 두 설정이 모두 막히는지와 `rootApp(isRelease: true)`가 설정 오류 앱을 고르는지도 본다. 실제 `flutter build appbundle --release` 결과물에서 이 화면이 뜨는지는 실행하지 않았다.

### 확인이 필요한 것

- **`Account` 계약** — 서버 응답에는 `loginId`가 없고 `email`이 `null`일 수 있어
  `lib/data/models.dart`의 `Account`와 형태가 다르다. 없는 값을 지어내지 않으려고
  `AuthAccount`를 따로 두었고, 계약이 합쳐지면 하나로 줄인다. PR #50 리뷰는 분리를
  유지해도 된다고 보았으며, 계정 식별 방식과 이메일이 없을 때의 기준을 BE와 맞추는 일이 남았다.
- **약관의 서버 관리** — 필수 여부는 서버 목록을 따르도록 고쳤으나 문구는 아직
  `consent_terms.dart`에 있다. 문구만 바뀌어도 앱 업데이트가 필요하고, 약관 버전이 다르면
  가입을 막는다. 서버가 약관 본문을 내려주는 방법이 정해져야 고칠 수 있다(PR #50 리뷰).
- **사용 중 세션 만료** — 세션은 1시간이면 만료된다. 공개 API(`ApiClient`)는 세션이 1분 안에
  만료되면 보내기 전에, 그래도 401을 받으면 그 자리에서 구글 무음 로그인 → `POST /auth/google`로
  새 세션을 받아 같은 요청을 한 번만 다시 보낸다(`session_refresher.dart`). 여러 요청이 함께
  401을 받아도 재인증은 한 번이다. 파일 업로드는 파일을 새로 만들어 다시 올린다. 무음 로그인이나
  서버가 거절하면 세션을 지우고 로그인 화면으로, 계정이 사라졌으면(`consentRequired`) 동의
  화면으로 보낸다(`main.dart`). 서버에 닿지 못했거나 서버가 `retryable: true`로 거절했으면(예: 503 `IDENTITY_PROVIDER_UNAVAILABLE`) 일시 장애로 보고 세션을 지우지 않으며 로그인 화면으로 보내지 않는다. 이때 401을 받은 원래 요청은 연결 실패(`ApiNetworkFailure`) 또는 다시 시도할 수 있는 서버 실패로 돌려줘, 음성 입력과 면회 사진처럼 다시 보낼 자료를 지우지 않는다. 요청을 시작한 뒤 다시 받기를 기다리는 동안 로그아웃했거나 다른 계정으로 로그인했으면 원래 요청을 보내지 않고 멈춘다(`ApiClient.continues`). 다시 받는 동안 로그아웃했으면 늦게 온 결과를 버리고, 계정 선택 창에서 원래와 다른 계정을 골랐으면 그 계정으로 바꾸지 않고 로그인 화면으로 보낸다. 두 경우 모두 원래 요청은 다시 보내지 않는다. 요청을 보낸 뒤 로그아웃했거나 다른 계정으로 로그인한 상태에서 그 요청의 401이 늦게 오면 재인증하지 않고 다시 보내지도 않는다. 401을 준 요청에 실었던 세션을 기억해, 같은 계정이 그 사이 새로 받은 세션일 때만 새 세션으로 다시 보낸다(`retryAfterUnauthorized`). 로그아웃과 탈퇴 같은
  `AuthApi` 요청은 여기에 해당하지 않아, 만료 뒤 탈퇴하기를 누르면 "로그인이 풀렸어요"를 띄우고
  로그인부터 다시 하게 한다. 실기기(SM-T875N)에서 세션을 2분으로 줄여 확인했다. 만료 뒤
  요청에서 `/auth/google`로 새 세션을 받고 원래 요청이 이어졌다. 기기에 새록에 로그인한 구글
  계정이 둘 이상이면 재인증 때 구글의 계정 선택 창이 한 번 뜬다. 면회를 녹음하는 동안(녹음 파일이 열려 있는 동안, 잠시 멈춤 포함) 재인증을 취소했거나 다른 계정을 골랐거나 계정이 사라졌으면 세션을 지우지 않고 녹음을 이어 간다. 세션을 지우면 어르신 목록이 비면서 녹음 화면이 닫히고 녹음이 멈추기 때문이다. 그동안은 계정 선택 창을 다시 띄우지 않고 요청은 401로 실패한다. 만남을 끝내거나 녹음 화면을 떠나 파일을 닫고 기기 기록(`pending-uploads.json`)을 남긴 뒤에 세션을 지우고 로그인 화면이나 동의 화면으로 보낸다(2026-11-10 E2E, `sessionHoldProvider`). 같은 계정으로 다시 로그인하면 홈의 이어 하기로 그 녹음을 보낼 수 있다. 11/10 운영 세션 수명을 30일로 늘렸지만 이 보호는 둔다.

## 면회 사진

`/visit/photo`(D-1)의 셔터를 누르면 `image_picker`로 기기의 카메라 앱을 연다. 카메라는 [visit_camera.dart](lib/features/visit/visit_camera.dart)의 `VisitCamera` 뒤에 두어 테스트에서 실제 카메라 대신 정해진 결과를 돌려주는 가짜로 바꿔 끼운다.

- 찍은 사진은 먼저 갤러리의 `새록` 앨범에 원본으로 남긴다([보관](#보관)). 다시 찍어 밀려난 사진도 갤러리에 남는다.
- 찍은 사진은 화면에 보여주고 `visitPhotoProvider`에 앱 사본의 기기 안 경로로 들고 있다. 경로는 앱이 켜져 있는 동안만 기억한다. 카드 화면에서 `대화 시작하기`를 눌러 새 회차를 시작하거나 로그아웃하면 경로를 비운다.
- 다시 찍으면 앞 사진의 앱 사본을 [보관](#보관) 기준에 따라 정리한다. 다시 찍다가 그만두면 앞 사진을 그대로 둔다.
- 갤러리에 저장하지 못하면 `사진을 갤러리에 저장하지 못했어요. 리포트에는 그대로 담아요.`를 보여주고, 그 사진으로 면회를 이어 간다.
- 5-2의 크기 상한(기본 20MB) 안에 들도록 긴 변 2048px, JPEG 화질 85로 줄여 받는다.
- 카메라가 열려 있는 동안에는 셔터와 시작 버튼을 막는다. 카메라를 열지 못하면 `카메라를 열지 못했어요. 사진 없이 시작해도 괜찮아요.`를 보여주고 사진 없이 시작할 수 있다.
- 찍은 사진을 앱 폴더로 옮기지 못하면 `사진을 저장하지 못했어요. 다시 찍거나 사진 없이 시작해도 괜찮아요.`를 보여준다.
- 카메라가 열린 사이 사진 화면을 떠났으면 찍은 사진을 갤러리에만 남기고 이번 면회에는 쓰지 않는다.
- 안드로이드는 시스템 카메라 앱에 촬영을 맡기므로 카메라 권한을 받지 않는다. 매니페스트에 `CAMERA` 권한을 넣으면 실행 중 권한 요청이 필요해지므로 넣지 않는다. 갤러리 저장은 안드로이드 11 이상에서 권한 없이 하고, 10 이하에서만 저장할 때 `WRITE_EXTERNAL_STORAGE`(`maxSdkVersion` 29)를 묻는다. 안드로이드 10은 앨범 폴더에 저장하려면 이전 저장소 방식이 필요해 `<application>`에 `requestLegacyExternalStorage`를 켰다. 이 값은 11 이상에서 무시된다([gal 2.3.3 안내](https://pub.dev/packages/gal/versions/2.3.3#android-setup)). 저장소에 iOS 프로젝트가 없어 `Info.plist`의 카메라 사용 문구(`NSCameraUsageDescription`)와 사진 추가 문구(`NSPhotoLibraryAddUsageDescription`)는 iOS를 추가할 때 넣어야 한다.

### 올리기

녹음을 처음 시작해 회차(5-1)가 만들어지면 찍어 둔 사진을 5-2로 올린다([visit_controller.dart](lib/features/visit/visit_controller.dart)의 `VisitState.photoUpload`). 녹음은 사진을 기다리지 않는다. 회차를 만들지 못하면 사진도 올리지 않는다.

- 올리면 갤러리에 원본이 있는 앱 사본은 지운다. 갤러리에 남기지 못한 사진은 사본을 남기고 올린 회차 ID만 적는다.
- 연결 실패와 서버가 `retryable: true`로 알린 실패만 자동으로 한 번 더 올린다. 그래도 안 되면 녹음 화면 아래 알림 띠에 `사진을 올리지 못했어요.` 줄을 바꿔 `녹음은 그대로 이어져요.`와 `사진 다시 올리기`를 닫을 때까지 둔다. 누르면 한 번 올린다.
- 형식 오류, 크기 초과, 평가가 끝난 회차처럼 다시 올려도 받지 않는 거절은 다시 올리지 않고 `사진을 올리지 못해 리포트에 사진 없이 담겨요.`를 잠시 보여준다.
- 올릴 사진 파일을 찾거나 읽지 못하면 다시 올리지 않고 `찍은 사진을 찾지 못해 리포트에 사진 없이 담겨요.` 줄을 바꿔 `녹음은 그대로 이어져요.`를 잠시 보여준다.
- 회차를 만든 뒤 사진 화면으로 돌아가 다시 찍으면 새 사진을 올린다. 5-2는 다시 올리면 앞 사진을 바꿔 끼운다. 올리기는 차례로 해서, 앞 사진 요청이 끝난 뒤 새 사진을 보낸다. 앞 사진의 결과는 화면 안내에 쓰지 않고, 올리는 중이던 앞 사진은 끝날 때까지 지우지 않는다. 앞 사진의 사본은 올리기가 끝난 뒤 [보관](#보관) 기준에 따라 정리한다.
- 녹음 화면은 아래 카드 자리 때문에 안내를 둘 높이가 남지 않아 본문 대신 알림 띠로 알린다. 녹음 전 안내부터 지켜보므로 녹음 화면이 뜨기 전에 끝난 실패도 알린다. 만남을 끝내거나 화면을 떠나면 알림 띠를 닫는다.
- 다시 올리기는 녹음 화면에서만 할 수 있다. 소감을 저장하면(6-1) 서버가 사진을 받지 않는다.

리포트 상세의 사진은 서버가 7-2 응답의 `photo.imageUrl`로 내려준다(PR #115). 리포트 기록도 7-1 응답의 같은 모양의 `photo`로 썸네일을 보여준다(PR #145).

### 보관

사진 원본은 보호자의 것으로 보고 갤러리에 남기고, 앱은 서버에 올리는 데 쓰는 사본만 관리한다(PR #136 리뷰). 코드는 [visit_gallery.dart](lib/features/visit/visit_gallery.dart)의 `VisitGallery`와 [visit_photos.dart](lib/features/visit/visit_photos.dart)의 `VisitPhotos`다.

| 언제 | 갤러리 원본 | 앱 사본(갤러리에 남김) | 앱 사본(갤러리에 못 남김) |
|---|---|---|---|
| 서버에 올린 직후 | 남김 | 지움 | 남김 |
| 올리기 전에 다시 찍음 | 남김 | 지움 | 남김 |
| 다음 면회 시작 | 남김 | 지움(올리지 못하고 남은 것) | 남김 |
| 로그아웃 | 남김 | 남김 | 남김 |
| 탈퇴 | 남김 | 지움 | 지움 |
| 앱 삭제 | 남김 | 지워짐 | 지워짐 |

- 갤러리 원본은 `gal`로 `새록` 앨범에 넣는다. 앨범이 없으면 만든다. 앱은 갤러리의 사진을 고치거나 지우지 않는다.
- 갤러리에 남기지 못한 사진은 앱 사본이 하나뿐인 파일이라 탈퇴 전에는 지우지 않는다.
- 카메라 앱이 남긴 파일은 기기가 비울 수 있는 임시 폴더에 있으므로, 갤러리에 남긴 뒤 `getApplicationDocumentsDirectory()` 아래 `visit_photos/`로 옮기고 임시 파일은 지운다. 파일 이름에는 시각만 넣는다.
- 같은 폴더의 `visit-photos.json`에 찍은 계정 ID, 파일 이름, 올린 회차 ID(올리기 전에는 `null`), 갤러리에 남겼는지(`inGallery`)만 적는다. `inGallery`가 없는 앞 버전의 기록은 남기지 못한 것으로 보고 지우지 않는다. 기록은 한 번에 하나씩 고쳐 써서, 새 면회 정리와 촬영이 겹쳐도 서로 덮지 않는다.
- 탈퇴하면 그 계정의 사본과 기록, 기록이 없는 사진 파일을 지운다.
- 사진 폴더는 녹음 폴더와 함께 자동 백업과 기기 간 이전에서 뺐다(`res/xml/data_extraction_rules.xml`, `res/xml/backup_rules.xml`).

아직 없는 것:

- 올리지 못한 사진은 갤러리에 남지만, 앱을 다시 켜면 그 사진을 다시 올리는 기능은 없다.
- 탈퇴하면 서버는 사진 행을 지우고 S3 원본의 객체 키를 삭제 대기열에 넣는다. 대기열을 처리하는 삭제 실행기(#204)는 11/5 배포부터 운영 이미지에 있지만, 저장소 밖 팀 운영 기록에 따르면 실제 삭제는 11/6 PM 결정으로 보류했고 예약 실행 기록도 없다. 그래서 운영에서 올린 사본이 실제로 지워졌는지는 확인하지 않았다([저장소 대조 안내](../backend/docs/storage-audit.md)). 같은 기록에 따르면 운영 사진 버킷은 버전 관리 중이며, 삭제 실행기는 버전 관리 이력이 있는 버킷의 객체를 지우지 않고 `VERSIONED_BUCKET_REQUIRES_REVIEW`로 남기므로(`backend/app/services/storage_deletion.py`) 처리 방식은 정하지 않았다.
- 사진을 올리는 중에 소감까지 빠르게 저장하면 서버가 평가가 끝난 회차라며 거절할 수 있다. 이때는 사진 없이 리포트가 만들어진다.
- 카메라 앱이 열린 동안 안드로이드가 메모리 부족으로 새록을 종료하면 찍은 사진을 되찾지 않는다(`retrieveLostData` 미사용). 다시 찍어야 한다.
- 실제 사용자 사진을 서버에 보관하기 전에 사진 보관 동의 확인이 필요하다(`api-spec.md` 미정 3). 사진 보관 동의는 아직 구현하지 않았다. 가입과 설정에서 받는 AI 사진 분석 동의(`photoAnalysis`, #257)는 분석 여부만 정하며 보관 동의를 대신하지 않는다.

## 면회 녹음

E-2 녹음 화면에서 실제로 마이크를 열고 기기에 파일을 남긴다. 이 파일은 소감 화면의
`리포트 만들기`에서 6-2로 서버에 보내 STT를 거친다([현재 사용자 흐름](#현재-사용자-흐름)). 코드는 [`visit_recorder.dart`](lib/features/visit/visit_recorder.dart)에
모여 있고, 화면과 [`VisitController`](lib/features/visit/visit_controller.dart)는
`VisitRecorder` 인터페이스만 본다. 테스트는 `visitRecorderProvider`를 override 한다.

E-1 녹음 안내에서는 회차마다 피보호자 동의를 확인하지 않는다. `[필수] 어르신께 녹음한다는 것을 알려드렸고 동의를 확인했어요` 체크는 팀 회의 결정으로 뺐고(2026-10-13 확인), 녹음과 음성 처리 동의는 가입 때 보호자의 필수 동의로 받는다(`docs/architecture/data-contracts.md`). 피보호자 본인의 동의와 대리 권한은 녹음 때가 아니라 피보호자 최초 정보 입력 전에 확인한다([ADR-001 녹음 동의 확인 시점](../docs/architecture/decisions/ADR-001-consent-and-temporary-processing.md#녹음-동의-확인-시점), PR #119). 이 확인의 방법, 기록과 화면 연결은 후속 설계이며 앱에는 아직 없다. 마이크 권한이나 녹음 버튼은 피보호자 동의를 대신하지 않는다.

E-1의 보관 안내(`recordingRetentionNotice`)는 두 줄이다. `녹음은 리포트와 다음 대화 준비에만 써요.` / `서버에서는 분석 후 지우고, 휴대폰에만 남겨요.` 서버 사본은 지우고 휴대폰에는 남는다고 나눠 말한다. 세 줄 문구(PR #223)가 길어 2026-11-06 디자인 리뉴얼에서 줄였고, PM 확인을 PR 본문에서 요청한다. 서버에 남는 전사문은 이 문구가 아니라 리포트와 동의 문서에서 다룬다. 서버 사본은 STT 직후 지우지만 기기 파일은 아래 [저장 위치](#저장-위치)의 녹음 보관 기준대로 남기므로, 예전 문구 "분석이 끝나면 바로 지워요"는 실제 동작과 달랐다. 첫 줄도 "리포트를 만드는 데만"에서 "리포트와 다음 대화 준비에만"으로 바꿨다. 전사문은 리포트와 함께 이야기 후보와 주제 조정 제안을 만들고, 보호자가 확인한 제안이 다음 카드에 들어가기 때문이다. 기기 파일을 언제 지우는지는 화면에서 약속하지 않는다. 가입 동의의 보유 기간 문구(`consent_terms.dart`)는 법률 문서와 동의 버전을 함께 바꿔야 해서 이 변경에 넣지 않았고 PM 확인이 남아 있다.

녹음을 처음 시작하면 마이크 권한 → 회차 만들기(API 5-1) → 파일 열기 순서로 간다. 권한을 먼저 보는 것은, 회차를 만든 뒤 권한을 거부하면 녹음 없는 회차가 남고 카드 묶음이 `inVisit`으로 묶이기 때문이다. 회차를 만들지 못하면 녹음을 시작하지 않고 `면회를 시작하지 못했어요`를 보여준다. 받은 `sessionId`는 `VisitState`에 앱이 켜져 있는 동안만 들고 있으며, 소감 저장과 녹음 제출이 쓴다. 면회 중 보충 카드는 5-3이 받아들인 뒤에 화면에 더하고, 실패하면 추가 화면에 남아 다시 누르게 한다. 회차가 생기면 서버에 다시 묻지 않고 카드 생성 상태를 `inVisit`으로, 홈 알림을 이 회차의 `평가 이어서 하기`로 바꾼다. 홈은 회차 상태(5-4)를 어르신마다 앱을 켠 뒤 한 번만 묻고 카드 화면은 녹음 화면 뒤에 그대로 남아 있어서, 끝내기를 누르지 않고 녹음 화면을 떠나면 카드 화면이 `대화 시작하기`를 다시 보여주고(누르면 5-1이 `CARD_SET_ALREADY_USED`로 거절) 홈에는 이어갈 배너가 없었기 때문이다(이슈 #234, PR #244).

`inVisit`을 이어서 할 때는 녹음 화면이 아니라 그 회차의 평가로 보낸다. 명세 4절 표는 `4-3 → 면회 화면`이지만, 녹음 화면을 떠날 때 파일을 닫아 같은 파일에 이어 녹음할 수 없고, 새로 녹음하면 회차마다 파일 하나를 받는 6-2에 앞 녹음이 빠진다. 이어 녹음(파일 잇기)은 녹음 형식과 함께 정할 일이라 넣지 않았다. 끝내기 창을 거치지 않아 참여자 수가 없는 녹음을 보내는 일은 #181(PR #206)이 맡는다.

### 저장 위치

`path_provider`의 `getApplicationDocumentsDirectory()` 아래 `visit_recordings/`다.
Android에서 이 값은 `context.getDir("flutter", MODE_PRIVATE)`이므로 실제 경로는
다음과 같다.

```
/data/user/0/app.saerok.android/app_flutter/visit_recordings/visit-2026-09-23T14-05-33-120.wav
```

- 앱 전용 내부 저장소다. 다른 앱과 갤러리, 파일 관리자에 보이지 않고 USB로도
  바로 꺼낼 수 없다. 앱을 지우면 함께 지워진다.
- 외부 저장소를 쓰지 않으므로 `READ/WRITE_EXTERNAL_STORAGE` 권한이 필요 없다.
- 파일 이름에는 시각만 넣는다. 어르신 이름이나 회차 정보처럼 사람을 알아볼 수
  있는 값은 파일 이름에 남기지 않는다.
- 확인은 `adb exec-out run-as app.saerok.android ls app_flutter/visit_recordings`로 한다.
  `run-as`는 디버그 빌드에서만 된다.

같은 폴더에 녹음의 기록 `pending-uploads.json`을 둔다
([pending_uploads.dart](lib/features/visit/pending_uploads.dart)). 앱을 다시 켠 뒤
`음성 다시 보내기`가 녹음 파일과 참여자 수를 회차 ID로 다시 찾기 위한 것이다.

- 담는 값은 녹음한 계정 ID, 회차 ID, 파일 이름, 참여자 수, 보냈는지(`uploaded`)뿐이다. 어르신 이름이나 대화 내용은 담지 않는다.
- 녹음을 끝내기 확인 창에서 마치거나 화면을 떠날 때 파일을 정상적으로 닫았으면 회차와 파일 연결을 적는다. 참여자 수를 확인하지 않았으면 `null`로 남긴다. 앱을 다시 켜도 파일을 찾을 수 있으며, 소감 제출 또는 녹음 다시 보내기에서 참여자 수를 확인한 뒤 보낸다. 확인을 취소하면 파일을 그대로 남긴다.
- 서버가 녹음을 받았거나(6-2 `202`) 이미 끝난 회차라고 거절하면 `uploaded: true`로만 바꾼다.
  다시 보낼 목록에서는 빠지지만 녹음 파일과 계정, 회차 연결은 남는다. 기록이 없던
  녹음이면 이때 새로 적는다.

녹음의 보관은 PR #117 리뷰에서 정한 대로 한다.

- 서버가 받은 뒤에도 지우지 않는다. 전사나 리포트가 성공하거나 실패해도 지우지 않는다.
  서버 처리에 문제가 생겼을 때 원본으로 되살리기 위해서다.
- 시간이 지났다고 지우지 않는다. 앱을 지우면 Android가 앱 전용 공간과 함께 지운다.
- 로그아웃해도 남긴다. 다른 계정으로 들어오면 그 녹음을 찾지도 보내지도 못한다
  (`pendingUploadsProvider`가 로그인한 계정의 기록만 본다).
- 탈퇴하면 그 계정의 녹음과 기록을 보냈는지와 관계없이 지운다. 기록이 없는 녹음 파일도 함께 지운다. 녹음을 끝내지
  못했거나 기록을 남기지 못한 파일이라 어느 계정 것인지 알 수 없고 다시 보낼 수도 없다.
- 녹음 폴더는 자동 백업과 기기 간 이전에서 뺐다. 지운 녹음이 다시 설치할 때 되살아나지 않게
  하려는 것이다. Android 12 이상은 `res/xml/data_extraction_rules.xml`, 11 이하는
  `res/xml/backup_rules.xml`을 쓴다. 두 파일을 함께 고친다.

기기에도 서버에도 녹음이 없는 회차(`audioPending`인데 기기 기록이 없음)는 다시 보내라고
하지 않는다. 소감 화면과 `음성 다시 보내기` 모두 `녹음이 없어 이 면회의 리포트는 만들 수
없어요.`와 홈으로 가기만 보여준다. 면회 기록과 소감은 그대로 둔다. 서버는 이 회차를 계속
`audioPending`으로 돌려주므로 홈 배너가 같은 회차를 반복해 띄운다. PR #115는 develop에
병합됐지만 이 반복을 막는 처리는 아직 없다([아직 없는 것](#아직-없는-것)).

### 녹음 파일 공유

리포트 화면 맨 아래의 `녹음 파일 공유`로 이 기기에 남은 그 회차의 WAV를 안드로이드 공유 창에 넘긴다(2026-11-09 PM 결정, #295. 새로 빌드한 APK에만 있고 설치된 앱에는 없다). 코드는 [recording_share.dart](lib/features/visit/recording_share.dart)다.

리포트를 만들지 못한 회차도 녹음이 남았으면 공유할 수 있다(2026-11-10 PM 결정. 새로 빌드한 APK에만 있고 설치된 앱에는 없다). 실패한 회차에는 리포트가 없어 리포트 화면의 버튼을 쓸 수 없으므로, 아래 두 자리에 같은 버튼을 둔다.

- 홈 배너와 알림 화면의 `리포트를 만들지 못했어요`를 누르면 아래에서 올라오는 시트로 `분석 다시 요청하기`와 `녹음 파일 공유` 중에 고른다([failed_report_sheet.dart](lib/features/home/failed_report_sheet.dart)). 공유를 고르면 시트를 닫고 공유 창을 열며 분석은 다시 요청하지 않는다. 녹음은 누를 때마다 다시 찾고, 없으면 시트 없이 바로 분석 다시 요청하기 화면을 연다. 찾는 동안이나 시트가 떠 있는 동안 알림을 한 번 더 눌러도 시트나 화면을 하나 더 열지 않고, 시트가 올라오는 동안과 그 뒤 0.3초는 시트의 버튼을 받지 않는다.
- 분석 다시 요청하기와 음성 다시 보내기 화면(`/visit/upload`)이 요청하지 못해 `다시 시도하기`를 보여줄 때도 녹음이 남았으면 그 아래에 `녹음 파일 공유`를 둔다.

- 파일은 회차 ID로 녹음 기록(`pending-uploads.json`)에서 찾는다. 서버에 보낸 녹음도 찾지만, 다른 계정의 녹음과 기록이 없는 녹음, 사라진 파일은 찾지 않는다. 찾지 못하거나 기록을 읽지 못하면 버튼 자리를 두지 않고 리포트는 그대로 보여준다.
- 안내 문구 없이 버튼만 둔다(2026-11-09 PM 결정). 보낼 곳은 보호자가 공유 창에서 고른다.
- 누른 사이 파일이 사라졌으면 `녹음 파일을 찾지 못했어요.`를 알리고 버튼을 거둔다. 공유 창을 열지 못하면 `녹음 파일을 공유하지 못했어요.`를 알린다.
- `share_plus`는 안드로이드에서 파일을 앱 캐시의 `share_plus/`에 복사한 뒤 받는 앱에 읽기 권한을 준다. 그 사본은 다음에 공유할 때 지워지고, 그 전에는 캐시를 비울 때 지워진다. 탈퇴하면 이 사본도 지운다(`RecordingShare.forgetCopies`가 `share_plus/` 폴더를 통째로 지운다). 로그아웃은 지우지 않는다. 캐시는 자동 백업에 들어가지 않는다.
- 공유 창과 기기 기록은 `recordingShareProvider`, `pendingUploadsProvider`로 바꿔 끼워 위젯 테스트에서 확인한다(`test/report_recording_share_test.dart`, 412dp, 글자 1.5배. 실패한 회차는 `test/failed_report_recording_share_test.dart`가 412dp에 글자 1.5배, 360dp에 글자 1.3배와 2배로 확인한다). 탈퇴 때 사본을 지우는지는 `test/google_login_test.dart`에서 확인한다. 실기기의 공유 창과 받는 앱에서 열리는지는 아직 확인하지 않았다.

### 분석 실패 후 다시 요청하기

홈과 알림의 실패 안내를 누른다. 이 기기에 그 회차의 녹음이 남아 있으면 시트에서 `분석 다시 요청하기`와 `녹음 파일 공유` 중에 고르고, 녹음이 없으면 바로 다시 요청한다(2026-11-10 PM 결정, [녹음 파일 공유](#녹음-파일-공유)). `분석 다시 요청하기`는 먼저 6-5로 저장된 전사의 재사용을 요청한다. 전사가 없다는 `RECORDING_REQUIRED` 응답일 때만 그 계정과 회차에 보관한 WAV를 6-2로 다시 보낸다. 파일이 없으면 복구할 수 없다고 안내하고 소감은 유지한다. 통신 오류나 동의 거절을 파일 재제출로 우회하지 않는다. 자동 반복 요청은 하지 않는다. 11/9 승인 배포(#285)부터 서버는 저장된 전사를 다시 쓰는 6-5를 회차당 기본 3회까지 받고, 넘으면 409 `REPORT_RETRY_LIMIT_EXCEEDED`로 거절한다. 6-2로 기기 녹음을 다시 보내는 것은 세지 않는다. 앱은 이 코드를 따로 다루지 않아 `분석을 요청하지 못했어요.`와 `다시 시도하기`를 보여 준다. 이 실패 안내에서도 녹음이 남았으면 `녹음 파일 공유`를 둔다.

기기 녹음은 재요청 후에도 남긴다. 6-2를 받았다는 표시가 있어도 분석 복구에서만 다시 찾을 수 있으며, 다른 계정의 파일은 찾지 않는다. [서버 복구 기준](../backend/docs/speech-recovery.md)을 함께 따른다.

기기 파일을 성공이나 경과 시간만으로 지우지 않는 것은 기존 동작이다. 이번에는 이미 전송한 파일을 복구할 때 다시 찾는 경로를 추가했다. 서버의 24시간 보관 기준을 기기 파일에 적용하지 않는다. 탈퇴 시 `forgetAccount`로 삭제를 시도하지만 파일 삭제 예외를 넘기며 영속 재시도는 없다. 보관 안내와 이 삭제 실패 처리는 [동의안의 로컬 수정안](../docs/legal/consent-draft.md#녹음과-임시-전사-보관-문구-수정안)에서 운영 적용 전 확인 항목으로 남긴다.

### 음성 형식

WAV / PCM 16비트 / 16kHz / 모노다. BE [PR #71](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/pull/71)과
AI [PR #66](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/pull/66)이 검사하는 형식과 같다.
두 PR은 develop에 병합됐고(10/1, 10/2), BE는 이 형식이 아닌 녹음을 받지 않는다(`backend/app/services/audio_validation.py`). PR #71의 ADR-008은 아직 `proposed`다. `app/CLAUDE.md`대로 형식은 AI 영역이 확정한다. 바뀌면
`visitRecordConfig`와 `VisitRecording.fileExtension`, 그리고
`test/visit_recording_test.dart`의 `음성 형식` 테스트를 함께 고친다.

1시간 녹음은 약 115MB다. PR #71의 서버 업로드 상한 기본값은 512MB다.

### 권한과 실패

`AndroidManifest.xml`에 `RECORD_AUDIO`를 넣었고, 사용자가 녹음을 시작할 때
`record`가 권한을 묻는다. 거부, 장치 열기 실패와 저장 실패는
`VisitState.problem`으로 구분해 화면에서 안내한다.

### 파일을 반드시 닫아야 하는 이유

WAV 헤더 44바이트는 녹음을 **끝낼 때** 파일 앞에 덮어 쓰인다
(`record_android`의 `WaveContainer.stop()`). 끝내지 않고 화면을 떠나거나 앱이
죽으면 그 자리가 0으로 남아, 소리는 들어 있는데 열 수 없는 파일이 된다.

- `만남 끝내기`뿐 아니라 **녹음 화면을 떠날 때도** 파일을 닫는다
  (`_RecordScreenState.dispose`가 `VisitController.stopRecordingOnLeave`를 부른다). 파일 닫기는 그 호출 안에서 바로 시작하고, 닫을 파일이 없을 때의 상태 변경만 다음 microtask로 미룬다. `dispose` 안에서 상태를 바로 바꾸면 디버그 빌드의 Riverpod이 build 중 provider 수정 오류를 던졌다.
- 닫은 뒤 파일이 정말 `RIFF`로 시작하는지 확인하고, 아니면 저장 실패로 알린다.
  경로가 있다고 성공이라 말하지 않는다.
- **개발 중 hot restart(`flutter run`의 `R`)는 이 과정을 건너뛴다.** 그때 남은
  파일은 재생되지 않으니 지우고 다시 녹음한다. 확인은 다음과 같이 한다.

  ```
  adb exec-out run-as app.saerok.android cat app_flutter/visit_recordings/<파일> | head -c 4
  ```

  `RIFF`가 나오면 정상이다.

### 만남 끝내기 확인 창

`만남 끝내기`를 누르면 바로 끝내지 않고
[`stop_recording_dialog.dart`](lib/features/visit/stop_recording_dialog.dart)의
확인 창을 띄운다.

- 창이 떠 있는 동안 **녹음과 시간을 잠시 멈춘다.** 창을 보는 사이의 침묵을
  대화로 남기지 않으려는 것이다. `이어서 녹음`을 고르면 같은 파일에 이어 쓴다.
  잠시 멈춤 상태에서 눌렀다면 멈춘 채로 돌아간다.
- 같은 자리에서 **참여자 수**를 받는다. 기본 2명이고 1~8명까지 고른다.
  물음은 `보호자님을 포함해 모두 몇 분인가요?`이고, 녹음을 다시 보내기 전에
  띄우는 창도 같다(2026-11-09 PM 결정, #295. 새로 빌드한 APK에만 있고 설치된 앱에는 없다).
  계약의 `VisitSession.participantCount`이며 STT 화자 분리 요청의
  `speakerCount`로 그대로 넘어간다.
- **앱이 목소리를 세어 짐작하지 않는다.** 보호자가 확인해 준 수만 쓴다. 창을
  거치지 않고 화면을 떠나면 값을 비워 둔다. 이 때문에 파일이 없다고 안내하지 않는다.
  전송 전에 같은 수 선택 화면으로 다시 묻고, 확인하지 않으면 전송하지 않는다.

### 화면 이탈 후 녹음 복원 검증

- `visit_recording_test.dart`: 끝내기 없이 화면을 떠나도 파일을 닫고 회차 연결을 남긴다. 파일 저장 자체가 실패하면 재전송 기록을 만들지 않는다. 녹음 전 안내나 녹음을 끝낸 뒤 화면을 떠나도 provider 수정 오류가 나지 않는지, 떠날 때 파일 닫기는 미루지 않고 상태 변경만 미루는지도 본다.
- `pending_uploads_test.dart`: 참여자 수가 없는 기록도 파일을 찾는다. 저장소를 다시 만들었을 때와 계정별 분리를 검사한다.
- `submission_test.dart`, `upload_retry_test.dart`: 참여자 수 확인 전에는 보내지 않고, 확인 후 같은 파일을 전송한다. 전송 실패 후에도 원본을 남긴다.
- `recording_recovery_screen_test.dart`: 412 x 917, 360 x 800 dp와 글자 배율 1.0, 2.0에서 확인, 취소와 전송 흐름을 검사한다.
- 모두 합성 파일과 API 대역을 쓴 로컬 테스트다. Android가 앱 프로세스를 강제로 종료하는 상황, 화면 잠금 중 녹음과 실제 서버 전송까지 검증한 것은 아니다. 저장 장치 오류로 기록 파일을 쓰지 못하면 재실행 후 복원은 보장하지 않는다.
- 그 뒤 11/7, 11/8 Galaxy S22에서 운영 서버로 강제 종료 뒤 녹음 복구를 확인했다([루트 README](../README.md#알려진-제한)). 녹음 중 화면 잠금은 실기기에서 확인하지 않았다.

### 녹음 중 화면 켜짐

면회 녹음은 휴대전화를 내려놓고 오래 이어지는 경우가 많다. 기기의 화면 자동 꺼짐 시간이 지나 화면이 꺼지지 않도록, 녹음하는 동안에는 Android 창의 `FLAG_KEEP_SCREEN_ON`을 켠다.

- 플러그인을 더하지 않았다. [MainActivity.kt](android/app/src/main/kotlin/app/saerok/android/MainActivity.kt)의 MethodChannel `app.saerok.android/screen_awake`(`setKeepScreenOn`, 인자 `on`)가 창 표시를 바꾼다. 창 표시만 바꾸므로 `WAKE_LOCK` 권한이 필요 없다.
- Dart 쪽은 [screen_awake.dart](lib/app/screen_awake.dart)에 있다. `ScreenAwakePlatform`이 채널을 감싸고, `ScreenAwake`가 켜 두기를 원하는 화면을 세어 하나라도 있으면 켜고 모두 놓으면 끈다. 화면은 `KeepScreenOn(enabled: 녹음 중)`으로 감싸기만 한다. 테스트는 `screenAwakePlatformProvider`를 대역으로 바꾼다.
- E-2에서는 `VisitState.recording`이 참인 동안만 켠다. `잠시 멈춤`, `만남 끝내기` 확인 창(창이 떠 있는 동안 녹음을 멈춘다), 녹음 끝내기와 녹음 실패에서는 끈다. `이어서 녹음`을 고르면 다시 켠다. 끝내기 없이 화면을 떠나면 `KeepScreenOn`이 빠지면서 끈다.
- 앱이 엔진에서 떨어지면(`AppLifecycleState.detached`) 녹음 중이어도 끄고, 다시 앞으로 오면 녹음 중일 때만 다시 켠다. `MainActivity`도 새 엔진을 붙일 때와 엔진을 정리할 때 표시를 지운다. 창이 사라지면 표시도 함께 사라진다.
- 채널이 없거나 창을 바꾸지 못해도 녹음은 막지 않는다. 창이 요청을 거절하면(`PlatformException`) 그 값을 보낸 적 없는 것으로 되돌리고, 다음 잡기나 앱이 다시 앞으로 올 때(`resumed`) 같은 값을 다시 보낸다. 그 사이에는 기기 설정대로 화면이 꺼질 수 있다.

한계는 다음과 같다.

- **화면이 켜져 있게만 한다. 앱이 백그라운드로 내려간 뒤의 녹음 지속은 이번 범위가 아니다.** 보호자가 전원 버튼으로 화면을 끄거나 다른 앱으로 옮기면 이 표시는 아무 일도 하지 않는다. 그 뒤에도 녹음을 보장하려면 마이크 유형의 포그라운드 서비스와 알림이 필요하며 아직 없다([아직 없는 것](#아직-없는-것)).
- 검증은 `screen_awake_test.dart`(세기 규칙, 생명주기, 채널 이름과 인자, 실패 시 던지지 않음, 켜기와 끄기 실패 뒤 다시 보내기, 늦게 끝난 실패가 뒤 요청을 되돌리지 않음), `record_keep_awake_test.dart`(E-2의 시작, 멈춤, 이어 가기, 확인 창, 끝내기, 화면 이탈, 권한 거부, 엔진 분리), `life_fact_step_test.dart`의 `녹음 중 화면 켜짐`(듣는 중, 다 말했어요, 5분 도달, 화면 이탈, 시작 실패)이다. 모두 대역으로 요청 시점만 본 로컬 테스트다. 실기기에서 화면이 정말 꺼지지 않는지, 실제 마이크 녹음 중의 동작은 확인하지 않았다.

### 아직 없는 것

녹음 업로드는 소감 화면의 `리포트 만들기`에 붙였다([현재 사용자 흐름](#현재-사용자-흐름)). 남은 것은 다음과 같다.

- 녹음이 없는 회차에 홈 배너를 반복해 띄우지 않기(#115 병합 뒤).
- 앱이 백그라운드로 내려갔을 때의 처리와 포그라운드 서비스. 녹음하는 동안 화면을 켜 두는 것만 있다([녹음 중 화면 켜짐](#녹음-중-화면-켜짐)).

## 푸시 알림

리포트 생성이 끝나면 서버가 FCM으로 이 기기에 알린다. 앱은 이 기기를 FCM에 등록해 받은 등록 ID를 서버에 등록하고(1-7), 로그아웃 전에 지우며(1-8), 알림을 누르면 그 리포트를 연다. 서버 쪽 발송은 [backend/README.md](../backend/README.md)의 "리포트 완료 푸시"에 있다.

### 등록 ID

FCM은 예전의 기기 토큰(`getToken`, HTTP v1의 `token`) 대신 Firebase Installation ID(FID)를 쓰도록 바꿨다. `firebase_messaging` 17에서 `getToken`, `onTokenRefresh`, `deleteToken`은 deprecated이고, 앱은 `register()`를 부른 뒤 `onRegistered`로 FID를 받는다. 서버는 HTTP v1 발송의 `fid`에 이 값을 넣는다([FCM 메시지 형식](https://firebase.google.com/docs/reference/fcm/rest/v1/projects.messages), [등록 관리](https://firebase.google.com/docs/cloud-messaging/manage-tokens)). FID는 바뀔 수 있어 `onRegistered`로 새 값이 오면 바꾼다.

### 언제 등록하고 언제 푸는가

| 상황 | 동작 |
| --- | --- |
| 로그인했고 알림 수신(선택 동의)에 동의함 | 알림 권한을 묻고(안드로이드 13 이상에서만 창이 뜬다, 앱을 켤 때마다 한 번) FCM에 등록해 FID를 받는다 |
| 로그인하지 않음, 알림 수신에 동의하지 않음 | 권한을 묻지 않고 Firebase를 초기화하지도 않는다 |
| 로그아웃, 세션 버림, 설정에서 알림 수신 동의를 끔 | FCM 등록을 푼다(`unregister`). 등록을 기다리는 중이었어도 푼다 |
| 다른 계정으로 바뀜 | 그 계정의 동의(1-3)를 다시 읽어 위 기준을 따른다 |
| 계정(1-3)을 처음 읽는 중이거나 읽지 못함 | 모르는 것으로 보고 그대로 둔다. 연결이 잠깐 끊겼다고 등록을 풀지 않는다 |

알림 권한을 거절해도 등록은 하지만 알림이 보이지 않는다. 앱을 켜자마자 FCM이 스스로 등록하지 않도록 `AndroidManifest.xml`에서 `firebase_messaging_auto_init_enabled`를 껐다. 그래서 동의한 계정이면 앱을 켤 때마다 앱 코드가 직접 `register()`를 부른다. 이 등록 ID(FID) 방식은 `firebase_messaging_installation_id_enabled`를 켜 두어야 쓸 수 있다. 빠지면 `register()`가 `IllegalStateException: API disabled`로 실패해 등록 ID를 받지 못하고 서버(1-7)에도 등록하지 않는다(2026-11-07 Galaxy S22 실기기에서 확인).

코드는 [push_messaging.dart](lib/features/push/push_messaging.dart)(Firebase를 감싼 `PushMessaging`)와 [push_registration.dart](lib/features/push/push_registration.dart)(`pushRegistrationProvider`)다. 기본 `pushMessagingProvider`는 아무것도 하지 않는 `NoPushMessaging`이고 `main.dart`의 `rootApp`만 `FirebasePushMessaging`으로 바꾼다. 그래서 기존 위젯 테스트와 여정 테스트는 계정(1-3)을 더 읽지 않고 Firebase도 부르지 않는다. 확인 내용은 `test/push_registration_test.dart`에 있다.

### 서버 등록

| 때 | 서버 호출 |
| --- | --- |
| FID를 받음(앱을 켤 때마다, FID가 바뀔 때) | 1-7 `PUT /auth/me/push-devices/{fid}`. 같은 실행에서 같은 FID는 한 번만 보낸다. 실패해도 다시 시도하지 않고 다음에 앱을 켤 때 다시 보낸다 |
| 설정의 로그아웃 | 세션을 지우기 **전에** 1-8 `DELETE`. 3초만 기다리고 실패해도 로그아웃한다. 오프라인에서도 로그아웃은 되어야 해서다 |
| 알림 수신 동의를 끔 | 부르지 않는다. 서버가 1-6에서 그 계정의 등록을 지운다 |
| 탈퇴 | 부르지 않는다. 서버가 계정과 함께 지운다 |

로그아웃의 1-8은 [settings_screen.dart](lib/features/settings/settings_screen.dart)의 로그아웃 버튼이 `SessionNotifier.signOut()` 앞에서 부른다. `signOut()` 안에서 부르면 `sessionProvider`가 자기에게 의존하는 `pushRegistrationProvider`를 읽게 되어 Riverpod가 순환 의존으로 막는다. 세션이 풀려 로그인 화면으로 가는 경우(`sessionLossProvider`)는 세션이 없어 1-8을 보내지 못한다. 그 서버 등록은 FCM 등록을 푼 뒤 발송이 `UNREGISTERED`로 실패할 때 서버가 지우고, 같은 기기에서 다른 계정이 등록하면 그 계정으로 옮겨진다. API는 [push_device_api.dart](lib/data/push_device_api.dart)이고, 본문 없는 `204`를 받으려고 `ApiClient.put`을 더했다.

### 알림을 받은 뒤

| 상황 | 동작 |
| --- | --- |
| 앱이 꺼졌거나 뒤에 있을 때 도착 | 안드로이드가 알림을 띄운다. 채널은 `MainActivity`가 만드는 `report_ready`(리포트 알림)이고 `AndroidManifest.xml`의 `default_notification_channel_id`로 지정했다 |
| 앱이 화면에 떠 있을 때 도착 | 시스템 알림을 띄우지 않는다(안드로이드 기본). 홈은 만드는 중인 리포트를 5초마다 묻고 있어 `리포트가 도착했어요`가 따로 뜬다. 로컬 알림 패키지는 더하지 않았다 |
| 알림을 누름 | `data.type == reportReady`의 `sessionId`를 `pendingReportOpenProvider`에 둔다. 보기만 하는 화면(홈, 제출 완료, 리포트와 리포트 기록, 알림, 설정, 프로필 설정과 프로필 전환, 일대기 보기)에 있으면 `main.dart`가 그 리포트(`/report/{sessionId}`)를 그 위에 바로 연다. 로그인, 동의, 등록, 면회 녹음과 평가, 업로드, 글 고치는 화면에서는 끊지 않고 기다렸다가 보기 화면에 오면 연다(`report_open_policy.dart`, #264). 앱을 켜는 중이면 스플래시가 세션을 확인하고 홈으로 옮긴 뒤 연다 |
| 로그아웃했거나 알림 수신 동의를 끈 뒤 누름 | 열지 않는다 |

알림 아이콘은 정하지 않아 앱 아이콘을 쓴다. 기기에 따라 흰 사각형으로 보일 수 있다. 다른 어르신의 리포트 알림을 눌렀을 때 고른 어르신을 바꿀지는 정하지 않았다. 리포트 화면은 회차 ID로 읽으므로 고른 어르신과 관계없이 열린다.

### 설정 파일

`android/app/google-services.json`은 Firebase 콘솔에서 받는다. `.gitignore` 대상이라 커밋하지 않고 저장소 밖으로 전달한다. [app/build.gradle.kts](android/app/build.gradle.kts)는 이 파일이 있을 때만 google-services 플러그인을 붙인다. 파일 없이 빌드하면 앱은 Firebase 초기화에 실패한 것으로 보고 등록 없이 지낸다. GitHub Actions의 `Release build`는 앱 빌드가 돌 때만([Play 업로드용 빌드](#play-업로드용-빌드)) 시크릿 `GOOGLE_SERVICES_JSON_BASE64`(11/8 등록)에서 이 파일을 만들고, 시크릿이 없으면 경고를 남기고 푸시 없는 앱을 만든다. 서버가 발송에 쓰는 서비스 계정 키는 앱에 넣지 않는다.

디버그 빌드는 받은 FID를 `[push] 등록 ID: ...`로 로그에 남긴다. Firebase 콘솔의 테스트 메시지에 이 값을 넣어 알림이 오는지 확인할 때 쓴다. 릴리스 빌드는 남기지 않는다.

## 새 버전 안내

Play에 새 버전이 올라오면 구버전 사용자에게 앱 안에서 알리고 받게 한다. 구글 플레이의 앱 내 업데이트 API를 쓰는 `in_app_update`의 유연한 업데이트다. 코드는 [app_update.dart](lib/features/app_update/app_update.dart)의 `AppUpdateController`와 [app_update_watcher.dart](lib/features/app_update/app_update_watcher.dart)의 `AppUpdateWatcher`이며, `MaterialApp.router`의 `builder`에 둔다. 플레이 호출은 `AppUpdateGateway` 뒤에 두어 테스트에서 가짜로 바꿔 끼운다.

`upgrader`와 `app_version_update`도 검토했다. 둘 다 Play 스토어 웹페이지를 읽어 버전을 찾으므로 페이지가 바뀌면 구버전 사용자에게 안내가 가지 않는다. 앱이 Android 우선이므로 공식 API를 골랐다. iOS를 추가하면 iOS 쪽 안내를 따로 정한다.

1. 앱을 켜 첫 화면이 그려진 뒤와, 백그라운드에서 돌아올 때마다 새 버전이 있는지 묻는다.
2. 새 버전이 있으면 Play가 안내 창을 띄운다. 문구와 모양은 Play가 정하며 앱이 바꿀 수 없다. 안내 창은 앱이 켜져 있는 동안 한 번만 띄운다. 보호자가 거절하면 앱을 새로 켤 때까지 다시 묻지 않는다. 받다가 실패하면 다음 확인 때 다시 묻는다.
3. 받기로 하면 앱을 쓰는 동안 뒤에서 받는다. 화면은 막지 않는다.
4. 다 받으면 어느 화면에 있든 알림 줄로 `새 버전을 받았어요. 다시 시작하면 바로 쓸 수 있어요.`와 `다시 시작`을 보여준다. 이 알림 줄은 저절로 사라지지 않고 닫기 아이콘으로 닫는다. 닫았으면 앱에 다시 돌아올 때 다시 보여준다. 받아 둔 채 앱을 껐다 켜도 다시 보여준다.
5. `다시 시작`을 누르면 Play가 설치하고 앱을 다시 띄운다. 보호자가 누를 때만 설치한다.

- **면회 흐름 동안에는 미루고 홈에 돌아오면 알린다.** 면회 흐름은 `/visit/photo`, `/visit/record`, `/visit/cards/add`, `/visit/review`, `/visit/review/done`, `/visit/upload`다. 이 화면들에서는 Play 안내 창도 다시 시작 알림 줄도 띄우지 않는다. 사진부터 리포트 만들기와 위로까지 한 사이클을 마치고 `/home`에 돌아오면 미뤘던 것을 띄운다. 알림 줄이 떠 있는 채로 면회를 시작하면 그 알림 줄은 닫고, 홈에 돌아오면 다시 띄운다. 면회 중에 앱이 다시 시작되면 WAV 헤더가 쓰이지 않아 열 수 없는 녹음 파일이 남고([파일을 반드시 닫아야 하는 이유](#파일을-반드시-닫아야-하는-이유)), 보내지 않은 소감도 사라진다. 현재 화면은 `push`로 쌓은 화면까지 포함해 `GoRouter.state`로 읽는다.
- 면회 흐름 밖의 화면(홈, 카드, 프로필, 일대기 등)에서는 바로 띄운다. 그 화면에서 입력하던 내용은 다시 시작하면 사라지지만, 보호자가 누를 때만 다시 시작하므로 따로 막지 않는다.
- 면회를 홈이 아닌 화면으로 빠져나가면(뒤로 가기로 카드 화면 등) 다음에 홈에 오거나 앱에 다시 돌아올 때 알린다.
- 다른 화면이 알림 줄을 새로 띄우면 이 알림 줄은 닫힌다. 앱에 다시 돌아올 때 다시 보여준다.
- Play에서 설치하지 않은 앱(`flutter run`, 직접 설치한 APK)은 확인이 실패하며, 이때는 아무것도 띄우지 않는다. 디버그 빌드에서만 `[app-update]` 로그를 남긴다.
- 사용자 자료는 보내지 않는다. 기기의 Play 스토어 앱에 이 앱의 새 버전이 있는지만 묻는다.

### 업데이트가 필요하다는 안내

서버가 바뀌어 구버전 앱의 요청이나 응답이 맞지 않게 되면, 화면의 실패 문구에 더해 업데이트가 필요하다고 알린다.

1. [서버 요청 공통 틀](#서버-요청-공통-틀)의 `ApiClient`와 로그인 전 API의 `AuthApi`가 앱이 서버와 맞지 않아 보이는 실패를 `onContractMismatch`로 알린다. 실패는 화면에 그대로 던진다. 고르는 기준은 [app_version.dart](lib/data/app_version.dart)의 `suggestsContractMismatch` 하나를 함께 쓴다.
   - 서버가 경로를 모른다: `404 NOT_FOUND`, `405`, `410`. 회차나 프로필이 없다는 `404`처럼 업무상 거절은 넣지 않는다.
   - 서버가 요청 형식이 틀렸다고 한다: `422 INVALID_REQUEST`. `REQUIRED_CONSENT_MISSING`처럼 업무상 `422`는 넣지 않는다.
   - 서버가 업데이트를 요구한다: `426`.
   - 성공 응답을 읽지 못했다: 객체가 아니거나 모양이 다르거나 모르는 값이 왔다. 각 API는 응답을 `ApiClient.read`로 읽고, 직접 확인한 값이 없으면 `ApiClient.unexpected`로 실패를 만든다.
2. `AppUpdateController.suspectOutdated`가 Play에 새 버전이 있는지 다시 묻는다. 새 버전이 있을 때만 업데이트가 필요하다고 본다(`AppUpdateState.needed`). 위 실패는 앱의 버그나 서버 쪽 실수여도 같은 모양이어서, 새 버전이 없으면 업데이트를 권하지 않는다. `426`만은 서버가 분명히 요구한 것이므로 새 버전을 찾지 못해도 필요하다고 본다.
3. 알림 줄로 알린다. 업데이트가 필요하다고 본 뒤에는 앱에 다시 돌아올 때마다 다시 알린다.

| 상태 | 알림 줄 | 버튼 |
| --- | --- | --- |
| 새 버전을 아직 받지 않음 | `새 버전이 나와서 지금 앱으로는 안 되는 기능이 있을 수 있어요. 업데이트해 주세요.` | `업데이트`. 앞서 Play 안내 창을 거절했어도 다시 띄운다 |
| 새 버전을 받아 둠 | `새 버전이 나와서 지금 앱으로는 안 되는 기능이 있을 수 있어요. 다시 시작하면 새 버전으로 바뀌어요.` | `다시 시작` |
| 면회 흐름 중 | `새 버전이 나와서 지금 앱으로는 안 되는 기능이 있을 수 있어요. 홈 화면으로 돌아가면 업데이트할 수 있어요.` 이번 실행에서 한 번만 알린다. 홈에 돌아오면 위 두 줄 중 하나로 바꿔 알린다 | 없음 |
| `426`인데 앱 안에서 받을 새 버전이 없음 | `새 버전으로 업데이트해야 쓸 수 있어요. Play 스토어에서 업데이트해 주세요.` | 없음 |

면회 흐름 중에는 버튼을 두지 않는다. 녹음 중에 다시 시작하면 열 수 없는 녹음 파일이 남기 때문이다. 6-2 녹음 제출이 실패해도 녹음은 기기에 남아 홈의 `음성 다시 보내기`로 업데이트 뒤에 다시 보낼 수 있다([현재 사용자 흐름](#현재-사용자-흐름)).

기기에 저장한 자료(보낼 녹음 목록 등)를 읽지 못하는 문제는 서버와 상관없어 넣지 않았다.

### 서버에 앱 버전 알리기

서버가 구버전을 확실히 거절할 수 있도록, 모든 요청(`ApiClient`, `AuthApi`)에 설치된 앱의 versionCode를 `X-App-Version-Code` 헤더로 싣는다. 값은 `pubspec.yaml` `version`의 `+` 뒤 숫자이며, 앱을 켤 때 `package_info_plus`로 한 번 읽어 `appVersionCodeProvider`에 넣는다(`main.dart`). 읽지 못하면 헤더 없이 보낸다.

서버가 최소 지원 버전보다 낮은 요청을 `426`으로 거절하면, 앱은 Play에서 새 버전을 찾지 못해도 업데이트가 필요하다고 알린다(위 표의 마지막 줄). 서버는 `426 APP_UPDATE_REQUIRED`로 거절하며, 앱은 `errorCode`를 보지 않고 `426`만 본다.

서버는 다음과 같이 처리한다(`backend/README.md`의 "최소 지원 앱 버전"). 헤더가 없거나 숫자가 아니면 통과시킨다. 헤더를 싣기 전 빌드(versionCode 4 이하)를 막지 않기 위해서다. 그래서 헤더를 싣는 첫 빌드부터만 서버가 구버전을 거절할 수 있다.

| 서버 | 할 일 |
| --- | --- |
| 설정 | `SAEROK_MIN_ANDROID_VERSION_CODE`, 기본값 `0`(검사 안 함) |
| 판단 | 헤더 값이 설정보다 작으면 `426`, 공통 `ErrorResponse`(`errorCode: APP_UPDATE_REQUIRED`, `retryable: false`) |
| 운영 | 구버전과 호환되지 않는 서버를 올리기 전, 호환되는 앱을 Play에 낸 뒤 설정을 그 versionCode로 올린다 |

### 확인하는 법

단위 테스트는 [app_update_test.dart](test/app_update_test.dart)가 가짜 창구로 묻는 횟수, 다시 시작 권유, 면회 흐름 중 보류와 업데이트 필요 안내를 확인한다. 어떤 실패를 알리는지는 [api_client_test.dart](test/api_client_test.dart)가, 앱 버전 헤더와 로그인 요청의 실패 알림은 [app_version_test.dart](test/app_version_test.dart)가 확인한다. 실제 안내 창은 Play에서 받은 앱에서만 뜬다.

1. 내부 테스트 트랙(또는 내부 앱 공유)에 versionCode가 낮은 버전을 올려 기기에 Play로 설치한다.
2. versionCode를 올린 버전을 같은 트랙에 올린다.
3. 기기의 Play 스토어에서 앱 페이지를 한 번 열어 새 버전을 알게 한 뒤 앱을 켠다.

### 확인이 필요한 것

- **강제 업데이트 여부와 기준(PM).** 지금은 거절할 수 있는 유연한 업데이트만 쓴다. 꼭 받아야 하는 버전(서버 계약 변경 등)에 화면을 막는 즉시 업데이트를 쓸지 정해야 한다. 즉시 업데이트의 기준인 업데이트 우선순위는 Play Console 화면에서 넣을 수 없고 Play Developer API로 올릴 때만 넣을 수 있으므로, 쓴다면 릴리스 절차도 함께 정한다.
- **거절한 보호자에게 다시 묻는 간격(PM).** 지금은 앱을 새로 켤 때마다 다시 묻는다.
- **알림 줄 문구(PM).** 위 문구는 모두 FE 초안이다.
- **헤더의 개인정보 검토(PM).** versionCode는 사용자를 식별하지 않는 앱 빌드 번호이지만, 요청마다 서버에 새로 보내는 값이므로 서버 로그에 남는지와 함께 확인한다.
- **실기기 확인(릴리스 담당).** 위 [확인하는 법](#확인하는-법)은 아직 하지 않았다.

## 서버 요청 공통 틀

로그인한 뒤 부르는 공개 API는 [api_client.dart](lib/data/api_client.dart)의 `ApiClient`로 보낸다. 서버 주소(`SAEROK_API_BASE_URL`), `Authorization` 헤더와 앱 버전 헤더(`X-App-Version-Code`, [서버에 앱 버전 알리기](#서버에-앱-버전-알리기))를 붙이고, 응답을 JSON 객체로 읽는다. 각 API는 경로와 본문만 넘긴다. `get`, `post`, `patch`, 파일 업로드용 `postMultipart`와 `delete`가 있으며, `delete`만 빈 `204` 응답을 성공으로 본다(2-8). 로그인 전 API는 `AuthApi`가 따로 맡는다.

| 실패 | 언제 |
| --- | --- |
| `ApiServerFailure` | 서버가 공통 `ErrorResponse`로 거절했다. `errorCode`를 읽지 못하면 `null`로 두고 지어내지 않는다 |
| `ApiNetworkFailure` | 연결 실패나 시간 초과. JSON 요청은 15초, 파일 업로드는 5분(`postMultipart`의 `limit`로 줄일 수 있다) |
| `ApiUnexpectedResponseFailure` | 성공 응답이 객체가 아니거나 계약과 모양이 다르다. 성공으로 넘기지 않는다 |
| `ApiSignedOutFailure` | 로그인 세션이 없다. 요청을 보내지 않는다 |

각 API는 성공 응답을 `ApiClient.read`로 읽고, 직접 확인한 값이 없으면 `ApiClient.unexpected`로 실패를 만든다. 앱이 서버와 맞지 않아 보이는 실패는 `onContractMismatch`로 알려 업데이트 안내에 쓴다([업데이트가 필요하다는 안내](#업데이트가-필요하다는-안내)).

API별 요청은 이 틀 위에 따로 둔다.

| 파일 | API |
| --- | --- |
| [card_api.dart](lib/data/card_api.dart) | 4-1 카드 생성 요청, 4-2 상태, 4-3 묶음 조회. 4-1이 `CARD_SET_READY`, `VISIT_IN_PROGRESS`로 거절되면 실패가 아니라 `ready`, `inVisit` 상태로 받는다. 4-2의 `ready`에 `needsRefresh: true`가 붙으면 `needsRefresh` 상태로 받는다 |
| [visit_api.dart](lib/data/visit_api.dart) | 5-1 회차 만들기, 5-3 보충 카드 더하기, 6-1 보호자 평가 저장, 6-2 녹음 제출(multipart). 6-1이 `EVALUATION_ALREADY_SUBMITTED`로 거절되면 이미 저장한 것으로 본다 |
| [speech_api.dart](lib/data/speech_api.dart) | 세부 정보 음성의 짧은 전사 `POST /api/v1/speech-transcriptions`(multipart `audio`, 이슈 #138). 명세(6-6)와 서버 구현은 #214. 결과를 2분까지 기다린다 |

세션은 요청할 때마다 `sessionProvider`에서 새로 읽는다. 세션이 곧 만료되거나 `401`을 받으면 새로 받아 한 번만 다시 보내고, 새로 받지 못하면 `401`을 그대로 돌려준다(위 "사용 중 세션 만료"). 파일 업로드(`postMultipart`)는 다시 보낼 수 있도록 파일을 만드는 함수를 받는다. 테스트는 `apiClientProvider`를 override하고, 확인 내용은 `test/api_client_test.dart`에 있다.

## 담당과 남은 연동

| 영역 | FE 작업 | 함께 정할 경계 |
| --- | --- | --- |
| 화면 | 초기 설정, 카드, 면회, 리포트, 평가와 일대기 | 카드 수와 제공 방식 등 제품 범위는 PM 결정 |
| 녹음 | 권한 안내, 녹음 상태, 제어와 앱 생명주기, 기기 저장 | 음성 형식은 AI가 확정한다. 녹음 제출(6-2)과 분석 상태 조회(6-3)는 연결함. 분석 실패 후 다시 요청(6-5)도 연결함(#213). 백그라운드 처리와 포그라운드 서비스는 남음 |
| 사진 | 카메라와 갤러리 연동 | 로그인 시 프로필 사진 업로드(3-1)와 설명 수정의 서버 저장(3-3, #205)을 연결함. 사진 삭제 버튼은 없음(서버 3-4는 #240). 로그인하지 않은 목 모드는 앱 안에서 처리함. 면회 사진은 기기 카메라로 찍어 갤러리 `새록` 앨범에 남기고 5-2로 올림. 프로필 사진 올리기(3-1)와 AI 설명 생성은 11/9 실기기(Galaxy S22)에서 운영 서버로 확인함(팀 운영 기록). 그 밖의 실제 기기와 운영 서버의 연결 검사는 별도 |
| 데이터 | 합의된 저장 및 서버 인터페이스를 앱에 연결 | BE가 저장 구조, 암호화와 API 담당. 로그인한 계정은 `ApiClient` 위의 API 파일로 서버를 쓴다. `MockRepository`는 로그인 없는 디버그 빌드와 테스트에서 쓴다. 로그인한 계정의 약관 동의 표시와 변경은 서버를 쓴다(#179). `profileProvider`는 목 프로필의 `lifeFactIds`를 채운다 |
| 품질 | 오류 상태, 수동 전환과 접근성 | 실제 모델 결과와 실패 상태는 AI, BE 계약 확인 |

STT는 Tailscale 사설망으로 연결하는 개인 GPU 서버, 사진 설명과 카드 및 리포트 생성은 ML API를 쓴다([ADR-006의 2026-10-11 정정](../docs/architecture/decisions/ADR-006-server-side-ai-processing.md#현재-적용할-방향-2026-10-11-정정)). 기본 STT 연결이 실패하면 예비 STT로 한 번 전환하며, 11/8 운영은 기본 STT 서버에 연결되지 않아 예비 STT로 처리했다([루트 README](../README.md#배포와-시연)). STT 서버 전사 기본값을 바꾼 #276은 11/9 예비 STT 서버에만 손으로 적용했고 기본 STT 서버에는 적용하지 않았다. 승인 배포 workflow는 STT 서버를 배포하지 않는다(팀 운영 기록). 사진 설명은 AI 사진 분석에 동의한 계정의 사진만 운영의 photo-worker가 만든다(#257). 실기기와 운영 서버에서 녹음부터 다음 회차까지 이어서 확인하는 일은 남아 있다.

동의와 개인정보 조건은 위 법률 문서를 따르며, 녹음 시작과 AI 제안의 프로필 및 스토리 반영에는 사용자 확인이 필요하다. 목 화면에 표시된 카드 수, 사진 설명과 동의 항목은 제품의 최종 결정이나 실제 연동 완료를 뜻하지 않는다. 계약과 PM 문서가 다른 부분은 관련 담당자가 확인한다.

### 계정 응답 읽기

`Account`는 공통 계약의 `authProvider`를 읽고 `loginId`를 요구하지 않는다. `email`은 `String?`이며 서버가 제공하지 않는 경우 `null`을 그대로 유지한다. 이메일을 임의로 채우지 않는다. 계정 목 데이터 두 벌은 이메일을 보관하지 않는 응답을 예시로 사용한다.

`test/account_model_test.dart`는 실제 `Account.fromJson`으로 이메일의 `null`, 문자열, 누락과 잘못된 타입을 검사한다. 이 변경은 계정 응답을 읽는 범위이며 이메일 미저장 정책을 확정하거나 화면의 실제 로그인 연동을 완료한 것은 아니다.

구글 로그인 연결과 별도 `AuthAccount`는 [PR #50](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/pull/50)에서 다룬다. 약관의 서버 관리, 앱 재실행 시 로그인 유지와 만료 후 자동 재인증은 해당 PR의 후속 요청이었다. 로그인 유지와 자동 재인증은 [세션 보관](#세션-보관)에 구현했고, 약관의 서버 관리는 아직 하지 않았다.
