# AI 영역

담당 리더: 이문영

## 현재 기준

- STT와 화자분리는 개인 GPU 서버에서 실행하고 BE는 Tailscale 사설망으로 연결하며, 사진 설명과 카드 및 리포트 생성은 ML API를 활용한다. 기본 STT 연결이 실패하면 BE가 ck 예비 STT로 한 번 전환한다. 온디바이스 실행은 현재 범위에서 제외한다. 기존 GPU 일괄 처리 기록과 후속 방향은 [ADR-006](../docs/architecture/decisions/ADR-006-server-side-ai-processing.md#현재-적용할-방향-2026-10-11-정정)에 구분한다.
- 이미지 설명은 별도 승인 없이 카드 입력에 사용하고 사용자가 원할 때 앨범에서 수정한다. 사진 설명을 승인된 생애 사실로 자동 저장하지 않는다. 현재 구현은 AI 사진 분석에 동의한 계정의 프로필 사진만 `photo_analysis/`로 두 문장에서 네 문장의 설명을 만든다(#257, 프롬프트 `photo-1`, 모델은 BE 설정 `SAEROK_PHOTO_ANALYSIS_MODEL`이 비면 리포트 모델). 동의를 거두면 BE가 저장된 AI 설명을 지우고, 다시 동의하면 다시 분석한다(#288, 11/9 배포부터 운영). 11/8 운영 시험에서 공개 사진 43장을 두 번씩 분석해 86건 모두 완료했다. 실제 사용자 사진의 품질 검증은 남아 있다.
- 사진 메타데이터는 AI 분석과 주제 추천 입력에서 제외한다. 이야기 후보의 사실 반영과 주제 추천 변경은 보호자의 최종 확인을 받는다.
- 클로바 STT는 사용하지 않는다.

STT와 화자 분리의 실행 서버는 [`stt-server/`](../stt-server/README.md)에 둔다. 이 폴더는 생성 모델과 VLM을 포함한 AI 검증 자료를 관리한다.

처리 위치, 원본 전송과 삭제 조건은 [ADR-006](../docs/architecture/decisions/ADR-006-server-side-ai-processing.md)을 따른다. ML API(엘리스)의 처리위탁, 국외 이전, 보관과 학습 조건은 [법률 문서](../docs/legal/README.md#엘리스-ml-api-처리위탁과-국외-이전)를 따른다. 모델 제공사명, 처리 국가와 위탁 계약 문서는 실제 사용자 자료를 보내기 전에 확인해야 한다.

### 사진 설명의 세부 특징 확인 (photo-2)

`photo_analysis/`의 코드상 프롬프트 버전을 `photo-2`로 올렸다. 위 `photo-1` 운영 시험 기록과 배포 상태는 별도다. 인물별 위치, 안경, 복장과 행동을 나눠 보고, 그림자와 안경, 배경과 옷, 손에 든 물건과 뒤에 있는 물건을 구분하도록 지시한다. 불분명한 세부는 생략하고 배경 풍경만 보고 인물의 시선, 활동이나 기분을 만들지 않도록 했다.

모델 선택, 추론 설정, 호출 횟수와 응답 형식은 그대로다. 사진 확대 화면, 카드 질문 생성과 리포트 본문은 각 기능에서 처리한다. 배포 후 새 분석부터 적용하며, 이미 저장된 설명을 자동으로 다시 분석하지 않는다. 보호자가 직접 고친 설명을 우선 사용하는 규칙도 유지한다.

11/10 로컬 재시험에서 `gpt-6-luna`, `photo-2`로 기존 사진 5장을 한 번씩 분석해 모두 응답했다. 일부 기존 오류가 다시 나오지 않았지만 새로운 세부 동작 오류가 남았다. 생략된 특징을 정확하게 판별한 것으로 세지 않았으며, 설명 전체의 정확도 향상은 추가 평가가 필요하다. 사진과 생성 원문은 로컬 비공개 기록으로 보관한다.

자동 테스트는 프롬프트 전달, 응답 형식과 오류 처리, BE가 저장하는 프롬프트 버전을 확인한다. 실제 모델의 시각 판단은 별도 품질 평가로 확인한다.

| 영역 | AI에서 정할 내용 | 함께 확인 |

| 생성 기능 | 카드, 추가 질문, 리포트와 이야기 후보의 입력 문맥, 기억과 검색 흐름 | PM, FE, BE |
| 품질과 실패 | 신뢰도, 통과 기준, 재시도 상한, 보호자 확인과 수동 전환 조건 | QA, FE |

현재 구현 (2026-11-09 기준): 이미지 분석은 위 `photo_analysis/`로, 면회 녹음은 앱이 WAV 16kHz mono로 보내는 형식으로 구현돼 있다. STT 서버 코드의 전사 기본값은 #276에서 VAD 켬, 앞 문장 조건 끔으로 바꿨다([전사 옵션 비교](../stt-server/docs/vad-condition-comparison-20261109.md)). 운영 기록에 따르면 11/9 ck 예비 STT 서버에만 손으로 적용했고 기본 STT 서버(개인 GPU)는 아직 갱신하지 않았다. BE 승인 배포 workflow는 STT 서버를 배포하지 않는다. 표의 항목은 품질 검증과 이후 변경 때 함께 정할 내용이다.

모델 선택 기록에는 출처, 버전, 해시, 라이선스, 입출력, 실행 환경, 처리 시간, 메모리, 정확도, 실패 사례와 재검토 조건을 남긴다. 실행 명령과 결과는 실제로 검증한 것만 기록한다.

## 생성 기능 코드

### LLM 재시도와 Claude 연결 준비(2026-11-11, 로컬 변경)

동기 `invoke`(내부 스트리밍 포함)의 연결 오류, 408, 일시적 429와 5xx에 같은 경로로 최대 1회 재시도하는 공통 코드를 추가했다. SDK 자체 재시도는 계속 0이며, 형식 재시도에서도 API 오류를 다시 시도하지 않는다. 재시도는 최초 호출의 시간 예산과 작업 전체 마감을 공유한다. 인증·입력 오류와 식별 가능한 할당량 소진은 재시도하지 않는다. 백엔드의 `SAEROK_LLM_RETRY_ENABLED` 기본값은 false다. 직접 `stream`·비동기 호출에는 이 재시도를 적용하지 않는다.

엘리스 Claude 연결 준비는 `common/elice_claude.py`에 분리했다. API 모델 식별자는 `anthropic/claude-haiku-5-5`이며, 제공된 설명은 `claude-haiku-5-5`도 허용한다. 주소는 아직 확인하지 않아 하드코딩하거나 운영 `ENDPOINTS`에 등록하지 않았다. 2026-11-11 사용자가 제공한 엘리스 API 설명에서 Chat Completions, 스트리밍, JSON 구조화 출력과 도구 호출 지원 및 모델 별칭을 확인했다. GPT용 Responses API·추론 옵션과 허용 목록에 없는 stream_options를 보내지 않는다. 문서상 지원 확인이며 실제 연동 동작과 품질은 미검증이다. 기존 생성 함수의 자동 전환에는 연결하지 않았다.

주소를 확인한 뒤 `ai/`에서 기존 환경변수 `ML_API_KEY`를 사용해 `uv run python -m common.check_elice_claude --base-url <확인한-엘리스-v1-주소>`로 합성 텍스트·구조화 출력·도구 왕복을 수동 점검할 수 있다. 실제 모델을 호출하는 명령이며 이번 작업에서는 실행하지 않았다. 키를 명령행에 넣지 않는다. 출력은 검사 성공 여부 또는 오류 종류만 담는다. 사진 입력과 긴 전사, 카드·리포트 품질 검증을 대신하지 않는다.

설계와 현재 구현 범위는 [LLM 장애 대응](../docs/architecture/llm-failover.md), 구조 검토는 [ADR-010](../docs/architecture/decisions/ADR-010-llm-resilience.md)을 따른다. 실제 사용자 자료 전송 전 조건은 [법률 확인 표](../docs/legal/README.md#개발-우선과-실제-사용자-자료-사용-전-확인)에서 관리한다.

backend가 부르는 생성 기능 네 가지(카드, 리포트, 변경 제안, 사진 설명)와, 면회를 합성 페르소나로 돌려 보는 시뮬레이터가 있다.

| 폴더 | 내용 |
| --- | --- |
| [`card_generation/`](card_generation/README.md) | 카드 생성. 면회 전에 backend가 모은 context로 카드 12장과 새로 만들 주제를 만든다 |
| `report_generation/` | 면회 리포트. 면회 뒤 전사, 소감, 고른 카드로 제목, 본문, 카드별 요약을 만든다 |
| `proposal_generation/` | 변경 제안. 면회 뒤 이야기 후보와 카드 주제 조정(more, less, exclude)을 제안한다 |
| `photo_analysis/` | 사진 설명. BE가 발급한 유효 시간이 짧은 HTTPS 사진 주소(S3 Presigned URL)만 받아 사진에서 직접 보이는 장면을 두 문장에서 네 문장으로 설명한다. 태그는 만들지 않고 사진 메타데이터를 따로 입력으로 넘기지 않는다. 사진 파일 안의 EXIF 제거는 별도 사항이다. backend의 photo-worker가 부른다([사진 분석](../backend/docs/photo-analysis.md)) |
| `common/` | LLM 설정과 모델 주소 목록(`ENDPOINTS`), 정해진 형식으로 답 받기, 리포트와 변경 제안이 같이 쓰는 #106 형식(`visit_report.py`) |
| [`simulation/`](simulation/README.md) | 시뮬레이션. 합성 페르소나로 면회를 회차마다 이어서 돌린다 |

리포트와 변경 제안은 #106 내부 API(8-3) 요청을 받고, `common.visit_report.combine()`으로 #106 응답 하나로 합친다. 쓰는 법은 각 패키지의 `__init__.py` 설명에 있다.

### 화자 정보가 부족한 전사

`report-3`, `proposals-5`는 라벨 누락이나 입력 인원과 라벨 수의 차이만으로 리포트와 이야기 후보 생성을 막지 않는다. 입력 인원과 라벨은 참고 정보로 쓰고 대화 맥락으로 화자와 경험의 주체를 추론한다. `speaker_context`는 입력 상태만 전달하며 후보 허용 여부를 계산하지 않는다.

전사에 나온 경험은 주체가 불확실해도 검토용 이야기 후보로 제시할 수 있다. 프롬프트는 후보의 `reason`에 추론 근거와 확인이 필요한 부분을 적도록 한다. 이 문구의 생성은 모델 지시이며 코드가 의미를 검증하는 것은 아니다. 전사에 없는 경험이나 관계는 만들지 않고, 보호자의 승인 전에는 생애 사실로 반영하지 않는다. 리포트 본문은 근거가 부족한 인물 귀속을 단정하지 않는다.

합성 입력과 모델 대역 테스트는 입력 전달과 후보 유지 동작을 검사한다. 실제 모델이 불확실성을 적절히 표시하는지와 화자 귀속 품질은 별도 검증이 필요하다.

### 이야기 후보의 인물 관계와 사건 맥락 확인 (proposals-10)

이야기 후보를 쓸 때 앞뒤 질문, 답변과 정정을 함께 읽고, 행동한 사람, 행동의 대상, 친족 관계와 사건 순서를 따로 확인하도록 지시한다. 관계가 불분명하면 `reason`뿐 아니라 보호자가 읽는 `title`, `content`에서도 단정하지 않는다. 확인 가능한 사건과 기억 단서는 후보로 남겨 보호자가 검토한다.

이야기 후보의 추론 강도는 `medium`, 공통 출력 상한은 16000으로 유지한다. 주제 조정의 지시와 필터, 리포트 본문, STT, 응답 형식과 보호자의 승인 절차는 그대로다. 새 버전은 배포 후 새로 생성하는 후보부터 쓰며 기존 후보를 자동 수정하지 않는다.

11/10 로컬 재시험에서는 `gpt-6-luna`에 저장된 장시간 전사를 넣고 `proposals-10`, `medium`으로 한 번 실행했다. 이 시험만 출력 상한 32000을 사용했으므로 제품 기본값 16000에서의 완료 검증과 구분한다. 일부 잘못된 인물 귀속의 단정은 줄었지만 정확한 관계 복원, 시간 표현과 사건 순서 오류가 남았다. 원문과 생성 내용은 로컬 비공개 기록으로 보관한다.

자동 테스트는 새 지시가 이야기 후보 호출에만 전달되는지, 기본 추론 강도와 출력 상한이 유지되는지, 응답 버전과 기존 필터를 확인한다. 모델의 의미 판단 정확도는 보호자의 확인과 별도 반복 평가가 필요하다.

### 보호자에게 보이는 말

`report-5`, `proposals-7`은 리포트와 이야기 후보(이유 포함)에 전사, 화자, 라벨, 보호자 소감처럼 처리 과정을 가리키는 말을 쓰지 않게 한다. 근거가 부족하면 그 사정을 설명하지 않고 말한 사람을 정하지 않는 표현으로 쓴다. 호칭과 관계는 모델 판단에 맡긴다(PM 결정). 11/8 운영 시험과 비교 결과는 `backend/docs/stability-test-20261108.md`에 있다.

### 이야기 후보 전부 받기와 아픈 기억 표시(2026-11-09 PM 결정)

이 절의 변경(`proposals-8`, `report-6`, 카드 생성 2판)은 #295로 develop에 들어갔고 2026-11-10 01:41 운영 배포(develop `83695093`)부터 운영에 있다. 운영 `.env`는 `SAEROK_CARD_GENERATION_PROMPT_VERSION`을 정하지 않아 backend 기본값 2가 쓰이므로 운영 카드도 2판이다. 그 전 운영 배포분(11/9, develop `59190ba7`)은 `proposals-7`, `report-5`였고 카드 생성 2판이 없었으며 backend의 카드 생성 판 기본값도 1이었다.

`proposals-8`은 이야기 후보와 주제 조정을 LLM 두 번으로 따로 받는다. 주제 조정은 이야기 후보 결과를 쓰지 않으므로 두 호출을 동시에 보낸다. 이야기 후보 전용 지시는 이야기 후보 절에만 두고, 두 호출이 함께 받는 공통 부분에는 화자 추론, 인원 주의, 명령 무시, 처리 과정 낱말 금지만 둔다. 이야기 후보 호출만 추론 강도를 `medium`으로 올리고, 대화 처음부터 끝까지 나온 서로 다른 경험을 하나씩 모두 내게 한다. 지금의 생각, 앞으로의 계획과 후회도 포함한다. 개수 제한은 프롬프트에서 없애고 코드에 안전 상한 30개만 둔다(넘으면 개수만 기록). 아픈 경험과 누구의 경험인지 불확실한 경험도 빼지 않고, 아픈 경험은 `sensitive`로 표시한다. 후보마다 일대기 분류(`storyCategory`: family, hobby, work, hometown, friend, travel, other)를 AI가 고른다. 주제 조정에서는 '면회 한 번에 많아야 2개'와 '꼭 필요한 것만'을 없앴고 카드당 하나와 아픈 기억 범위 규칙은 그대로다.

`report-6`은 본문을 '네다섯 문장' 대신 대화에서 나눈 화제마다 짧은 문단 하나씩 이야기한 순서대로 쓰게 하고, 분량을 가늠하도록 녹음 길이(`recording_minutes`, 분)를 넘긴다. 카드 요약은 오래 이야기한 카드에 두세 문장까지 허용한다. 기존 안전 규칙은 그대로다.

카드 생성 2판(`card_generation/_versions/v2`)은 쌓아온 이야기나 초기 정보에 나온 아픈 경험을 후보로 낼 수 있게 하고 그 카드를 `sensitive`로 표시한다. 사진, 빈 칸 여쭙기, 보편 추억으로는 아픈 경험을 꺼내지 않으며 최근 기억 시험 카드는 계속 막는다. backend 설정 `card_generation_prompt_version`이 2일 때 2판이 쓰이고, 1판은 결과의 `sensitive`가 늘 false다. 2판 문안은 `sensitive` 카드의 아픈 순간을 캐묻지 않는다(규칙 8). 남은 문제는 `card_generation/README.md`의 '아픈 경험 카드(2판)'에 있다.

### 아픈 이야기 표시 잇기와 아쉬웠던 카드의 주제 조정(2026-11-10, 운영 배포 전)

11/10 E2E 문제 5, 10, 12를 고친다. 보호자가 지우지 않는 한 아픈 이야기도 카드에 쓴다(PM 결정). backend가 승인한 이야기의 아픈 기억 표시를 `life_facts.sensitive`에 남기고 카드 생성 입력 `lifeFacts[].sensitive`로 넘긴다. 카드 생성 2판은 그 이야기를 근거로 한 카드를 코드로 늘 `sensitive`로 내고, 에이전트 프롬프트는 그런 이야기를 피하지 말고 좋았던 기억 쪽 장면으로 후보를 내게 한다. 1판 입력 처리와 결과는 바꾸지 않았다. 자세한 것은 `card_generation/README.md`의 '아픈 경험 카드(2판)'.

`proposals-9`는 보호자가 아쉬웠어요(`negative`)로 평가한 카드에 주제 조정 `more`를 내지 않게 한다. 프롬프트에 적고, 모델이 내도 코드(`_topics`)가 버린다. 같은 카드의 다음 조정(`less`, `exclude`)은 받는다. 앱이 AI 제안을 미리 골라 두므로 평가와 거꾸로 가는 '더 자주 꺼내기'가 그대로 반영되던 것을 막는다. 실제 모델로는 다시 돌려 보지 않았다.

리포트와 변경 제안 결과(`ReportResult`, `ProposalResult`)에는 처리 기록용 숫자(모델이 낸 후보 수, 토큰 수)가 붙지만 #106 응답에는 넣지 않는다. 위 문구가 실제 모델에서는 PM의 실제 면회 녹음 1건(약 88분)으로 확인했다([실제 면회 검증 기록](../docs/pm/real-visit-validation-20261109.md)).

출력 상한(`ChatConfig.max_tokens`=16000)은 Responses API에서 추론 토큰과 출력 토큰이 함께 쓴다. 위 실제 면회 녹음에서 이야기 후보 `medium`은 상한 안에서 끝났고, `high`는 추론 토큰 14,543으로 상한에 닿아 답이 비었다. 긴 면회에서 이야기 후보가 20~30개 나오고 추론 강도가 `medium`이면 이 상한에 닿아 응답이 잘릴 수 있고, 잘리면 `GENERATION_FAILED`로 그날 리포트까지 함께 실패한다(backend는 다시 시도하지 않음). 이야기 후보 호출만 상한을 올리는 안은 엘리스 프록시가 받는 값인지 확인하지 않아서 넣지 않았다. 운영에서는 처리 기록의 끊긴 응답 수(`incomplete_responses`)로 상한에 닿은 회차를 본다.

생성 기능은 DB를 읽지도 쓰지도 않는다. `pyproject.toml`은 `ai/`에 하나 두고, backend가 경로 의존성으로 설치할 때는 생성 기능 넷(`card_generation`, `report_generation`, `proposal_generation`, `photo_analysis`)과 `common`만 들어간다. `uv run pytest`도 네 패키지의 테스트를 돈다.

카드에는 좁은 치료 효과 검사만 적용하며 리포트의 기존 검사는 변경하지 않는다.

### 11/3 로컬 모델 전환

BE의 새 카드와 리포트 기본 모델, 시뮬레이션 기본 모델은 `gpt-6-luna`다. 공통 출력 상한은
16000이며 Responses API 스트리밍, 추론 `low`와 기존 시간 제한을 유지한다. 최대 출력 허용량을
늘린 것이며 항상 16000토큰을 생성한다는 뜻은 아니다. 이전 모델을 명시한 작업도 처리할 수
있도록 기존 주소는 유지한다. 운영 환경의 명시적 설정은 기본값보다 우선한다.

호출 주소와 키는 평가 문서에 기록하지 않는다. 모델 주소는 `common/llm.py`의 `ENDPOINTS`,
키는 기존 환경변수를 사용한다. 전환 검사는 합성 입력으로 진행하며 운영 배포는 별도다.

현재 구현 (2026-11-09 기준): 이 기본값은 11/5 운영 배포부터 들어갔고,
운영 기록(#187의 11/5 운영 배포 기록)에는 그날 운영 서버에서 `gpt-6-luna`로 카드 12장을 만든 기록이 있다.
