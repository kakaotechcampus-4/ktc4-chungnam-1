# 동의 문구와 기능 대응표

상태: 운영 중

이 문서는 `consent-draft.md`의 문구를 변경하지 않고, 각 문구가 적용되는 기능과 대응하는 법적 쟁점을 설명한다. `대응됨`은 문구와 기능이 연결됐다는 뜻이며, 실제 구현과 운영까지 자동으로 적법해졌다는 뜻은 아니다.

사진 등록과 AI 분석의 구분은 PR #92로 병합됐으며, 2026-10-14 PM이 두 항목을 가입 화면의 별도 선택 동의로 받고 기존 계정 동의 이력에 저장하도록 정했다. [ADR-001](../architecture/decisions/ADR-001-consent-and-temporary-processing.md#등록-사진과-분석용-임시-사본의-구분)의 보관 조건과 [동의안](consent-draft.md#가입-시-선택-동의)을 함께 읽는다. 유효한 동의는 다시 묻지 않고, 미동의자가 해당 기능을 사용하려고 할 때 필요한 동의를 요청한다. 정책 결정과 동의 및 삭제 기능 구현 완료는 구분한다. 2026-11-09 기준 AI 분석 동의는 2026-11-07 #257로 구현됐고(가입 화면, 설정의 계정 약관 동의, `consent_records.photo_analysis`), 철회 때 저장된 AI 설명을 지우는 처리는 #288로 더해 2026-11-09 배포(develop `59190ba7`)부터 운영에 있다. 사진 보관 동의는 구현되지 않았다.

2026-10-14 녹음 동의 확인 시점은 [ADR-001의 PM 수정안](../architecture/decisions/ADR-001-consent-and-temporary-processing.md#녹음-동의-확인-시점)을 따른다. 가입 동의와 피보호자 최초 등록 전 확인을 구분하며 매회 녹음 전 같은 확인 체크박스를 다시 요구하지 않는다. 피보호자별 동의와 대리 권한 확인의 구현이 끝났다는 뜻은 아니다.

## 대응 수준

- 대응됨: 동의 문구에 목적, 항목, 기간과 거부 영향을 반영함
- 부분 대응: 동의 문구가 있으나 권한 확인, 삭제 증명이나 제3자 동의가 추가로 필요함
- 미대응: 현재 동의문에 해당 기능이나 데이터 처리가 포함되지 않음

## 문구별 기능과 법적 쟁점

| 동의 문구 | 연결 기능 | 적용 시점 | 대응 법적 쟁점 | 대응 수준 | 구현과 운영에서 남은 조건 |
| --- | --- | --- | --- | --- | --- |
| 구글 계정 식별과 계정 생성 | 구글 로그인, 계정 생성과 재로그인 | 구글 인증 후 계정 생성에 필요한 필수 동의 완료 시 | 외부에서 받은 계정 식별정보의 최소 수집, 서버 저장과 파기 | 부분 대응 | 실제 OAuth 범위와 반환 항목, ID 토큰 폐기, 로그 제외와 계정 삭제를 구현으로 검증해야 함 |
| 서비스 제공을 위한 개인정보 처리 동의 | 회원가입, 피보호자 프로필, 카드, 녹음, STT, 화자 처리와 리포트 | 최초 가입과 피보호자 등록 전 | 보호자와 피보호자의 일반 개인정보 처리, 음성 수집, 서버 임시 저장, 목적에 필요한 최소 수집 | 부분 대응 | 계정 식별자와 동의 이력 외의 서버 저장 범위, 녹음 원본, 임시 파일과 로그의 삭제를 구현으로 검증해야 함 |
| 건강 관련 민감정보 처리 동의 | 인지 상태, 대화 주의사항, 발화 분석 결과, 금기 질문 차단 | 민감정보 최초 입력 전 | 건강 관련 민감정보를 일반 개인정보와 구분하여 별도 동의 | 대응됨 | 별도 체크박스로 받아야 하며 암호화, 접근 통제와 삭제 절차가 필요함 |
| 피보호자에게 안내하고 동의를 확인했다는 확인 | 피보호자 등록, 해당 피보호자의 녹음과 정보 처리 | 피보호자 최초 정보 입력 전. 매회 녹음 전 별도 체크박스는 요구하지 않음 | 앱 사용자가 아닌 피보호자의 의사 확인 | 부분 대응 | 보호자 가입 동의로 대신하지 않음. 동의자와 대리 권한의 확인 방법 및 기록은 후속 설계이며 현재 프로필 API에 없음. 철회나 대상 및 처리 범위 변경 시 재확인 필요 |
| 제3자 참여 시 녹음 중단 또는 별도 동의 | 다인 면회실 녹음 | 제3자 참여 감지 또는 확인 시 | 보호자가 참여하지 않은 타인 간 대화 녹음, 제3자 음성 수집 | 부분 대응 | 녹음 일시정지, 구간 삭제 또는 제3자 동의 절차가 실제 화면과 파이프라인에 필요함 |
| 사진 서버 보관 선택 동의 | 프로필 및 면회 사진 등록, 앨범과 일대기 표시 | 가입 화면. 미동의자는 업로드를 원할 때 요청하며 유효한 동의는 반복하지 않음 | 보관 목적, 항목, 기간과 거부 영향 고지, 정보주체의 처리 근거 | 부분 대응 | 사진 보관 동의 항목은 아직 DB와 API에 없고 현재 사진 업로드는 이 동의를 확인하지 않음. 기존 계정 동의 이력 확장, 기록 없는 계정 및 철회 계정의 재확인, 사진 속 정보주체 또는 대리 권한 확인, 철회 및 S3 실제 삭제 검증 필요. 거부해도 가입과 사진 없는 기본 서비스 이용 가능 |
| AI 이미지 분석 선택 동의 | VLM 분석, 이미지 기반 소재 추천 | 가입 화면. 미동의자는 분석을 원할 때 요청하며 유효한 동의는 반복하지 않음 | 보관 동의와 분석 동의 구분, 임시 사본의 처리 목적과 기한 | 부분 대응 | 계정별 분석 동의 이력(`consent_records.photo_analysis`), 가입과 변경 API, 미동의 계정의 작업 차단(worker가 가져올 때와 저장 직전에 확인), 분석 중 철회 시 결과 폐기는 #257로 구현. 철회 시 저장된 AI 설명은 지우기로 2026-11-09 PM 결정(API 1-6). #288로 구현해 2026-11-09 배포부터 운영에 있음. 철회하면 프로필 사진의 AI 설명을 지우고 분석 대기(`pending`)로 되돌리며 보호자가 쓴 설명은 남김. worker는 ML API를 부르기 바로 전에도 동의를 다시 확인함(#288). 미동의 때 올린 프로필 사진은 분석 대기(`pending`)로 남아 나중에 동의하면 분석됨. 이것이 "분석을 요청한 사진" 문구에 맞는지 PM 확인 필요. 현재 worker는 별도 임시 사본을 만들지 않고 S3 원본의 짧은 수명 조회 주소를 ML API에 넘김. 다만 ML API가 그 주소로 사진을 받아 가므로 업체 쪽 사본의 보관 조건은 확인하지 않음. AI 설명에서 이미 만든 대화 주제와 지난 카드 문구는 철회 때 지우지 않으며 처리 기준은 미정. 다만 근거가 AI 설명이 지워진 사진뿐인 주제는 다음 카드 생성 입력에서 빠짐(#291). AI 설명은 보호자 확인 없이 카드 생성 입력에 들어가므로(보호자가 고친 설명이 있으면 그것을 우선, 생애 사실로는 저장하지 않음) '보호자가 확인하기 전까지 사실로 반영하지 않음' 문구와 맞는지 PM 확인 필요. 미확인 분석 결과의 보관 기준, 메타데이터 항목은 미정이며 확인된 이야기 소재의 기존 보유 기준 및 얼굴 식별과 건강정보 추론 금지 유지 |
| 외부 AI 처리 안내 | 외부 STT, 화자 처리, 외부 LLM 카드와 리포트 생성 | 외부 서비스 최초 호출 전 | 처리위탁, 제3자 제공과 국외 이전 가능성 고지 | 부분 대응 | 업체명, 국가, 연락처, 전송 시기와 방법, 보유기간, 자체 학습 여부를 처리방침과 기능 실행 전에 알려야 함. 2026-11-09 기준 운영 서버는 엘리스 ML API로 카드, 리포트, 변경 제안과 사진 설명을 만들며, 사진은 S3 원본의 짧은 수명 조회 주소를 넘겨 ML API가 받아 감(#257). 업체 쪽 보관과 학습 조건은 문서에 없음. 리포트용 전사문 전송을 24시간 보관 기한 안으로 묶는 변경(#279)은 2026-11-09 배포부터 운영에 있음([법률 검토](README.md#실패-전사와-기기-녹음-보관의-로컬-수정안)) |
| 가명처리된 정보의 서비스 품질 개선 활용 동의 | 카드 평가, 리포트 평가, AI 모델 개선, 내부 평가셋 | 서비스 개선용 데이터 저장 전 | 기본 서비스와 구분된 추가 목적 이용, 선택 동의, 가명정보 처리 | 대응됨 | 원본과 추가정보 분리, 재식별 금지, 접근자 제한, 90일 만료 삭제가 필요함 |
| 선택 동의 거부 시 기본 서비스 이용 가능 | 학습 데이터 제공 여부 | 선택 동의 화면 | 선택 동의 거부를 이유로 기본 서비스 제공을 거부하는 문제 | 대응됨 | 거부 사용자의 데이터를 학습 데이터셋과 평가셋에 넣지 않도록 기술적으로 분리해야 함 |
| 면회 준비와 리포트 완료 알림 수신 동의 | 푸시 알림, 리포트 처리 완료 알림 | 알림 활성화 전 | 기기 토큰 처리와 선택 기능 거부권 고지 | 대응됨 | 알림 본문에 환자 이름, 건강정보, 전사와 리포트 내용을 포함하지 않아야 함. 현재 FCM 알림은 고정 문구와 회차, 분석 ID만 담음. 면회 준비 알림은 보내지 않으며, 앱 문구는 목적을 리포트 처리 완료 알림으로 줄여 표시함(`app/lib/features/auth/consent_terms.dart`). 동의안 문구를 좁힐지는 PM 확인 필요 |

## 기능별 확인 위치

| 앱 흐름 | 확인할 동의 |
| --- | --- |
| 구글 로그인과 계정 생성 | 필수 2개와 선택 4개를 한 화면에서 구분해 받는 것이 PM 결정. 현재 API(운영 배포)와 develop 앱의 가입 화면은 필수 2개와 선택 3개(서비스 품질 개선, 알림 수신, AI 이미지 분석)를 받고(#257) 사진 보관 항목은 미구현. 선택 동의는 설정의 계정 약관 동의 화면에서 바꿈(#271) |
| 피보호자 최초 등록 전 | 해당 피보호자 본인의 동의 확인. 대리인이 동의하면 동의와 적법한 대리 권한을 함께 확인. 확인 방법과 기록은 후속 설계이며 가입 동의로 자동 충족하지 않음 |
| 사진 등록과 보관 | 가입 때 받은 보관 동의가 유효하면 재요청하지 않음. 미동의, 철회 또는 기록 없는 계정이 업로드를 원할 때만 보관 동의를 요청하고 기존 계정 이력에 저장. 사진 보관 동의는 미구현이라 현재 업로드는 이 동의를 확인하지 않음 |
| AI 이미지 분석 | 가입 때 받은 분석 동의가 유효하면 재요청하지 않음. 미동의, 철회 또는 기록 없는 계정이 분석을 원할 때만 요청. 보관 동의로 대신하지 않음. 현재 develop 앱은(Play 출시 전) 미동의 계정이 사진을 올리기 전에 동의 시트를 띄우고, 거절하거나 닫으면 분석 없이 올림('다시 띄우지 않기'는 이 기기에서 계정별로 기억, #272). 미동의 계정에는 설명을 직접 쓰는 칸을 보여줌(#261). 설정에서 동의를 거두면 서버가 저장된 AI 설명을 지움(#288) |
| 휴대폰 사진 선택과 카메라 및 마이크 접근 | 기능 사용 시 필요한 운영체제 접근 절차를 처리. 서버 보관과 분석 동의 및 피보호자 본인 동의와 구분 |
| 대화 카드 생성과 선택 | 서비스 제공을 위한 개인정보 처리 |
| 면회 녹음 시작 | 앞서 확인한 동의 범위가 유지되는 경우 매회 체크박스를 다시 받지 않음. 마이크 권한이나 녹음 버튼으로 피보호자 동의를 대신하지 않음 |
| 녹음 제출, STT와 화자 처리 | BE가 계정의 필수 동의 두 항목과 회차 접근 권한을 검사. 피보호자별 동의 확인은 아직 구현되지 않음 |
| 외부 STT와 LLM 호출 | 확정 업체의 처리위탁과 국외 이전 안내 |
| 리포트 생성과 보호자 평가 | 서비스 제공을 위한 개인정보 처리, 건강 관련 민감정보 처리 |
| AI 품질 평가와 공통 모델 개선 | 가명처리된 정보의 서비스 품질 개선 활용 |
| 푸시 알림 | 면회 준비와 리포트 완료 알림 수신 동의(현재는 리포트 완료 알림만 보냄) |
| 스토리북 생성 | 등록 사진 표시는 사진 보관 동의의 목적에 포함. 이야기 생성과 그 밖의 정보 처리 범위는 추가 검토 유지 |

| 기능 | 판정 | 법적 근거와 적용 조건 |

## 구글 로그인 데이터 이동 검토안

구글 로그인 관련 표와 아래 내용은 PM 제안에 대한 검토안이다. 계정 식별자와 동의 이력만 저장하고 이메일과 이름을 저장하지 않는 방향의 구현 영향과 추가 항목 필요성을 BE와 FE가 확인한 뒤 확정한다.

- 구글은 자체 계정을 인증하고 ID 토큰을 발급하는 외부 인증 제공자이며, 현재 설계에서 새록이 보유한 개인정보를 대신 처리하는 수탁자로 두지 않는다.
- 새록은 사용자가 구글 로그인을 선택한 경우 구글에서 계정 식별자 `sub`를 받는다.
- 새록이 보유한 프로필, 음성, 사진, 전사문, 면회 기록과 리포트를 로그인 목적으로 구글에 보내지 않는다.
- 현재 흐름은 새록이 보유한 개인정보의 구글 제3자 제공, 처리위탁 또는 국외 이전으로 분류하지 않는다.
- 실제 OAuth 요청 범위, 반환 항목이나 데이터 이동이 달라지면 운영 전에 다시 검토한다.
