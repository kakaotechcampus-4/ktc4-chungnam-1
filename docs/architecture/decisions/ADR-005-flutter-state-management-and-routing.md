# ADR-005: Flutter 상태 관리와 화면 이동 방식

상태: accepted

담당: FE

결정일: 2026-09-06

관련 Issue: #5

## 배경

`app/README.md`는 상태 관리와 화면 이동 방식을 FE 리더가 정할 사항으로 두었고, 구조를 바꾸는 선택은 ADR로 남기도록 했다. 목 데이터 워킹 스켈레톤을 만들면서 두 가지를 함께 정해야 했다.

이 앱에는 선택에 영향을 주는 조건이 두 가지 있다.

- 목 데이터로 먼저 화면을 만들고 나중에 BE와 AI 결과로 교체한다. 교체할 때 화면 코드를 고치지 않아야 한다.
- 리포트 도착을 푸시 알림으로 알리고 알림에서 리포트 화면으로 바로 이동한다. 딥링크가 필요하다.

## 결정

상태 관리는 **Riverpod**, 화면 이동은 **go_router**를 사용한다.

| 항목 | 패키지 | 버전 |
| --- | --- | --- |
| 상태 관리 | `flutter_riverpod` | 3.4.3 |
| 화면 이동 | `go_router` | 18.0.1 |

**Riverpod을 고른 이유** — 화면은 provider만 보고, 그 provider가 목 데이터를 주는지 서버 응답을 주는지는 override로 바꾼다. 목 데이터에서 실제 연동으로 넘어갈 때 화면 코드를 건드리지 않아도 된다. 위젯 트리에 의존하지 않아 테스트에서 값을 갈아끼우기도 쉽다.

**go_router를 고른 이유** — 알림에서 리포트 화면으로 바로 여는 딥링크를 기본으로 지원한다. Navigator만으로 시작하면 딥링크가 필요해지는 시점에 화면 이동 구조를 다시 짜야 한다. Flutter 팀이 직접 관리하는 패키지라는 점도 고려했다.

**코드 생성(`riverpod_generator`, `build_runner`)은 지금 도입하지 않는다.** 빌드가 느려지는 비용에 비해 스켈레톤 단계에서 얻는 이득이 작다. 나중에 provider가 늘어나면 다시 판단한다.

## 검토한 대안

**상태 관리**

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| Provider | 가장 단순하고 자료가 많다 | 화면과 상태가 늘면 보일러플레이트가 빠르게 늘어난다 |
| BLoC | 상태 전이가 명시적이라 녹음 상태머신에 잘 맞는다 | 보일러플레이트가 가장 많다. 녹음 화면 하나 때문에 앱 전체를 이 방식으로 가는 것은 과하다 |

BLoC은 녹음 화면에 한정해 다시 검토할 수 있다.

**화면 이동**

| 대안 | 장점 | 채택하지 않은 이유 |
| --- | --- | --- |
| Navigator 1.0 | 추가 학습이 없다 | 딥링크와 백스택 복원을 직접 구현해야 한다. 알림에서 리포트로 이동하는 흐름에서 곧 한계가 온다 |
| auto_route | 타입 안전 | 코드 생성이 필요해 빌드가 느려진다. 코드 생성을 미루기로 한 판단과 어긋난다 |

## 영향

- 화면과 데이터 사이에 provider 계층이 생긴다. 화면은 저장소 구현을 직접 부르지 않는다.
- 목 데이터와 실제 데이터의 교체 지점이 provider override 한 곳으로 모인다.
- 화면 이동 경로를 한곳에 선언한다. 새 화면을 추가하면 경로도 함께 등록한다.
- 두 패키지가 `app/pubspec.yaml`의 의존성에 추가된다.

## 검증

- `flutter analyze`와 `flutter test`가 통과하는지 확인한다.
- 목 데이터를 provider로 읽어 화면에 표시하고, override로 다른 값을 주입했을 때 화면 코드 변경 없이 바뀌는지 확인한다.
- 알림에서 리포트 화면으로 여는 딥링크는 알림 기능을 붙이는 시점에 실제 기기에서 확인한다.

## 재검토 조건

- 녹음 화면의 상태 전이가 provider로 관리하기 어려울 만큼 복잡해지면 그 화면에 한해 BLoC 도입을 검토한다.
- provider 수가 늘어 수동 선언의 실수가 반복되면 코드 생성 도입을 다시 판단한다.
- `go_router`의 주요 버전이 올라가면서 경로 선언 방식이 바뀌면 이관 비용을 확인한다.
