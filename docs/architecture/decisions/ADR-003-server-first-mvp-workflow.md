# ADR-003: Python 서버 우선 MVP 워크플로

상태: proposed
담당: PM, BE, AI
결정일: 결정 대기
관련 Issue: 없음

## 배경

현재 아키텍처는 프로필, 전사문과 회차 기록의 단말 저장을 기본으로 하고, STT와 화자 처리도 단말 실행을 우선 검토한다. 이 방향은 실제 사용자 데이터의 외부 이동을 줄일 수 있지만, MVP 개발 초기부터 Flutter 로컬 저장소, 모바일 AI 런타임과 전체 처리 파이프라인을 함께 구현해야 한다.

초기에는 모델, 신뢰도 기준, 처리 단계와 공통 데이터 계약이 계속 바뀔 가능성이 높다. 이 상태에서 단말 구현까지 동시에 진행하면 AI와 BE가 파이프라인을 반복적으로 실행하고 수정하기 어렵고, FE도 확정되지 않은 로컬 인터페이스에 의존하게 될 수 있다.

## 제안

- MVP 개발과 검증에 사용하는 전체 워크플로의 기준 구현을 Python 서버에 둔다.
- 프로필 저장, 카드 생성, 녹음 입력, STT, 신뢰도 판정, 화자 처리, 대화 구조화, 리포트와 누적 문맥 생성을 서버에서 우선 연결한다.
- 개발과 평가에는 합성 자료 또는 사용 권한이 확인된 테스트 자료만 사용한다. 사용 권한과 공개 저장소 재배포 권한은 별도로 확인하며, 재배포 권한이 불명확한 원본은 Git에 저장하지 않는다.
- 개발용 테스트 데이터와 처리 결과는 MVP 파이프라인 검증을 위해 서버 개발 환경에서 관리할 수 있다.
- 실제 사용자 데이터의 기준 저장 위치, 데이터별 보유기간, 삭제 범위와 외부 처리 조건은 실제 사용자 검증을 시작하기 전에 별도 결정한다.
- 공통 데이터 계약은 서버 DB, HTTP와 특정 모델 형식에 종속되지 않게 정의한다. Flutter와 AI 구현은 버전이 있는 동일 계약을 사용한다.
- 핵심 흐름과 품질 기준이 안정된 뒤 대상 Android 단말에서 처리 시간, 메모리, 발열과 실패를 측정하고, 효과가 확인된 처리부터 단계적으로 로컬 구현으로 교체한다.
- 기존 ADR-001의 실제 사용자 원본 처리 경계와 동의 기준은 이 제안으로 완화하지 않는다.

이 ADR이 승인되기 전까지 기존 테크스펙과 영역별 README의 로컬 우선 기준은 유효하다.

## 검토한 대안

### 처음부터 단말에서 전체 처리

- 실제 사용자 데이터의 외부 이동을 최소화할 수 있다.
- Flutter 로컬 저장소, 모바일 모델 연동, 단말별 성능과 복구까지 동시에 해결해야 하므로 초기 종단 흐름 검증이 늦어질 수 있다.

### 서버와 단말 구현을 동시에 개발

- 두 실행 위치를 조기에 비교할 수 있다.
- 아직 안정되지 않은 계약과 모델을 두 번 구현하게 되어 현재 인력과 일정에서 중복 작업이 커질 수 있다.

### Python 서버 기준 구현 후 단계적 로컬 이전

- AI와 BE가 한 환경에서 모델과 파이프라인을 빠르게 반복 검증할 수 있다.
- 서버 구현이 저장소, HTTP 또는 외부 AI에 강하게 결합되면 이후 로컬 이전이 재개발이 될 수 있으므로 포트와 어댑터 경계가 필요하다.

## 영향

- BE는 Python API, 작업 상태, 저장소와 AI 실행을 분리한 서버 기준 파이프라인을 설계한다.
- AI는 STT, 화자 처리, 카드와 리포트 생성의 모델 입출력, 신뢰도와 실패 상태를 서버에서 먼저 검증한다.
- FE는 서버 구현 세부사항이 아니라 합의된 요청, 작업 상태와 결과 계약에 의존한다.
- QA는 합성 자료 또는 사용 권한이 확인된 자료로 정상, 저신뢰도, 처리 실패와 수동 검수 흐름을 검증한다.
- 서버 우선 방향이 승인되면 `docs/tech-spec.md`, `backend/README.md`, `local_ai/README.md`, 공통 데이터 계약과 필요한 법률 문서를 같은 변경에서 갱신한다.
- 실제 사용자 데이터를 처리하는 서버 구조는 동의, 인증, 암호화, 로그, 보유기간, 삭제와 외부 업체 조건을 확정한 뒤 도입한다.

## 검증

- 허가된 테스트 자료로 프로필 입력부터 카드와 리포트 생성까지 종단 흐름을 재현할 수 있어야 한다.
- STT와 화자 처리의 저신뢰도 결과를 정상 결과와 구분하고 수동 검수 상태로 반환해야 한다.
- 앱이나 처리 서버가 중단되어도 작업 상태와 재시도 가능 여부를 확인할 수 있어야 한다.
- 서버 모델과 저장소 구현을 교체해도 공통 요청 및 결과 계약이 유지되어야 한다.
- 로컬 이전 여부는 대상 단말의 처리 시간, 메모리, 발열, 정확도와 실패 결과를 기록한 뒤 판단한다.

## 재검토 조건

- 핵심 사용자 흐름의 서버 기준 구현과 평가 계약이 안정된 경우
- STT, 화자 처리와 생성 모델의 품질 및 실패 기준이 확정된 경우
- 대상 Android 단말 벤치마크 결과가 나온 경우
- 실제 사용자 자료를 이용한 검증을 시작하는 경우
- 프로필, 전사문, 리포트와 누적 문맥의 서버 보존 여부를 결정하는 경우
- 외부 STT, LLM 또는 이미지 분석 업체를 도입하는 경우
