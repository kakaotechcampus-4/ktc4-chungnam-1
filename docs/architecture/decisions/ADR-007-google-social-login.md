# ADR-007: 구글 소셜 로그인과 백엔드 ID 토큰 검증

상태: proposed
담당: BE, FE, PM
제안일: 2026-09-15 (BE 로그인 방식 제안, PM 개인정보 처리 검토안 추가, 공동 검토 대기)
관련 Issue: 미정
관계: [ADR-006](ADR-006-server-side-ai-processing.md)의 서버 중심 데이터 관리 가운데 인증과 계정 저장 부분을 구체화한다.

## 배경

`docs/architecture/data-contracts.md`의 결정 대기 항목에는 "계정 기능을 넣을지, 넣는다면 서버를 사용할지 정해지지 않았다"가 PM과 BE 몫으로 남아 있었다. 그동안 FE의 로그인 화면은 아이디와 비밀번호를 받는 목업이었고, `Account` 객체에도 `loginId` 필드가 있었다.

계정 기능은 리포트 기록을 회차에 걸쳐 같은 사용자에게 묶는 데 필요하다. 아이디와 비밀번호를 직접 받으면 비밀번호 저장, 재설정, 탈취 대응과 계정 복구를 모두 직접 만들어야 하고, 이는 12주 일정에서 감당할 범위를 넘는다. 새록이 다루는 자료가 건강 관련 민감정보를 포함하므로 자체 비밀번호 관리의 사고 비용도 크다.

작업 과정에서 Flutter 앱에 Firebase Auth를 붙이는 시도가 있었고 개발용 스키마 초안의 `users` 테이블도 `firebase_uid`를 신원 기준으로 잡고 있었다. Firebase를 쓰면 SDK와 Gradle 플러그인, 플랫폼 설정 파일(`google-services.json`)이 앱과 빌드에 들어오고, 구글 로그인 하나를 위해 Firebase 프로젝트와 SDK 전체에 의존하게 된다. 이 앱이 Firebase에서 필요한 기능은 구글 계정으로 사용자를 식별하는 것 하나뿐이다.

이 제안은 ADR-004의 첫 구현 범위 조항과 맞닿아 있다. ADR-004는 "첫 구현은 합성 데이터로 동작하는 상태 확인과 대화 카드 생성까지로 제한한다. 실제 인증, 데이터베이스, 사용자 기록 저장, 음성·이미지 업로드와 외부 AI 호출은 포함하지 않는다"고 적었고, 검증 항목에도 "첫 구현에 실제 계정 DB ... 경로가 없는지 확인한다"가 있다.

그 조항의 목적은 인증을 영구히 막는 것이 아니라, 검증용 로컬 FastAPI 환경이 운영 서버 도입이나 사용자 자료의 상시 서버 저장으로 확대 해석되지 않게 막는 것이다. ADR-004의 영향 절도 그 취지를 "운영 서버 도입이나 실제 사용자 데이터의 외부 전송 동의로 확대 해석되지 않도록"이라고 적고 있다. 계정 식별자와 동의 이력만 저장하는 인증은 이 취지를 깨지 않는다.

[ADR-006](ADR-006-server-side-ai-processing.md)이 AI 처리 위치와 데이터 관리 방향을 서버 중심으로 정하면서 ADR-003과 ADR-004의 온디바이스 병렬 검증 및 단말 우선 저장 방향은 대체됐다([PR 37](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/pull/37)에서 도입, develop 반영 전). ADR-004의 로컬 FastAPI 검증 원칙은 그대로 유지되므로, 이 문서는 ADR-006이 연 서버 중심 방향 가운데 인증과 계정 저장이라는 한 부분을 구체화한다.

## 결정

- 인증은 구글 소셜 로그인 한 가지를 사용한다. 자체 아이디와 비밀번호는 받지 않는다.
- Firebase Auth를 사용하지 않는다. 앱은 `google_sign_in`으로 구글 ID 토큰을 받고, 백엔드가 구글 공개키(JWKS)로 그 토큰을 직접 검증한다.
- 사용자 식별자는 `(provider, social_id)`다. `social_id`는 구글 계정의 `sub`이고 `provider`는 현재 `google` 하나다. 내부 기본키는 `users.user_id` UUID를 유지한다.
- PM 제안: 계정 정보 가운데 `user_id`, `provider`, `social_id`와 필수 동의 이력만 서버 데이터베이스에 저장하는 방향이 적절하다고 본다. 이메일과 구글 계정 이름은 현재 로그인 목적에 사용하거나 영구 저장하지 않는 안을 제안한다. BE와 FE가 추가 항목의 필요성과 구현 영향을 확인한 뒤 저장 범위를 확정한다. 계정과 동의 이력 밖의 데이터는 ADR-006의 서버 중심 데이터 관리를 따르며, 데이터별 저장 범위와 보관 기간은 이 문서에서 정하지 않는다.
- 구글 인증에 성공한 뒤 계정 생성에 필요한 필수 동의를 받고, 동의가 완료되면 계정과 동의 이력을 함께 저장한다. 동의를 거부하거나 중단하면 영구 계정을 만들지 않는다.
- ID 토큰은 백엔드 검증에만 사용하고 검증 후 폐기한다. 데이터베이스, 로그, 예외 메시지와 오류 응답에 저장하지 않는다.
- `Account` 계약에서 `loginId`를 없애고 `authProvider`를 넣는다. 구글 `sub`와 ID 토큰은 공통 데이터 계약에 포함하지 않는다.
- 백엔드가 발급하는 세션의 형식, 수명과 갱신 방식은 이 ADR에서 정하지 않는다. BE가 구현 전에 정하고 이 문서에 추가한다.
- ADR-004의 로컬 FastAPI 기준 환경과 공통 데이터 계약 검증 원칙은 그대로 유지한다. 실제 인증과 계정 저장은 ADR-004의 첫 구현 범위 조항이 아니라 ADR-006과 이 문서를 따른다.
- 이 문서가 정하는 서버 저장 범위는 계정과 동의 이력까지다. 프로필, 생애 사실, 전사문, 회차와 리포트의 서버 저장 항목, 단말 보관 여부와 보관 기간은 ADR-006에 따라 BE가 정리하고 FE, AI와 PM이 함께 확인한다.
- 음성과 이미지 원본의 임시 처리, 즉시 삭제와 최대 24시간 제한은 ADR-001과 ADR-006을 그대로 따르며 이 문서에서 바꾸지 않는다.
- ADR-004의 상태는 이 문서에서 바꾸지 않는다. 온디바이스 병렬 검증과 단말 우선 저장 방향은 이미 ADR-006이 대체했고, 남은 로컬 FastAPI 검증 원칙은 계속 유효하다.

## 검토한 대안

### 자체 아이디와 비밀번호

- 외부 제공자에 의존하지 않고 계정 정보가 프로젝트 안에만 남는다.
- 비밀번호 해시, 재설정, 잠금, 복구와 유출 대응을 직접 만들어야 한다. 민감정보를 다루는 서비스에서 이 구현의 사고 비용이 크고 12주 일정에 맞지 않는다.

### Firebase Auth를 통한 구글 로그인

- 토큰 검증, 세션 갱신과 계정 연동을 SDK가 처리하므로 백엔드 구현이 줄어든다.
- 구글 계정 식별 하나를 위해 앱에 Firebase SDK, Gradle 플러그인과 플랫폼 설정 파일이 들어온다. 앱이 필요로 하지 않는 기능까지 의존성에 포함된다.
- 사용자 식별자가 Firebase가 발급하는 `uid`가 되어 신원 기준이 외부 서비스에 묶인다. 나중에 Firebase를 걷어내면 기존 계정과의 연결이 끊긴다.
- 인증 경로에 구글 외에 Firebase라는 처리 주체가 하나 더 생기므로 개인정보 처리 문서에 기재할 대상이 늘어난다.

### 구글 ID 토큰을 백엔드가 직접 검증

- 앱은 `google_sign_in`만 의존하고 Firebase SDK, Gradle 플러그인과 플랫폼 설정 파일이 필요 없다.
- 사용자 식별자가 구글 `sub`이므로 신원 기준이 제공자 안에 남고 중간 서비스에 묶이지 않는다.
- 백엔드가 JWKS 조회와 캐시, 토큰 검증(서명, `aud`, `iss`, 만료)과 세션 발급을 직접 구현해야 한다. 표준 라이브러리로 처리할 수 있는 범위이며 검증 규칙이 명시적으로 드러난다.

위 이유로 세 번째 대안을 선택한다.

## 영향

- BE는 ID 토큰 검증(서명, `aud`, `iss`, 만료), 계정 생성과 조회, 세션 발급과 갱신, 실패 시 오류 코드를 구현한다. 검증에 실패한 토큰을 성공으로 처리하는 대체 경로를 만들지 않는다.
- `backend/database/init.sql`은 이 PR에 없다. 개발용 부트스트랩 스키마는 [PR 39](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/pull/39)에서 다루며 `users`를 `firebase_uid` 없이 `(provider, social_id)` 기준으로 만든다. 스키마 소유권은 Alembic 마이그레이션에 있으므로 마이그레이션을 같은 기준으로 맞추는 일은 후속 작업이다.
- FE는 `app/lib/features/auth/login_screen.dart`의 아이디와 비밀번호 입력을 구글 로그인으로 바꾸고 `signup_screen.dart`의 위치를 다시 정한다. 이 작업은 FE 리더 영역이며 이 ADR에 포함하지 않는다.
- FE와 BE는 `Account`의 `loginId` 제거와 `authProvider` 추가를 공통 검토한다. `docs/architecture/data-contracts.md`의 변경 절차는 `Account`의 필드 이름을 FE, AI와 BE가 함께 확인하도록 요구한다.
- PM 제안의 검토 항목: 구글 계정 식별자 `sub`로 동일 계정을 식별하고, 이메일과 구글 계정 이름은 실제 구현에서 반환되더라도 사용하지 않고 로그인 처리 후 폐기할 수 있는지 BE와 FE가 확인한다. 추가 저장이 필요하면 목적과 이유를 함께 검토한다.
- 구글은 자체 계정을 인증하는 외부 인증 제공자다. 현재 로그인 흐름에는 새록이 보유한 개인정보를 구글에 전달하는 단계가 없으므로 새록의 구글 제3자 제공, 처리위탁 또는 국외 이전으로 분류하지 않는다. 실제 구현이나 계약 조건이 이 흐름과 다르면 운영 전에 PM이 다시 판단한다.
- `docs/legal/README.md`, `consent-draft.md`와 `consent-mapping.md`에 수집 항목, 처리 목적, 보관 기간, 삭제 절차와 위 판단을 기록한다.
- 이 문서는 `proposed`이며 BE 리더 단독으로 확정하지 않는다. ADR-006의 서버 중심 데이터 관리와 함께 읽고 PM, BE와 FE가 같은 검토에서 확정한다.
- 이 제안이 받아들여지지 않으면 구글 로그인 구현을 미루고, 그때까지 개발용 스키마의 계정 테이블을 적용하지 않는다.
- 안드로이드 OAuth 클라이언트는 패키지명 `com.saelog.app`과 서명 인증서 SHA-1을 Google Cloud Console에 등록해야 동작한다. 디버그 키와 릴리스 키의 SHA-1이 다르므로 둘 다 등록한다.
- 클라이언트 ID는 비밀이 아니지만 저장소에 자격증명 파일을 두지 않는다. `.gitignore`의 `client_secret_*.json`과 서비스 계정 키 규칙을 유지한다.

## 검증

계정 저장 항목과 동의 후 계정 생성에 관한 아래 항목은 PM 제안이 채택될 경우의 검증안이다. 현재 구현 완료나 팀 합의를 뜻하지 않는다.

- 허용된 개발 계정으로 앱에서 구글 로그인을 수행하고 백엔드가 ID 토큰 검증에 성공한 뒤 필수 동의를 완료해야 계정이 만들어지는지 확인한다.
- 같은 계정으로 다시 로그인했을 때 새 계정이 생기지 않고 `(provider, social_id)`로 기존 계정을 찾는지 확인한다.
- 서명이 잘못된 토큰, 만료된 토큰, `aud`가 다른 토큰이 각각 명시적인 오류 코드로 거부되는지 확인한다. 어느 경우에도 계정이 만들어지지 않아야 한다.
- 구글 JWKS 조회가 실패했을 때 검증을 건너뛰고 통과시키는 경로가 없는지 확인한다.
- 필수 동의를 거부하면 계정 생성이 진행되지 않는지 확인한다.
- ID 토큰, `sub`, 이메일, 구글 계정 이름과 세션 값이 데이터베이스의 허용되지 않은 필드, 로그, 예외 메시지와 오류 응답에 남지 않는지 확인한다.
- `app/`의 의존성과 빌드 설정에 Firebase SDK와 Gradle 플러그인이 남아 있지 않은지 확인한다.
- 실제 사용자 계정이 아닌 개발용 계정으로만 검증하고 결과에 계정 식별자를 남기지 않는다.

## 재검토 조건

- 구글 외의 제공자를 추가하는 경우
- 계정 삭제와 탈퇴 시 서버와 단말 자료의 삭제 범위를 변경하는 경우
- 세션 형식, 수명 또는 갱신 방식을 정하거나 바꾸는 경우
- ADR-006의 데이터별 저장 계약이 정해져 계정과 동의 이력의 저장 범위를 맞춰야 하는 경우
- 한 계정을 여러 단말에서 함께 사용해야 하는 경우
- 구글이 ID 토큰 검증 방식이나 `google_sign_in`의 인증 흐름을 바꾸는 경우
- 개인정보 처리 문서 검토에서 수집 항목이나 보관 기간을 바꿔야 하는 경우
