# ADR-008: 면회 음성의 비동기 STT 및 리포트 처리

상태: proposed
담당: BE, FE, AI, PM
제안일: 2026-09-25
관계: [ADR-001](ADR-001-consent-and-temporary-processing.md)의 원본 임시 처리와
[ADR-006](ADR-006-server-side-ai-processing.md)의 서버 측 AI 실행을 구체화한다.

## 배경

Flutter 앱은 면회가 끝나면 WAV 녹음을 닫고 보호자에게 참여자 수를 확인받는다.
이후 홈으로 이동해 해당 면회의 타일에 `리포트를 만들고 있어요` 상태를 표시하고,
STT와 리포트 생성이 끝나면 완성된 리포트로 바꾸는 화면 흐름을 사용한다.

현재 백엔드의 `POST /api/v1/speech-analyses`는 이미 S3에 있는 음성의 Presigned
GET URL을 받아 AI 서버의 동기 API를 호출하고 최종 `SpeechAnalysisResult`를 바로
반환한다. 이 호출의 기본 대기 설정은 600초다. 이를 앱까지 그대로 연결하면 앱의
HTTP 요청도 GPU 처리가 끝날 때까지 완료되지 않는다. 모바일 네트워크나 프록시가
먼저 연결을 끊으면 AI 처리가 끝나도 앱이 결과를 다시 찾을 수 없다.

또한 S3 업로드, 참여자 수 전달, 작업 상태 영속화, 중복 방지, 원본 삭제 확인과
홈 타일용 상태 조회가 현재 구현에 없다.

## 결정

### 처리 경계

- 앱에서 백엔드로 보내는 공개 API는 비동기 작업 제출 방식으로 제공한다.
- 제출 요청은 인증, 회차 접근 권한과 동의를 확인하고 WAV를 S3에 임시 저장한 뒤
  작업을 PostgreSQL에 영속화한 시점에 `202 Accepted`를 반환한다.
- `202`는 STT나 리포트 생성을 완료했다는 뜻이 아니다. 서버가 작업 수행에 필요한
  원본과 작업 상태를 안전하게 인수했다는 뜻이다.
- BE 작업자는 작업을 가져와 기존 AI 서버의 동기
  `POST /internal/v1/speech-analyses`를 호출한다. AI 서버 API를 이번 결정 때문에
  비동기 API로 바꾸지 않는다.
- 앱은 작업 또는 면회 상태를 다시 조회해 홈 타일을 갱신한다. 첫 구현은 폴링과
  앱 활성화 시 새로고침을 사용하며 웹소켓과 푸시는 범위에 넣지 않는다.

```text
FE ── WAV + participantCount ──▶ BE 제출 API
                                   ├─ 인증·동의·WAV 검증
                                   ├─ S3 임시 업로드
                                   ├─ 작업 DB 저장
FE ◀──── 202 + analysisId ─────────┘

BE worker ── Presigned GET + speakerCount ──▶ AI 동기 API
          ◀──────── SpeechAnalysisResult ────┘
          ├─ S3 원본 삭제
          ├─ 리포트 생성 단계 실행
          └─ 작업·회차·리포트 상태 갱신

FE ── 상태 조회 ──▶ BE
FE ◀─ processing | completed | failed
```

### 공개 API

작업 제출은 다음 형태를 기준으로 한다.

```http
POST /api/v1/visit-sessions/{sessionId}/speech-analyses
Authorization: Bearer <accessToken>
Content-Type: multipart/form-data

audio=<WAV file>
participantCount=2
```

성공 응답은 다음과 같다.

```http
HTTP/1.1 202 Accepted
```

```json
{
  "schemaVersion": 1,
  "analysisId": "analysis_123",
  "sessionId": "session_123",
  "status": "queued"
}
```

작업 조회는 `GET /api/v1/speech-analyses/{analysisId}`를 사용한다. 작업은 요청한
계정이 소유한 면회에 속해야 하며 다른 계정의 작업은 반환하지 않는다. 홈의 면회
목록 API는 같은 상태를 타일용 요약에 포함할 수 있다.

### 상태와 화면 의미

내부 작업 상태는 다음 전이만 허용한다.

```text
uploading → queued → transcribing → sttCompleted
                                      └→ generatingReport → completed
                └─────────────── 실패 ─────────────────▶ failed
```

- `uploading`은 제출 요청 내부 상태다. 앱에는 `202`로 반환하지 않는다.
- `queued`, `transcribing`, `sttCompleted`, `generatingReport`는 홈에서
  `리포트를 만들고 있어요`로
  표시할 수 있다.
- `completed`는 리포트가 준비됐다는 뜻이다. STT만 끝난 상태를 완료로 표시하지
  않는다.
- `failed`는 정상 결과가 아니다. 안전한 `errorCode`만 저장하고 음성, 전사문과
  AI 오류 본문은 저장하거나 응답하지 않는다.
- `VisitSession.sessionStatus`는 작업 접수 후 `processing`, 리포트 준비 후
  `completed`, 최종 실패 후 `failed`로 맞춘다.
- `VisitReport.reportStatus`는 생성 중 `generating`, 준비 후 `ready`로 맞춘다.

### 참여자 수와 입력 검증

- 앱이 보호자에게 확인받은 `participantCount`만 사용하며 서버나 AI가 인원수를
  추측하지 않는다.
- 허용 범위는 1명 이상 8명 이하이며 BE가 검증한다.
- BE는 이 값을 AI 요청의 `speakerCount`로 이름만 바꾸어 전달한다.
- 입력 음성은 WAV/PCM 16-bit/16kHz/mono로 제한한다. 파일명과 Content-Type만
  신뢰하지 않고 WAV 헤더를 검사한다.
- 업로드 크기 상한은 서버 설정으로 두고 BE와 AI의 상한을 같게 운영한다.

### 저장, 중복 방지와 작업 실행

- S3 객체 키에는 사용자 이름, 프로필 정보, 원래 파일명과 전사 내용을 넣지 않고
  무작위 `analysisId`만 사용한다.
- 버킷은 비공개로 두고 서버 측 암호화를 적용한다. AI에는 수명이 제한된 Presigned
  GET URL만 전달한다.
- 한 면회에는 하나의 활성 음성 분석 작업만 허용한다. `sessionId` 고유 제약과
  작업 생성 트랜잭션으로 중복 버튼 입력 및 동일 요청 재전송을 막는다.
- 작업은 PostgreSQL에 저장하고 별도 worker가 임대 방식으로 가져간다. 여러 worker가
  같은 작업을 처리하지 않도록 행 잠금과 lease 만료 시각을 사용한다.
- FastAPI 프로세스 내부의 `BackgroundTasks`만을 작업 큐로 사용하지 않는다. 서버
  재시작 시 작업이 사라지고 홈에서 상태를 복구할 수 없기 때문이다.
- 첫 구현의 자동 재시도 상한은 0회다. 실패를 숨겨 반복 처리하지 않고 `failed`로
  기록한다. 자동 재시도, 사용자 재시도와 취소 API는 실패 유형 및 GPU 운영 기준을
  공동 검토한 뒤 추가한다.

### 원본과 전사 결과 수명

- BE는 AI가 STT 결과를 반환한 직후 S3 음성 원본 삭제를 시도한다. 리포트 확인이나
  사용자 승인까지 원본을 보관하지 않는다.
- 정상 경로의 즉시 삭제와 별도로 S3 Lifecycle을 두어 어떤 경우에도 업로드 후
  24시간을 넘지 않게 한다. `dataExpiresAt`은 이 최종 삭제 기한이다.
- 삭제 실패는 성공으로 숨기지 않으며, 원본 내용과 객체 URL을 제외한 삭제 상태를
  운영 확인 대상으로 남긴다.
- AI 서버가 다운로드한 임시 파일은 요청 종료 시 삭제한다.
- 전사문은 화면에 직접 표시하지 않고 리포트 생성 입력으로만 사용한다. 첫 구현은
  worker 메모리에서 다음 단계로 전달하며 DB에 원문 전사를 영구 저장하지 않는다.
  장애 복구를 위해 전사문 저장이 필요해지면 암호화, 접근 권한, 보관 기간과 삭제
  조건을 별도 합의하고 이 ADR과 법률 문서를 갱신한다.
- 앱의 로컬 WAV는 서버가 `202`로 작업을 인수한 뒤 삭제할 수 있다. `202`를 받지
  못한 경우에는 재전송을 위해 유지하되 단말 보관 및 정리 정책은 FE 문서에서 정한다.

### 리포트 생성 경계

- STT 성공은 리포트 완료가 아니다. worker는 검증된 `SpeechAnalysisResult`를 리포트
  생성 서비스에 넘기고 리포트가 저장된 뒤에만 작업을 `completed`로 바꾼다.
- 리포트 생성기가 연결되지 않은 STT 통합 단계에서는 원본 삭제와 AI 응답 검증 후
  `sttCompleted`에서 멈춘다. 이 상태를 리포트 완료로 표시하지 않는다.
- 현재 리포트 생성 모델과 입력 계약은 확정되지 않았다. BE는 작업 단계와 호출
  인터페이스를 마련하되 확인되지 않은 요약이나 의료적 해석을 임의로 생성하지 않는다.
- 리포트 생성 계약이 연결되기 전에는 해당 단계가 완료된 것처럼 응답하지 않는다.

## 검토한 대안

### 앱 요청이 끝날 때까지 STT 결과를 기다리는 방식

구현이 단순하고 현재 BE-AI 동기 호출을 그대로 공개할 수 있다. 그러나 모바일 연결,
프록시 타임아웃과 GPU 대기시간에 결과 전달 여부가 종속되며, 연결이 끊긴 후 결과를
다시 조회할 식별자와 상태가 없다. 홈의 처리 중 타일 흐름과도 맞지 않아 채택하지
않는다.

### FastAPI BackgroundTasks만 사용하는 방식

별도 worker가 없어 초기 구현은 간단하다. 그러나 API 프로세스 재시작과 배포 때 작업이
유실되고, 여러 프로세스에서 중복 실행을 제어하기 어렵다. 민감한 원본의 삭제 작업도
복구할 수 없으므로 채택하지 않는다.

### 앱이 S3에 직접 업로드하는 방식

BE의 대용량 파일 중계를 줄일 수 있다. 반면 Presigned PUT 발급, 업로드 완료 통지와
미완료 객체 정리 계약이 추가되고 현재 합의한 `앱 → BE → S3` 흐름을 바꾼다. 이번
범위에서는 채택하지 않으며 업로드 병목이 측정되면 재검토한다.

## 영향

- FE는 녹음 업로드가 `202`로 접수된 뒤 홈으로 이동하고, 처리 중·완료·실패 상태를
  조회해 타일에 반영한다.
- BE는 인증·동의 확인, WAV 검증, S3 임시 저장, 작업 영속화, worker, 상태 조회,
  중복 방지와 원본 삭제 확인을 구현한다.
- AI는 기존 동기 API를 유지하고 `speakerCount`, URL 만료, 파일 크기·SHA-256과 WAV
  규격을 검증한다. 입력 오류와 일시 장애의 오류 계약은 BE와 함께 정리한다.
- PM과 법률 담당은 제3자 목소리가 포함된 녹음, 전사문의 임시 처리와 단말 원본 보관
  문구를 검토한다.
- 이 문서는 `proposed`이며 구현은 합성 자료로 계약과 실패 흐름을 검증하는 범위다.
  실제 사용자 자료 전송 승인을 뜻하지 않는다.

## 검증

- 합성 WAV만 사용해 업로드 후 `202`와 작업 식별자가 반환되는지 확인한다.
- `202` 반환 전에 S3 업로드와 작업 저장이 완료되는지 확인한다.
- 앱 연결이 끝난 뒤에도 worker가 STT를 수행하고 상태 조회로 결과를 확인할 수 있는지
  검사한다.
- 같은 면회 제출을 반복해도 활성 작업과 S3 원본이 중복 생성되지 않는지 확인한다.
- 참여자 수 누락·범위 초과, WAV 위장 파일, 손상 파일과 크기 초과를 거부한다.
- 인증, 회차 소유권, 필수 동의와 녹음 허가가 없으면 업로드를 시작하지 않는다.
- AI 성공, 입력 오류, 서버 오류와 타임아웃에서 상태 전이와 `retryable` 의미를 검사한다.
- 성공과 실패 경로에서 S3 삭제를 확인하고 Lifecycle이 24시간 상한을 보장하는지
  운영 설정을 별도로 확인한다.
- 음성, 전사문, Presigned URL과 원래 파일명이 로그, 오류 응답과 작업 테이블에 남지
  않는지 확인한다.
- worker 종료 후 lease가 만료된 작업의 복구 방식은 자동 재시도 정책을 정할 때 함께
  검증한다. 첫 구현은 자동으로 재실행하지 않는다.
- worker를 `--once`로 실행해 실제 S3·AI 요청 하나가 `sttCompleted`가 되는지 확인한다.

## 재검토 조건

- 업로드 시간이 화면 전환 기준을 충족하지 못해 앱의 백그라운드 업로드나 S3 직접
  업로드가 필요한 경우
- GPU 동시 처리량과 대기시간을 측정해 자동 재시도, 우선순위 또는 취소가 필요한 경우
- 전사문을 장애 복구나 품질 개선 목적으로 저장해야 하는 경우
- 리포트 생성 서비스의 입력·출력과 실패 계약이 확정되는 경우
- 웹소켓 또는 푸시 알림으로 상태 전달 방식을 바꾸는 경우
- 원본 또는 파생 데이터의 보관 기간과 처리 목적이 바뀌는 경우
