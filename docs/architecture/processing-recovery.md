# 작업 중단과 실패 후 복구 기준

상태: 검토 중 (`proposed`)

작성일: 2026-10-10

검토: PM, BE, FE, AI

녹음 전송, STT와 리포트 생성에서 작업이 끊겼을 때 저장된 결과를 확인하고 실패한 단계부터 이어 처리하는 기준을 제안합니다. 멘토가 요청한 worker 정상 종료, 중단 작업의 재처리와 사용자 재제출 범위를 함께 다룹니다.

- 보호자 소감 저장 후 녹음을 제출하고, 전사와 소감이 준비된 뒤 리포트를 만드는 기존 순서는 유지합니다.
- 자동 재시도 1회는 검토 제안입니다. 이 문서의 게시나 병합이 구현 완료를 뜻하지 않습니다.
- 녹음과 전사문의 삭제 시점, 보관 기간과 사용자 삭제 범위는 별도 보관 기준에서 정합니다. 이 문서는 해당 정책을 변경하지 않습니다.
- 구체적인 API, DB 필드와 종료 시간 설정은 담당자가 검토합니다. 기존 JSON과 enum을 이 문서만으로 바꾸지 않습니다.

## 1. 정상 완료와 실패 상황

아래는 구현 목표입니다. 화면 문구는 의미를 확인하기 위한 예시이며 FE에서 기존 화면에 맞게 다듬습니다. 자료를 재사용하는 모든 경로에는 소유권, 처리 동의와 별도 보관 기준을 만족하는 자료가 실제로 남아 있어야 합니다.

| 상황 | 처리 방법 | 앱에서 보여줄 내용과 사용자 행동 |
| --- | --- | --- |
| 정상 완료 | 전사와 보호자 소감으로 만든 리포트 및 해당 변경 제안이 정상 저장되고 조회되는지 확인한 뒤 완료로 표시한다. 녹음 접수나 STT 성공만으로 완료 처리하지 않는다. | 완료된 리포트를 연다. 앱을 다시 켜도 같은 결과를 조회한다. |
| 녹음 전송 전 앱 종료 | 기존 면회와 기기 녹음 파일을 다시 찾고 재생 및 형식을 검사한다. 이미 닫힌 정상 파일은 제출을 이어갈 수 있다. 녹음 도중 종료됐다면 복구 가능한 구간이 있는지 확인하고, 일부 파일을 전체 녹음인 것처럼 제출하지 않는다. | 남아 있는 녹음을 확인하고 제출한다. 일부만 남았다면 길이와 누락 사실을 먼저 안내한다. 복구할 수 없는 경우에만 다시 녹음이 필요하다고 알린다. |
| 보호자 소감 저장 실패 또는 응답 끊김 | 서버의 저장 여부를 먼저 확인한다. 저장돼 있으면 녹음 제출로 이어가고, 없으면 같은 면회에 소감만 다시 제출한다. 소감 저장 전에는 녹음을 제출하지 않는다. | 저장 실패를 안내하고 소감 제출을 다시 시도한다. 앱에 남아 있는 입력을 다시 작성하게 하지 않는다. |
| 녹음 전송 실패 또는 접수 응답 끊김 | 같은 면회에 접수된 작업이 있는지 먼저 조회한다. 접수됐다면 기존 작업을 조회하고, 미접수가 확인되면 기기 파일로 다시 전송한다. 상태 조회도 실패하면 접수 여부를 모르는 상태로 안내하고 중복 전송하지 않는다. | 미접수이면 `녹음 다시 보내기`, 접수됐다면 처리 상태를 표시한다. 소감은 다시 제출하지 않는다. |
| 배포로 worker 정상 종료 요청 | 새 작업을 가져오지 않고 진행 중인 작업을 종료 유예 시간 안에서 마친다. 강제 종료되거나 시간 안에 마치지 못하면 아래 중단 작업 복구로 넘긴다. 무한정 기다리지 않는다. | 앱은 기존 작업을 계속 조회한다. 배포만을 이유로 녹음을 다시 보내게 하지 않는다. |
| STT 도중 worker 중단 또는 일시적인 통신 오류 | 서버가 기존 실행의 유효성을 확인한 뒤 실패한 실행을 무효화한다. 사용 가능한 서버 녹음이 있으면 같은 면회의 STT를 다시 실행한다. 없으면 기기 파일의 재제출 가능 여부를 확인한다. | 자동 재처리 중이면 처리 중으로 표시한다. 자동 재처리가 끝내 실패하면 가능한 경우에만 다시 처리하거나 녹음을 다시 보내는 선택을 제공한다. |
| STT 결과를 받았지만 전사문 저장 실패 | 전사문이 실제 저장됐는지 먼저 확인한다. 메모리에 유효한 결과가 남아 있으면 저장을 다시 시도한다. 결과를 잃었으면 사용 가능한 녹음으로 STT를 다시 실행한다. 저장 전 결과를 저장 완료로 표시하지 않는다. | 전사 결과 저장이 지연됐음을 안내한다. 새 녹음이 필요한지 여부는 남아 있는 자료를 확인한 뒤 판단한다. |
| 전사문 저장 후 리포트 생성 또는 저장 실패 | 같은 면회의 전사문, 소감과 카드 정보를 사용한다. 리포트가 이미 저장됐으면 재생성하지 않고 작업 상태를 정리한다. 저장되지 않았으면 유효한 생성 결과를 저장하거나 리포트만 다시 생성한다. STT를 반복하지 않는다. | `리포트 다시 만들기`를 제공한다. 녹음과 소감을 다시 제출하라고 안내하지 않는다. |
| 처리 중 앱 종료 또는 상태 조회 실패 | 앱이 다시 켜지면 기존 면회의 서버 상태를 조회한다. 조회 실패를 서버 작업 실패로 바꾸지 않는다. 접수 응답을 놓쳐 작업 ID가 없더라도 면회에서 작업을 다시 찾을 수 있어야 한다. | `진행 상태를 확인하지 못했어요`와 새로고침을 제공한다. 서버 처리가 끝났다면 리포트를 연다. |
| 파일 손상, 규격 오류 또는 잘못된 AI 응답 | 같은 입력으로 반복해도 해결되지 않는 오류는 자동 재시도하지 않는다. 파일 문제는 정상 파일 재제출 가능 여부를 확인하고, 잘못된 AI 응답은 담당자가 원인을 확인한다. 잘못된 결과를 정상 자료로 저장하지 않는다. | 전송, 전사 또는 리포트 중 실패한 단계를 알린다. 서버의 응답 오류를 이유로 사용자에게 무조건 다시 녹음하라고 하지 않는다. |
| 재처리에 필요한 자료가 없음 | 리포트 재처리에는 전사문이, STT 재처리에는 정상 녹음이 필요하다. 어느 쪽도 사용할 수 없으면 재처리를 멈추고 기존 면회와 소감의 조회는 유지한다. 별도 삭제 요청으로 이미 제거된 기록은 복원하지 않는다. | 자료가 없어 이 면회의 리포트를 만들 수 없다고 안내한다. 존재하지 않는 자료에 `다시 시도` 버튼을 제공하지 않는다. |

## 2. 자동 재시도와 사용자 재시도

멘토는 복구 방식의 선택을 요청했으며 횟수를 지정하지 않았습니다. 아래 횟수는 이번 검토안의 제안입니다. 일시 장애를 한 번 넘길 기회를 주되 같은 오류로 GPU 작업과 대기 시간이 계속 늘어나지 않도록 제한합니다.

- 자동 재시도는 일시적인 통신 오류와 worker 중단에 한해 음성 분석 작업 전체에서 최초 실행 외 1회로 제한하는 안을 제안합니다. STT와 리포트 단계마다 횟수를 새로 주거나 worker 재시작으로 횟수를 초기화하지 않습니다.
- 자동 재시도 상한을 넘으면 실패한 단계와 사용 가능한 수동 재시도를 안내합니다. 사용자가 다시 시도하더라도 자동 재시도 횟수는 초기화하지 않습니다.
- 처리 중인 작업에는 사용자 재시도를 동시에 시작하지 않습니다. 서버가 같은 면회에 활성 작업 하나만 허용하고 연속 클릭과 중복 요청을 차단합니다.
- 녹음이나 전사문이 남아 있다는 사실만으로 재처리하지 않습니다. 재시도할 때도 권한, 처리 동의, 자료의 유효성과 별도 보관 기준을 확인합니다.
- 파일 손상과 규격 오류는 입력을 바로잡은 뒤, 인증 오류는 재인증 뒤, 서버 설정과 AI 응답 계약 오류는 담당자가 원인을 수정한 뒤 처리합니다. 모든 오류에 같은 재시도 버튼을 붙이지 않습니다.
- 정상 완료된 리포트를 새 내용으로 다시 만드는 기능은 이번 실패 복구 범위에 포함하지 않습니다.
- 손상된 녹음 파일을 복원하는 별도 도구나 여러 조각을 자동으로 합치는 기능도 추가하지 않습니다. 기기에 남은 파일의 사용 가능 여부를 확인하고 기존 면회에 다시 연결하는 범위입니다.

## 3. 중복 처리와 늦게 도착한 결과

- worker가 응답하지 않아 다른 실행으로 넘길 때는 실행별 식별자 또는 동등한 검증으로 이전 실행이 결과를 저장하지 못하게 합니다. 구체적인 필드와 잠금 방식은 BE가 제안합니다.
- 이전 실행에서 늦게 도착한 성공 또는 실패 응답이 새 실행의 상태와 결과를 덮어쓰지 못하게 합니다.
- STT 응답이 늦게 도착해도 현재 유효한 실행인지 확인하기 전에는 전사문 저장이나 자료 삭제를 수행하지 않습니다.
- 리포트가 저장된 직후 worker가 멈춘 경우에는 저장 결과부터 확인합니다. 이미 있는 리포트와 제안을 중복 생성하지 않습니다.
- 복구를 위해 새 면회를 만들지 않습니다. 같은 면회에서 재시도하며, 분석 작업과 시도 이력을 연결하는 방식은 BE가 기존 DB 제약에 맞춰 정합니다.

## 4. 카드 생성 실패

카드 생성은 녹음 분석과 다른 작업입니다. #107에서 요구한 카드 생성 실패 검사도 다음 범위로 연결합니다.

- 생성 요청의 응답이 끊기면 기존 카드 작업을 조회하고, 이미 실행 중이거나 완료된 요청을 중복 생성하지 않습니다.
- 카드 생성이 실패하면 저장된 프로필과 확인된 이야기를 다시 입력하게 하지 않고 카드 생성만 재요청합니다.
- 잘못된 질문이나 근거를 정상 카드로 저장하지 않습니다. 실패한 새 묶음을 완료로 표시하거나 이미 사용한 카드 묶음으로 조용히 대체하지 않습니다.
- 기존 카드와 면회 기록은 새 카드 생성 실패 때문에 변경하지 않습니다.
- 카드 생성의 별도 자동 재시도 횟수는 이번 음성 분석의 1회 제안을 그대로 적용하지 않습니다. 기존 카드 재요청 경로와 담당 구현에서 검토합니다.
- 최초 카드 생성 조건, 추천 알고리즘과 정보 부족 시 일반 질문 제공 여부는 이 복구 문서에서 새로 정하지 않습니다.

## 5. 보관 기준 PR과의 관계

이 PR은 어떤 자료를 얼마 동안 남길지 정하지 않습니다. 기기 녹음을 서버 접수 후 지울지, 전사문 저장 후 지울지와 전사문을 면회 기록과 함께 보관할지는 별도 보관 기준 PR의 검토 대상입니다. 기존 기간을 이 문서에서 재확정하거나 새로운 기간으로 바꾸지 않습니다.

복구 구현이 지켜야 할 조건은 다음과 같습니다.

- 필요한 자료가 정책상 사용 가능하고 실제로 남아 있을 때만 재처리합니다. 보관 기한을 재시도로 임의 연장하지 않습니다.
- 전사문을 저장한 것으로 표시하려면 DB 저장과 해당 면회 연결이 확인돼야 합니다. 녹음이 없고 전사문도 저장되지 않았다면 리포트 재처리가 가능하다고 표시하지 않습니다.
- 현재 실패 처리에서 전사문을 지우는 동작과 녹음을 지운 뒤 전사문을 저장하는 순서는 복구 가능 여부에 영향을 줍니다. 이 부분은 별도 보관 기준과 맞춰 수정한 뒤 재처리 가능 여부를 검증해야 합니다.
- 별도 보관 기준에서 필요한 자료를 사용할 수 있도록 정리되기 전에는 서버 녹음 재처리, 전사문을 사용한 리포트 재생성과 기기 파일 재제출이 항상 가능하다고 안내하지 않습니다. 조회 복원, 중복 방지와 정상 종료 준비는 먼저 진행할 수 있습니다.
- 사용자가 삭제를 요청했거나 처리 동의를 철회한 자료는 복구를 이유로 다시 처리하지 않습니다. 삭제 대상과 처리 절차 자체는 별도 기준에서 정합니다.

보관 기준이 확정되면 정본 링크만 연결하고 이 문서에 삭제 규칙을 복사하지 않습니다. 보관 기간과 삭제 정책, 법률 및 동의 문서 정리는 별도로 검토합니다.

## 8. 구현 후 확인할 항목

- [ ] 정상 처리에서 리포트 저장 후에만 완료로 표시되고 앱 재실행 후 같은 결과가 열린다.
- [ ] 소감 저장 응답과 녹음 접수 응답을 각각 끊어도 기존 저장 및 접수 결과를 찾아 중복 제출하지 않는다.
- [ ] 녹음 전송 전 앱을 종료했을 때 정상 파일, 일부만 남은 파일과 손상 파일을 구분해 안내한다.
- [ ] worker 정상 종료 요청 시 새 작업을 받지 않고 유예 시간 안에서 현재 작업을 마친다.
- [ ] STT 도중 강제 종료해도 자료가 사용 가능한 경우 상한 내에서 재처리하며, 이전 실행의 늦은 응답이 결과를 덮어쓰지 않는다.
- [ ] 전사문 저장 직전과 직후에 각각 실패시켜, 실제 저장 여부에 따라 STT 또는 리포트 단계로 복구한다.
- [ ] 리포트 생성 실패와 리포트 저장 직후 중단을 구분하고, STT 반복이나 중복 리포트 및 제안 저장이 없다.
- [ ] 자동 재시도 상한에 도달하면 자동 처리만 중단한다. 자료와 권한 및 처리 동의가 유효하고 재시도 가능한 오류라면 사용자 재시도를 제공한다.
- [ ] 자료 없음, 권한 없음과 삭제 요청 상태에는 재시도 버튼을 제공하지 않는다.
- [ ] 카드 생성 실패와 재요청이 기존 카드 및 면회 기록을 변경하지 않는다.
- [ ] 같은 통합 버전의 커밋과 정상 및 실패 경로 결과를 #107에 연결한다.

## 9. 검토한 대안

- worker가 현재 작업을 마치고 종료하는 방법만으로는 강제 종료와 장비 장애를 복구할 수 없습니다. 남아 있는 자료를 확인한 재처리와 사용자 재제출을 함께 검토했습니다.
- 모든 오류를 자동 재시도하면 잘못된 파일과 서버 설정 오류까지 반복합니다. 일시 장애만 제한적으로 재시도하고, 입력 및 구현 오류는 원인을 수정하도록 구분했습니다.
- 처음부터 STT를 다시 실행하면 이미 저장한 전사문과 리포트를 활용하지 못합니다. 저장 결과를 확인해 실패한 단계부터 이어 처리하도록 제안합니다.
- 보관 기간 변경은 복구 외의 기능과 동의에도 영향을 줍니다. 별도 PR에서 정하고, 이 문서는 사용할 수 있는 자료에 따른 복구 동작만 정의합니다.
