기존 PR의 연결 수정과 새 정정 기능은 별도 작업으로 관리한다. 기존 PR을 이 기능까지 전부 넣는 대형 PR로 확장하지 않는다. 위 이름은 PM의 요청 담당이며 착수 또는 일정 수락을 뜻하지 않는다. 담당 영역이 다르거나 일정이 어려우면 실제 담당과 가능한 일정을 회신한다. BE 내부 세부 분담은 BE에서 정한다.

### 작업 순서와 FE 분담 경계

- 인성님이 갱신 필요 상태, 사용 중지 카드와 재생성 상태를 전달할 API 및 필드를 먼저 공유한다. 필드 이름은 이 문서에서 임의로 확정하지 않는다.
- 서형님은 일대기 서버 조회와 저장 연결을 맡고, 채원님은 그 연결을 사용해 정정 이후 화면 상태를 처리한다. 같은 저장 API를 각자 따로 구현하지 않는다.
- 카드 선택 제한은 채원님, 재생성 요청과 완료 후 대화 시작 연결은 서형님이 맡는 초안이다. 두 분은 착수 전에 함께 수정할 화면과 공용 상태 코드의 담당을 나누고 같은 서버 상태를 사용한다.
- 생성 중 정정 저장 제한은 인성님이 서버에서 검사하고 채원님이 정정 화면에 표시한다. 서형님의 재생성 화면과 함께 검증한다.
- 채원님은 #128에서 10/18 이후 후속 진행 의사를 밝혔다. 다른 담당자의 수락과 전체 일정 확정으로 해석하지 않는다. 분담 제안과 질문은 [#128 댓글](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/pull/128#issuecomment-6216721678)에서 확인한다.

## 공통 테스트 자료

합성 프로필의 직업을 ‘교사’로 두고, 같은 사실을 근거로 한 카드 두 장과 관계없는 취미 카드 한 장을 준비한다. 사용자가 생성된 내용을 본 뒤 직업을 ‘버스 운전사’로 정정하는 상황을 검사한다. 실제 사용자 자료는 사용하지 않는다.

| 번호 | 상황과 조작 | 통과 기준 | 확인 담당 |
| --- | --- | --- | --- |
| C01 | 직업 정정 저장 | 사실과 갱신 필요 기록 저장. AI 호출 없이 관련 두 카드 사용 중지. 취미 카드는 열람 가능 | 인성, 채원 |
| C02 | 추가 사실을 여러 번 정정 | 저장만 하고 매번 생성하지 않음. 다음 대화 준비 시 최신 정정이 모두 입력에 포함 | 인성 |
| C03 | 정정 저장 요청 실패 | 저장 완료로 표시하지 않음. 재입력 또는 재시도할 수 있고 기존 편집 내용 유실 여부 확인 | 채원 |
| C04 | 정정 후 앱 종료와 재실행 | 서버에 저장한 정정과 사용 중지 상태 유지. 잘못된 카드로 대화 시작 불가 | 서형, 채원 |
| C05 | 다음 대화 준비 선택 | 누적 정정으로 묶음 전체 재생성. 완료 전 대화 시작 불가, 성공 후 새 묶음으로 교체하고 카드 선택 가능 | 인성, 서형 |
| C06 | 재생성 중 정정 저장 시도 | 해당 프로필의 저장을 잠시 막고 진행 상태 표시. 성공 또는 실패로 작업 종료 후 다시 저장 가능 | 인성, 서형, 채원 |
| C07 | 재생성 실패와 재시도 | 정정은 유지. 잘못된 기존 묶음으로 대체하지 않음. 최신 정정으로 재시도 | 인성, 서형 |
| C08 | 준비 버튼 반복 클릭 | 같은 입력으로 중복 생성 작업과 카드 묶음이 등록되지 않음 | 인성, 서형 |
| C09 | 카드 근거 연결이 없어 영향 판별 불가 | 정상 카드를 추측하지 않고 해당 묶음 전체 사용 중지 및 갱신 대상으로 처리 | 인성 |
| C10 | 사용 중지 후 평가와 추천 입력 조회 | 대화 평가의 미사용이나 부정 반응으로 기록하지 않고 추천 불이익 없음 | 인성, 문영 |
| C11 | 새 묶음 완료 후 추가 정정 | 다시 저장 및 사용 중지. 자동 재생성하지 않고 다음 준비 요청에서 반영 | 인성, 서형 |
| C12 | 기존 면회 기록 조회 | 정정을 이유로 과거 면회 내용을 소급해 다시 작성하지 않음 | 인성, 채원 |
| C13 | 실제 모델로 정정 후 질문 생성 | 생성 입력은 버스 운전사로 정정돼 있고 교사 경험을 사실로 전제하는 질문이 나오지 않음. 모델 출력 검사는 코드 검사와 별도 기록 | 문영, 인성 |

각 검사에는 실행 커밋, 환경, 입력과 결과, 통과 또는 미실시 사유를 남긴다. 10/18 첫 회차 통합 성공을 이 정정 기능의 완료로 대신하지 않는다.

## BE 검사 결과 (이인성, #158)

브랜치 `feature/backend-card-correction-refresh`, 로컬 PostgreSQL 17 임시 DB에서 `uv run pytest`로 BE 테스트 373개 통과(새 테스트 `backend/tests/test_card_corrections.py` 22개, `test_migrations.py` 1개 포함). 앱, 실제 worker와 모델 호출은 실행하지 않았다.

다시 만들어야 하는 표시는 카드 한 장이 아니라 묶음 단위로 붙였다. 고친 뒤에는 어차피 그 묶음으로 면회를 시작하지 않고, 다시 만들면 12장이 모두 바뀌기 때문이다. 카드 단위 표시가 화면에 꼭 필요하면 근거(`evidence`)로 영향받은 카드를 찾아 따로 붙일 수 있다.

| 번호 | BE 결과 |
| --- | --- |
| C01 | 묶음 단위로 통과. 직업이나 이야기 내용을 고치면 AI 호출 없이 묶음이 `needsRefresh`가 된다. 영향받은 카드만 골라 표시하는 것은 하지 않았다 |
| C02 | 고칠 때마다 생성하지 않음은 통과. 다시 만들 때 최신 정정이 입력에 들어가는 것은 기존 `build_context`가 DB를 읽는 방식에 따른 것이며 이번에 따로 검사하지 않았다 |
| C05 | BE 부분 통과. `needsRefresh`인 묶음은 4-1이 새로 만들고 5-1이 `CARD_SET_NEEDS_REFRESH`로 거절한다 |
| C06 | BE 부분 통과. 카드를 만드는 중에 카드 생성에 쓰는 값을 고치면 2-4, 2-7, 2-9가 `CARD_GENERATION_IN_PROGRESS`로 거절하고 저장하지 않는다. 이름처럼 카드 생성에 쓰지 않는 값은 고칠 수 있다 |
| C07 | BE 부분 통과. 다시 만들기가 실패해도 고친 내용은 남고 예전 묶음은 5-1이 계속 거절한다 |
| C08 | 기존 동작. 만드는 중 작업은 프로필당 하나(`uq_card_sets_running`)이며 기존 테스트로 확인 |
| C09 | 해당 없음. 근거와 상관없이 묶음 전체를 `needsRefresh`로 둔다 |
| C10 | 기존 동작. 지난 카드 입력은 평가까지 끝난 회차의 카드만 읽으므로 쓰지 않은 묶음은 들어가지 않는다. 이번에 따로 검사하지 않았다 |
| C11 | 통과. 새 묶음이 나온 뒤 다시 고치면 그 묶음이 다시 `needsRefresh`가 되고, 자동으로 다시 만들지 않는다 |
| C12 | 통과. 면회에 쓴 묶음은 고쳐도 표시하지 않는다 |
| C13 | 미실시. 실제 모델 출력 검사는 AI 담당 |

남은 것

- FE의 `needsRefresh` 표시와 다시 만들기 버튼, 새 409 두 개(`CARD_SET_NEEDS_REFRESH`, `CARD_GENERATION_IN_PROGRESS`) 처리. 지금 앱은 `ready`이면 4-1을 부르지 않으므로, BE만 먼저 병합하면 고친 뒤 면회를 시작할 방법이 없다. FE를 먼저 병합해야 한다.
- 사진 설명도 카드 생성에 쓰이지만 수정 API(3-3)가 아직 없다. 생기면 같은 방식으로 표시를 붙인다.
- 이야기 추가(2-6, 7-4)와 사진 추가는 정정이 아니라서 표시하지 않는다. 다음 생성부터 반영된다.
