## 제품과 대상

새록새록 팀의 카카오테크캠퍼스 충남대 1팀 2단계 프로젝트다. 보호자가 면회 전에 확인된 생애 정보와 지난 반응으로 대화 소재를 준비하고 확인된 이야기를 축적하는 Android 우선 Flutter 앱이다.

초기 대상은 경도인지장애부터 경도 치매 단계의 부모를 면회하는 보호자다. 대화가 어려워진 부모와 성인 자녀까지 넓힐지는 검토 중이다. 안부 이후 소재 부족, 반복과 침묵으로 느끼는 보호자의 부담을 다룬다.

## 제품 범위

| 포함 | 제외 |
| --- | --- |
| 프로필 이미지, 기본 정보, 취향과 생애 정보 | 의료 진단, 병세 예측, 기억 회복과 치료 효과 주장 |
| 대화 카드와 추가 질문 지원 | AI가 보호자를 대신해 대화 |
| 면회 녹음, STT와 화자 처리 | 피보호자 직접 인지 훈련 |
| 보호자 평가, 리포트와 변경 제안 | 확인되지 않은 생애 사실의 자동 반영 |
| 생애 시기별 이야기와 다음 회차 반영 | 말기 치매 대상 초기 검증 |

실물 스토리북 판매와 iOS는 후속 검토다. 요구사항별 상태와 제외 이유는 [테크스펙](../tech-spec.md)에 기록한다.

## 제품 흐름과 확인 원칙

프로필과 선택적 사진 첨부 → 카드 생성과 선택 → 동의 및 권한 확인 후 면회 녹음 → 보호자 소감 저장 → 녹음 제출과 STT → 리포트와 변경 제안 → 승인된 이야기와 최종 주제 선택 반영 → 다음 회차.

- 보호자 소감을 먼저 저장하고 녹음을 제출한다. 전사 결과와 소감이 모두 준비된 뒤 리포트를 만든다.
- 대화가 이어지면 주제가 달라져도 개입하지 않는다. 소재가 필요하면 보호자가 미리 준비한 꼬리 질문이나 다른 카드를 선택한다.
- 사진 메타데이터는 AI 분석과 주제 추천 입력에서 제외한다. AI 출력은 후보이며 보호자 확인 전 사실로 반영하지 않는다.
- 분석 실패 시 계산하지 못한 수치나 리포트를 만들지 않는다. 실패한 단계와 사용 가능한 자료를 확인하는 [복구 검토안](../architecture/processing-recovery.md)을 따르며, 소감만으로 정상 리포트를 완성하는 대체 흐름을 확정하지 않는다.
- 한 회차의 반응이나 카드 미사용 및 미응답만으로 소재를 영구 제외하지 않는다. 사용자가 직접 추천 제외를 선택하는 경우는 아래 기준을 따른다. 승인된 이야기의 수정과 거절 후보의 복구는 구분한다.
- 회차가 쌓이면 소재 선택의 근거가 늘어난다고 설명하며 대화의 질 향상이나 치료 효과를 보장하지 않는다.

분기와 반복은 [목표 흐름](../architecture/README.md#목표-사용자-흐름)을 참고한다. 첫 질문, 사진 설명 사용과 다음 추천은 [주제 카드 전체 설계 검토안](../architecture/card-generation-flow.md)에 모은다. 사진 설명은 별도 승인 없이 카드 입력에 사용하고, 사용자가 원할 때 앨범에서 수정하는 것이 기존 결정이다. 사진 등록이나 카드 선택에 필수 설명 확인을 다시 요구하지 않는다.

## 카드와 이야기의 현재 기준

- [현행 카드 계약](../architecture/data-contracts.md#대화-카드-묶음-cardset)의 12장 구성, 선택용 9장과 보충용 3장, 카드당 첫 질문 1개와 꼬리 질문 3개를 유지한다. 사용할 카드는 보호자가 고른다. 일대기의 6개 분류에 카드 2장씩을 배정하는 규칙은 아니다.
- 9월 23일 회의에서 정한 대로 첫 질문과 꼬리 질문은 면회 전에 준비한다. 면회 중 실시간 질문 생성은 현재 MVP 범위에서 제외한다.
- [현행 변경 제안 계약](../architecture/data-contracts.md#변경-제안-changeproposal)에는 승인한 제안을 취소해 이전 상태로 되돌리는 기능이 없다. 승인으로 저장한 이야기는 일대기에서 직접 수정한다. 추천 제외 해제는 별도 설계 대상이다.
- 거절한 이야기 후보는 30일 보관하고, 기간 내 복구하면 승인 전 후보로 돌아간다. 승인된 이야기의 취소와는 다른 기능이다. [후보 복구 기준](../architecture/card-generation-flow.md#이야기-후보의-승인-거절과-복구)에 따라 BE와 FE가 저장, 복구 API와 화면을 설계한다.

위 내용은 기능 기준이며 구현 완료를 뜻하지 않는다.

## 사실 정정과 다음 면회 카드 반영

2026-10-16 PM 결정. 제품 흐름의 기준이며 구현 완료를 뜻하지 않는다. 개발상 어렵거나 불가능한 부분은 FE, BE와 AI가 이유와 대안을 제시하고 PM과 조정한다.

### 즉시 처리와 다음 면회 전 처리의 구분

보호자 소감은 대화 상태에 대한 평가이며 아직 생성되지 않은 카드의 정정 단계가 아니다. 정정은 생성된 카드나 일대기를 확인한 뒤 한다. 정정은 즉시 저장하고 영향받은 카드의 사용을 중지한다. 매번 재생성하지 않고 ‘다음 대화 준비’에서 누적 정정을 반영해 카드 묶음 전체를 한 번 재생성한다. 완료 후 카드 선택과 대화 시작을 허용한다.

| 잘못된 내용을 발견한 시점 | 즉시 처리 | 카드 생성 또는 갱신 시점 |
| --- | --- | --- |
| 생성된 내용에서 오류 발견 | 정정 저장, 영향받은 카드 사용 중지와 갱신 필요 기록 | 다음 대화 준비 때 누적 정정을 반영해 카드 묶음 재생성 |
| 이후 추가 정정 | 정정 저장과 사용 중지 대상 갱신 | 매번 생성하지 않고 다음 대화 준비 때 함께 반영 |
| 다음 면회를 시작하려는데 정정이 카드에 반영되지 않음 | 기존 카드로 면회를 시작하지 못하도록 안내 | 정정을 반영해 카드를 갱신하고, 완료된 뒤 면회를 시작한다. 갱신 실패 시에도 잘못된 기존 카드로 대신 진행하지 않는다. |

저장하지 않은 편집을 확정 사실로 취급하지 않는다. 사실 저장이 실패했다면 저장 완료나 정정 반영 완료로 표시하지 않는다.

- 최초 프로필에서 사용자가 직접 입력한 내용은 사용자 확인 정보로 사용한다. 다시 AI의 확인을 받게 하지 않으며, 이후 사용자 정정은 반영한다.
- 면회 전사에서 추출한 내용과 그 내용으로 만든 AI 카드 후보는 사용자 확인 정보와 구분한다. 전사나 생성 성공만으로 사실이 확정되지는 않는다.
- 정정은 즉시 저장하고 영향받은 카드의 사용을 중지한다. 매번 재생성하지 않고 ‘다음 대화 준비’에서 누적 정정을 반영해 카드 묶음 전체를 한 번 재생성한다. 완료 후 카드 선택과 대화 시작을 허용한다.
- 이후 일대기나 프로필을 보다가 수정하면 사실 자체는 저장하고, 카드 반영이 필요하다는 기록을 남긴다. 수정할 때마다 모델을 호출하지 않고 다음 면회 준비에서 누적된 정정을 한 번에 반영한다.
- 다음 면회는 정정이 반영된 카드로 시작해야 한다. 카드 갱신이 필요하거나 진행 중이면 잘못된 기존 카드로 새 면회를 시작시키지 않는다. 비용을 이유로 정정 반영을 그다음 면회로 미루지 않는다.
- 생성 중에는 해당 프로필의 정정 저장을 잠시 막고 진행 상태를 보여준다. 작업 종료 후 다시 허용한다. 완료 후 새 정정이 생기면 갱신 필요 상태로 기록한다. 과거 면회 기록은 소급해 다시 쓰지 않는다.
- 사진 설명은 별도 승인 없이 사용하는 기존 기준을 유지한다. 사진 메타데이터는 입력에 넣지 않는다. 사용자 정정이 생긴 경우에는 이 갱신 기준을 적용한다.

### 정정 이후 카드 사용 기준

| 카드 구분 | 표시와 동작 |
| --- | --- |
| 정정의 영향을 받지 않은 카드 | 계속 열람 가능. 갱신이 필요한 묶음으로 다음 대화를 시작하지는 않음 |
| 정정한 사실을 근거로 만든 카드 | ‘정보 수정으로 갱신 예정’ 표시. 다음 대화용 선택 불가 |
| 정정을 반영해 새로 생성한 묶음 | 생성 성공 후 기존 묶음을 교체하고 카드 선택과 대화 시작 허용 |

영향받은 카드는 근거 연결로 판별한다. 연결이 없어 정확히 구분할 수 없다면 해당 묶음 전체를 갱신 대상으로 두고 사용을 중지한다. 카드 한 장만 숨기고 잘못된 사실을 다음 생성 입력에 그대로 남기지 않는다.

정정으로 사용 중지한 카드를 대화 평가의 ‘미사용’으로 저장하거나 추천 점수에 불이익을 주지 않는다. 재생성 실패 시 정정 내용을 유지하고 재시도를 안내한다. 재생성이 끝난 뒤 다시 정정하면 갱신 필요 상태로 돌아가며, 자동 재생성하지 않고 다음 대화 준비에서 다시 반영한다.

BE는 사실 저장, 영향받은 카드 판별과 사용 중지, 갱신 필요 기록과 면회 시작 검사를 맡는다. AI는 최신 정정을 반영해 카드 묶음 전체를 생성한다. FE는 정정 화면, 사용 중지 표시, 다음 대화 준비와 생성 중 정정 저장 제한을 처리한다. 저장 필드, API와 상태 값은 공동 설계하며 이 문서에서 새 이름을 확정하지 않는다. 담당별 요청과 검증 사례는 [개발 인계와 검증](card-correction-checks.md)에 둔다.

## 2026-09-19 PM 결정

### 카드 미사용과 추천 제외

카드를 쓰지 않은 이유는 시간 부족이나 나중에 이야기하려는 선택일 수도 있다. 미사용과 미응답만으로 비선호를 추정하거나 추천 순위를 낮추거나 추천 대상에서 제외하지 않는다.

추천 제외는 사용자가 `앞으로 추천하지 않기`처럼 의사를 직접 표시했을 때 적용한다. 추천 대상에서 제외하는 것이며 과거 카드와 면회 기록을 삭제한다는 뜻은 아니다. 카드 추천은 핵심 기능이므로 로직을 별도로 설계한다. 제외할 대상의 범위, 해제 방법, 화면과 저장 필드 및 API는 후속 설계에서 함께 정한다.

### 면회 기록 삭제와 승인된 사실

면회 기록을 삭제해도 보호자가 이미 승인해 프로필에 넣은 사실은 유지하고, 삭제한 면회와의 출처 연결만 해제한다. 기록을 지운 이유만으로 승인한 사실까지 틀렸다고 판단할 수 없기 때문이다. 삭제 행동을 부정적 감정이나 카드 비선호로 자동 해석하지 않는다.

면회에서 확인한 사실은 생성 시 출처 회차를 연결하고, 해당 회차가 삭제된 뒤에는 연결값을 비울 수 있다. 필드 규칙은 [LifeFact 계약](../architecture/data-contracts.md#확인된-생애-사실-lifefact)을 따른다. 이 결정은 면회 기록 삭제에 한정하며 계정 탈퇴나 프로필 삭제 범위를 정한 것은 아니다.

### 개발 GPU와 시연 장비

현재 RTX 3060 Ti는 개발용이다. 시연에 필요한 장비 사양과 처리 성능은 AI와 BE의 추가 실험 결과를 보고 정한다. RTX 3060 Ti를 최종 시연 장비로 확정하거나 상시 가동 및 새 장비 구매를 승인한 것은 아니다.

## 처리와 동의

STT는 GPU 서버, 사진 설명과 카드 및 리포트 생성은 ML API를 활용하는 방향이다. 기존 온프레미스 일괄 처리 결정과 후속 변경은 [ADR-006](../architecture/decisions/ADR-006-server-side-ai-processing.md#현재-적용할-방향-2026-10-11-정정)에 구분했다. RTX 3060 Ti는 개발용이며 시연 장비 사양은 실험 후 정한다. BE가 데이터별 저장과 처리 범위를 정리하고 FE, AI와 PM이 확인한다. 사진의 별도 내용 승인을 생략해도 사진 분석 동의와 실제 사용자 자료의 외부 전송 조건은 확인해야 한다. 등록 사진과 분석용 임시 사본은 [ADR-001](../architecture/decisions/ADR-001-consent-and-temporary-processing.md#등록-사진과-분석용-임시-사본의-구분)에서 구분한다. 녹음과 전사문 보관의 추가 변경은 별도 검토하며 이 카드 설계 정정으로 기존 삭제 규칙을 바꾸지 않는다.

필수 동의는 개인정보 처리, 건강 관련 민감정보 처리와 피보호자 동의 확인이다. 이미지 분석은 기능 이용 시 동의를 확인한다. 품질 개선과 푸시 알림은 선택이며 거부해도 가입과 기본 기능을 차단하지 않는다. 대리 동의의 자격과 절차는 검토가 필요하다. 자세한 문구와 외부 전송 조건은 [법률 문서](../legal/README.md)가 정본이다.

## 검토 중인 제품 결정

| 결정 | 확인할 내용 |
| --- | --- |
| 최종 대상 | 질환 단계 한정 또는 부모와 성인 자녀로 확대 |
| 기억과 추천 | 확인된 사실, 최근 반응, 미확인 후보의 저장과 검색 및 갱신 규칙. 미사용 및 미응답 불이익 금지와 명시적 추천 제외 원칙은 확정했고, 추천 로직과 제외 범위 및 해제 방식은 별도 설계 |
| 데이터 관리 | 서버 중심 방향에 맞춘 데이터별 저장 범위, 단말 보관 여부, 접근 권한, 보관 기간과 삭제 구현 |
| 후속 확장 | 웹 검색, 사용자 설정, 스토리북 직접 제공과 실물 판매 |

현행 계약과 제품 기준이 다른 항목은 [계약 정합성 확인 목록](../architecture/data-contracts.md#현재-적용-범위)에서 함께 확인한다. 미결 정책을 구현자가 임의로 확정하지 않는다.

## 역할

| 담당 | 역할과 지원 관계 |
| --- | --- |
| 김영석 | 주 PM, 문제와 범위, 우선순위, PR 병합과 제출 |
| 이예은 | 부 PM, 결정 검토와 기록, 제출 및 진행 관리, 주 PM 부재 시 진행 |
| 이서형 | FE 리드, Flutter 화면과 접근성, 권한 및 합의된 인터페이스 연동 |
| 김민혁 | BE 리드, 저장과 데이터 이동, API, 서버 실행 연동과 로그 및 삭제 |
| 이문영 | AI 리드, 이미지와 음성 모델, 녹음 입력, 생성과 품질 및 실패 기준 |
| 성채원 | 정보 수집과 QA 전반, FE 중심 지원 |
| 이인성 | AI와 BE 리더 지원, 실험과 구현 검증 |

모델은 AI, 저장과 실행 구조는 BE, 화면과 앱 연동은 FE가 기술 검토한다. 공통 계약은 함께 확인하고 PM이 범위와 진행을 관리한다. 개인별 작업과 기한은 GitHub 이슈, 리뷰와 병합은 [협업 규칙](../../CONTRIBUTING.md)을 따른다.

[12주 목표](12-week-team-goals.md)와 [주간 운영](weekly-operations.md)은 별도 관리한다. 제품 대상, 범위나 성공 기준을 바꾸면 PM 확인 후 이 문서와 관련 명세를 함께 갱신한다.
