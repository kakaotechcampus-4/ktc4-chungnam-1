# ck STT 예비 서버의 SSH 운영 연결

상태: 2026-11-03 KST PM의 자동 전환 적용 요청으로 임시 배포. GitHub PR 게시와 병합은 미실행.

이 문서는 SSH 운영 연결 PR의 범위다. GPU 실행 설정과 BE 전환 코드는 각각 별도 PR로
검토한다. 세 브랜치는 develop에서 따로 분리했으며 운영 연결에는 두 코드 변경이 먼저 필요하다.

기본 개인 GPU의 Tailscale 연결을 유지한다. 기본 서버에 연결하지 못할 때만 ck로 한 번
전환한다. ck를 기본으로 바꾸거나 개인 PC를 중계 서버로 사용하지 않는다.
기존 Tailscale망의 관리 권한이 확보되지 않아 ck는 SSH로 먼저 검증한다.
Tailscale 통일 여부는 이문영과 김민혁 확인 후 결정한다.

## 처리 규칙

| 조건 | 처리 |
| --- | --- |
| 기본 서버 정상 | 기본 서버만 호출 |
| 기본 서버의 TCP 연결 실패 또는 연결 시간 초과 | 예비 서버를 한 번 호출 |
| 요청 전송 후 응답 대기 시간 초과, 전송 오류 또는 HTTP 오류 | 예비 서버로 재전송하지 않고 기존 오류 반환 |
| 결과 형식이나 작업 ID 불일치 | 기존 응답 검증 오류 유지 |
| 예비 서버도 연결 실패 | `ConnectError`는 `AI_SERVER_UNAVAILABLE`, 연결 시간 초과는 `AI_SERVER_TIMEOUT`으로 종료 |
| 다음 작업 | 기본 서버부터 다시 시도 |

예비 서버를 설정한 경우 두 시도는 `SAEROK_AI_SERVER_TIMEOUT_SECONDS`의 같은 전체
마감을 공유한다. 서버별 연결 제한은 `SAEROK_AI_SERVER_FAILOVER_CONNECT_TIMEOUT_SECONDS`
(기본 5초)다. 예비 주소가 비어 있으면 기존 단일 서버 동작과 연결 제한을 유지한다.
자동 동시 전송, 무한 재시도, 큐 재등록과 실패 작업 복구는 추가하지 않는다.

worker는 두 시도가 끝날 때까지 같은 S3 원본을 유지하고, STT 성공 또는 최종 실패 후
기존 삭제 처리를 수행한다. 전환으로 원본의 삭제 기한을 늘리지 않는다. 전환 로그에는
`speech_analysis_backup_used reason=connect_failure`만 기록하며 음성, 전사문과 URL은 남기지 않는다.

## SSH 예비 연결의 제한

| 항목 | 제한 |
| --- | --- |
| 키 | BE에서 생성한 ck 전용 키. 개인 관리자 키를 복사하지 않음 |
| ck 계정 | root가 아닌 터널 전용 계정. 비밀번호 로그인, 셸과 SFTP 사용 불가 |
| 접속 출발지 | 등록한 BE 공인 IP 한 개만 해당 키 사용 가능. IP 변경 시 갱신 필요 |
| 전달 목적지 | ck의 loopback STT 한 포트만 허용 |
| 불필요한 경로 | 역방향, Unix 소켓, 에이전트와 X11 전달 금지 |
| 서버 신원 | 기존에 인증된 ck 연결에서 확인한 호스트 키 지문을 대조. 호스트 키 검사 생략 금지 |
| 공개 범위 | ck STT와 BE 터널 수신 포트를 인터넷에 공개하지 않음 |

전용 계정에 `AllowTcpForwarding local`, `PermitOpen`, `PermitListen none`,
`MaxSessions 0`과 `ForceCommand /bin/false`를 함께 적용한다.
`restrict,port-forwarding,permitopen`만으로 역방향 전달까지 막았다고 판단하지 않는다.
기존 관리자 계정의 정책은 바꾸지 않고 새 설정은 `sshd -t`, 계정별 `sshd -T -C`와
실제 허용 및 차단 접속으로 확인한다. 키와 실제 주소는 저장소에 넣지 않는다.

BE 터널은 worker가 접근 가능한 비공개 네트워크에 있어야 한다. 컨테이너의
`127.0.0.1`은 호스트가 아닌 해당 컨테이너 자신이다. 검증에서는 worker의 네트워크
namespace 안에 임시 SSH 연결을 만들고 후보 클라이언트를 별도 프로세스로 실행한다.
이것은 초기 임시 검증 방식이다. 자동 전환 적용에서는 BE 호스트의 systemd가 기존 SSH
클라이언트를 관리하고, 터널은 BE Docker bridge의 사설 주소에만 바인딩한다. 새 컨테이너나
사용자 PC 중계는 추가하지 않는다. 인터넷 인바운드와 기본 Tailscale 주소는 변경하지 않는다.

## 기동과 원복

- BE는 `ops/stt-backup/run-tunnel.sh`와 `saerok-stt-backup.service`를 사용한다.
  주소, 포트, 검증된 known_hosts와 전용 키 경로는 서버 내부 EnvironmentFile에만 둔다.
  SSH 연결이 끊기면 10초 간격으로 재연결하며 호스트 키 검사를 유지한다.
- ck는 Supervisor 4.3.0을 별도 가상 환경에 설치해 `ops/ck-backup/`의 설정으로 해당
  STT 프로세스만 관리한다. 관리 소켓은 0600의 Unix 소켓이며 HTTP 관리 포트는 열지 않는다.
  시작 중 연속 실패는 세 번까지만 재시도한다.
- 앱과 캐시 경로, GPU 번호와 연산 형식은 ck의 비공개 `runtime.env`로 지정한다.
  운영 모드에서는 `localFile`과 검증 파일 제공 경로를 사용하지 않는다.
- 예비 모델의 대기 상태도 GPU 메모리를 사용한다. 다른 작업을 종료하거나 독점 예약하지 않는다.
  현재 설정의 가용량과 긴 녹음 처리 성능은 AI 담당자와 확인한다.
- ck 컨테이너 자체는 systemd로 부팅하지 않는다. Supervisor는 SSH 접속 종료와 무관하게
  실행되지만 학교 측에서 컨테이너 자체를 재시작하면 Supervisor 재기동이 필요하다.
- 임시 이미지는 기존 배포본 위에 변경한 세 모듈과 worker의 설정 전달 두 줄만 추가했다.
  서버에 있던 worker의 다른 변경은 보존했다. API, 카드 worker, DB와 Caddy는 교체하지 않았다.
- 원래 이미지와 환경을 BE 내부에 보관하고, worker 전용 compose override를 팀 체크아웃에
  연결했다. 실제 설정은 로컬 Git 제외 목록에 넣고 커밋하지 않는다. 임시 worker 이미지는
  고정돼 있으므로 팀원의 정식 배포 전에 이 override를 확인해야 한다. 기능 PR 병합 후
  정식 이미지로 교체하고 임시 override를 해제한다.
- 원복은 보관한 기존 이미지와 원래 환경을 쓰는 worker 전용 rollback override로 한다.
  다른 서비스와 DB 볼륨은 내리지 않는다.

## 검증 범위와 운영 전 확인

- 단위 테스트: 기본 서버 우선, 연결 실패 시 한 번 전환, 공유 마감, 응답 오류 재전송 금지,
  설정 전달과 삭제 순서. DB가 없는 환경의 DB 테스트는 건너뛴 것으로 구분한다.
- 실제 연결: BE 컨테이너 → 제한된 SSH 터널 → ck의 실제 STT 앱. 합성 WAV는 비공개 S3의
  검증 전용 객체로 올리고, Presigned GET 입력의 다운로드, 크기와 SHA-256 검증 및 모델 실행을 확인한다.
- 검증용 파일 제공 경로와 후보 코드 전송 경로는 임시 loopback 검증 서버에만 추가한다.
  제품 API에 추가하거나 인터넷에 노출하지 않으며 검증 후 해당 서버를 종료한다.
- 실제 사용자 음성, DB 작업과 외부 리포트 생성은 이 연결 검증에 사용하지 않는다.
- 정식 배포 전에 담당자가 GPU 가용량, 서버 재부팅 후 기동, 터널 재연결, worker 재생성 후
  연결 유지와 종료 유예를 확인한다. SSH 키 교체 및 폐기 담당도 정한다.
- 기본 Tailscale 접근 정책(#172), worker 종료 유예(#173)와 기존 터널 정리 PR #157은 별도 작업이다.
  ck 연결 성공으로 이 작업들까지 완료 처리하지 않는다. #157의 기본 GPU용 compose 터널을
  되살리는 변경이 아니며, 이 예비 연결은 별도 서비스로 관리한다.

공통 요청 및 응답 JSON과 상태 계약은 변경하지 않는다. 실제 사용자 자료 사용 전에
[법률 문서의 경로별 확인](../../docs/legal/README.md#개발-우선과-실제-사용자-자료-사용-전-확인)을 따른다.

## 2026-11-03 KST 검증 결과

02:37 KST에 음성 worker만 임시 배포했다. 적용된 운영 설정으로 합성 음성을 보내
기본 경로 연결 실패 후 ck를 한 번 사용해 7.598초에 성공했다. 기존 기본 주소는 유지했고
연결 제한은 5초, 전체 STT 제한은 600초다. SSH 서비스는 active 및 enabled이며 ck 관리
프로세스도 실행 중이다. 인터넷에서 예비 포트 접속은 실패했고 검증 파일 제공 경로는 404다.
기존 실패 작업을 복구하거나 실제 앱에서 리포트까지 다시 만든 검사는 아니다.

기존 배포 worker에는 develop과 다른 코드가 있어 현재 배포본을 보존하고 설정 전달만
추가했다. 정식 이미지로 바꾸기 전에 BE 담당자와 그 차이를 대조한다.

### 임시 배포 전 후보 코드 검증

아래 표는 02:06 KST까지 진행한 초기 검증이며, 위의 02:37 KST 임시 배포 후 검사와
구분한다. 기준은 develop `2f3c141`에서 분리한 후보 코드다. 실제 BE 컨테이너 안의
별도 프로세스로 검사했으며 당시 운영 worker 설정은 변경하지 않았다.

| 검사 | 실제 결과 |

| Python 3.12와 잠금 의존성, PostgreSQL 17 임시 DB의 BE 전체 테스트 | 429건 통과, 건너뜀과 실패 없음 |

| 기본 서버 연결 불가 상황을 만든 뒤 ck 전환 | 실제 S3 입력, 실제 모델로 성공. 준비된 모델에서 1.288초 |

| 전용 키로 셸 실행, 다른 포트 연결과 역방향 전달 | 각각 차단, SSH 종료 코드 255 |
| 합성 S3 원본 정리 | 삭제 요청 204. 삭제 전 HEAD 200, 삭제 후 HEAD와 기존 GET URL 모두 403 |

위 음성은 10.29초, 한 화자의 한국어 합성 음성이다. 두 화자 정확도, 긴 녹음, 동시 처리량,
앱부터 DB 및 리포트까지의 전체 실행이나 운영 품질을 검증한 수치는 아니다.
검증 당시 기존 개인 GPU 경로의 상태 확인은 연결 시간 초과였다. 하드웨어 고장 판정은 아니다.

S3는 [목록 권한이 없으면 존재하지 않는 객체도 403을 반환할 수 있다](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html).
따라서 403만으로 삭제를 증명하지 않고 삭제 요청의 성공 및 이전에 작동한 URL의 재조회
불가를 함께 기록했다. 객체 버전 전체의 완전 삭제나 Lifecycle 검증까지 수행한 것은 아니다.
이 검증을 위해 IAM 권한을 추가하지 않았다.
