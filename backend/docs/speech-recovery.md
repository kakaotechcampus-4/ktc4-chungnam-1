## 저장과 중복 방지

- 실패한 작업의 전사는 기존 `transcript_expires_at`까지만 보관한다. 재요청으로 기한을 늘리지 않는다. 다만 기존 develop은 실패 즉시 전사를 지웠으므로, 실패 후 보관은 정책 변경이다. 이 변경은 2026-11-03 PM이 승인했다. 동의 화면 반영은 아래 확인 항목을 따른다.
- 새 작업 ID를 사용하므로 이전 작업의 늦은 모델 응답은 저장되지 않는다.
- 회차 행 잠금과 기존 활성 작업 유일 제약으로 중복 접수를 막는다. `retry_of_analysis_id`는 리포트 재시도의 이전 작업을 가리킨다.
- 리포트 저장 성공 시 전사를 지우는 기존 처리는 유지한다. 원본 녹음 삭제 실패는 별도 대기열에 남긴다.
- 원본을 이미 지운 상태에서 STT를 반복할 수 있다고 가정하지 않는다. 전사가 없으면 사용자가 기기에 남긴 파일을 다시 보낸다.
- 완료한 리포트, 다른 계정, 동의 철회를 재시도로 우회하지 않는다.
- worker가 `sttCompleted`에서 집어 가는 작업은 두 가지다. 재요청한 작업은 바로 가져간다. 리포트까지 이어 가던 worker가 전사 저장 때 둔 인계 임대(`SAEROK_SPEECH_ANALYSIS_LEASE_SECONDS`, 기본 900초) 안에 리포트 생성을 시작하지 못하고 멈춘 작업은 그 임대가 끝난 뒤 가져간다. STT 단독 실행 작업은 인계 임대가 없으므로 리포트 생성에 넘기지 않는다.
- 이어받기는 실패한 작업의 재시도가 아니다. 작업이 `generatingReport`로 바뀐 뒤 다시 `sttCompleted`로 돌아오지 않으므로 작업마다 한 번뿐이다. 이미 이어받은 작업이면 늦게 돌아온 원래 worker는 리포트 생성을 시작하지 못한다. 이어받은 worker는 리포트 생성 전에 S3를 부르지 않고, 원본 삭제 기록이 없으면 삭제 요청만 대기열에 남긴다. 리포트 생성이 실패하면 기존 실패 처리대로 원본 삭제를 다시 시도한다.
- 두 경우 모두 남은 전사 기한이 생성 단계 임대 시간(`SAEROK_SPEECH_ANALYSIS_LEASE_SECONDS`) 이상일 때만 집어 간다. 그보다 적게 남았으면 생성을 시작하지 않고 worker 정리 때 전사를 지우며 `TRANSCRIPT_EXPIRED`로 끝낸다. 이후 재요청은 회차의 재요청 횟수와 관계없이 `RECORDING_REQUIRED`이므로 기기 녹음을 다시 보낸다.
- 현재 구현 (2026-11-09 기준): 위 세 항목의 인계 임대(#280)와 남은 기한 조건(#279)은 11/9 배포(run 42568179490)부터 운영에 있다. 그 전 운영(11/8 배포, develop `9c2b8276`)의 worker는 `sttCompleted`에서 재요청한 작업만 가져갔으므로, 전사 저장 뒤 리포트 시작 전에 멈춘 작업은 STT 완료 후 24시간이 지나 `TRANSCRIPT_EXPIRED`로 끝날 때까지 `sttCompleted`에 남았다.
- 수동 재요청(6-5)은 면회 회차당 `SAEROK_REPORT_RETRIES_PER_SESSION`(기본 3)회까지다(2026-11-09 PM 결정, #285). 재요청마다 전사를 외부 ML로 다시 보내기 때문이다. 회차 행을 잠근 뒤 그 회차에서 `retry_of_analysis_id`가 있는 작업 수를 세므로 동시 재요청에도 넘지 않는다. 처리 중인 재요청을 다시 보내 같은 작업을 돌려받는 경우는 세지 않는다. 횟수는 남은 전사를 다시 쓸 때만 적용한다. 한도를 넘었고 전사가 남아 있으면 `REPORT_RETRY_LIMIT_EXCEEDED`이며, 남은 전사는 기존 기한 정리로 지운다. 그동안 6-2는 `REPORT_RETRY_AVAILABLE`로 재제출을 받지 않는다. 전사가 없거나 기한이 지났으면 한도와 관계없이 `RECORDING_REQUIRED`이므로, 앱이 기기 녹음을 6-2로 다시 보내 그 회차의 리포트를 받을 수 있다. 이 재제출은 `retry_of_analysis_id`가 없는 새 작업이라 재요청 횟수에 넣지 않는다(2026-11-09 PM 결정). 재제출한 작업의 리포트가 다시 실패하면 그 전사로 하는 6-5에는 같은 한도가 적용된다.
- 자동 재시도 횟수, 24시간 밖의 보관 연장, 과거 실패 작업의 일괄 재처리는 추가하지 않는다.

## 실패 전사와 기기 녹음의 보관 대조

상태: 2026-11-03 실패 전사 보관 변경은 PM 승인. 동의 문안의 실제 동의 화면 반영과 운영 적용은 아직이다. 최대 시간 값이 같다는 이유로 보관 정책이 그대로라고 설명하지 않는다.

현재 구현 (2026-11-09 기준): 위 상태 줄은 11/3 작성 당시 기준이다. #213의 BE 코드와 migration은 11/5 운영 배포(develop `6cebcf72`)부터 운영 서버에 있다([#187의 11/5 운영 배포 기록](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/issues/187#issuecomment-6652039046)). #213의 앱 변경(홈의 재요청, 기기 녹음 재제출)은 BE 배포와 별개라 그 변경이 든 앱 빌드가 설치돼야 사용자에게 보인다. 아래 "DB 삭제 경로"의 인계 임대(`mark_stt_completed`)와 임대 시간 기준으로 앞당긴 정리(`expire_transcripts`), "외부 ML 전송과 기한"은 #280, #279의 동작이고, `mark_failed`와 `expire_leases`가 기한과 비교할 때 DB 시각을 한 번만 읽는 것은 #281의 동작이다. 셋 다 11/9 배포(run 42568179490)부터 운영에 있다. 앱 동의 화면(`consent_terms.dart`)은 아직 "녹음 원본은 분석 완료 후 즉시 삭제하며 최대 24시간"만 안내하고, 아래 서버 사본, DB 전사, 기기 녹음의 구분 문구는 반영하지 않았다. 문구 적용은 PM 확인 항목으로 남아 있다.

| 대상 | 보관과 삭제 기준 | 이번 변경 여부 |
| --- | --- | --- |
| 서버의 녹음 사본 | 정상 경로는 STT 직후 삭제 시도. 업로드 후 `data_expires_at`까지 정리하는 기존 기준 유지. 실패한 삭제는 대기열로 처리 | 실패 전사를 보관한다고 녹음 사본의 기한을 연장하지 않음 |
| DB 임시 전사 | 최초 STT 결과 저장 시점 + 24시간을 `transcript_expires_at`으로 저장. 리포트 저장이 먼저 끝나면 즉시 삭제 | 실패 즉시 삭제하던 동작을 남은 기한 동안 재처리에 쓰도록 변경 |
| 기기 앱 전용 폴더의 녹음 | 전송, 분석 성공이나 실패, 경과 시간만으로 삭제하지 않음. 로그아웃 시 유지하고 다른 계정에서는 찾지 못함. 탈퇴 시 삭제 시도, 앱 삭제 시 OS가 앱 전용 자료 제거 | 기존 develop `2f3c141`에도 있던 동작. 이번에는 이미 전송한 파일을 분석 재시도에서 찾는 경로를 추가 |

서버 녹음의 업로드 시각과 DB 전사의 최초 STT 저장 시각은 다르다. 두 기한을 합쳐서 “모두 녹음 후 24시간”이라고 안내하지 않는다. 위 기기 녹음은 갤러리의 사용자 사진 원본과 별개다.

### DB 삭제 경로

- `mark_stt_completed`: 최초 전사 저장 시 `TRANSCRIPT_RETENTION_SECONDS=86400`으로 기한을 정한다. 리포트까지 이어 가는 worker는 인계 임대도 함께 기록한다. 이어받은 작업도 같은 만료 시각을 쓰며, 남은 기한이 생성 단계 임대 시간보다 짧은 전사는 이어받지 않는다.
- `mark_failed`, `expire_leases`: 기한 전이면 실패 전사를 유지한다. 이미 만료된 경우에는 전사와 임대 정보를 정리한다. 한 문장에서 DB 시각을 한 번만 읽어 기한과 비교하므로, 기한 바로 그 순간에도 전사 유지와 삭제 시각 기록이 어긋나 CHECK 제약에 걸리지 않는다.
- `retry_report`: 원래 STT 시각과 만료 시각을 새 작업에 그대로 옮기고 이전 작업의 전사는 지운다. 재실패와 재요청으로 보관 기한을 늘리지 않는다.
- `complete_job`: 리포트 저장 트랜잭션에서 전사를 지운다.
- `expire_transcripts`: 실패한 작업을 포함해 만료된 전사를 지우고 `TRANSCRIPT_EXPIRED`로 기록한다. 모든 `sttCompleted` 작업(`--stt-only` 결과 포함)은 남은 기한이 임대 시간보다 짧아지면 리포트 생성을 시작할 수 없으므로 같은 방식으로 앞당겨 끝낸다. 실행 중인 `generatingReport`와 실패 작업의 전사는 원래 기한까지 둔다. 새 접수가 없어도 worker의 다음 `run_once`에서 실행한다.
- 계정 또는 프로필 삭제: 외래키 연쇄 삭제로 연결된 회차와 작업 전사도 삭제한다. 백업 사본의 삭제는 이 테스트 범위가 아니다.

### 외부 ML 전송과 기한

- 시작 조건: `claim_next`(재요청과 인계 임대가 끝난 작업)와 `mark_generating_report`(최초 생성)는 남은 전사 기한이 생성 단계 임대 시간 이상일 때만 `generatingReport`로 바꾼다. worker는 생성 제한 시간(기본 600초)이 임대보다 60초 이상 짧을 때만 시작하므로, 생성 중 새 외부 호출은 전사 기한 전에만 시작된다.
- 두 번째 전송 직전 확인: 리포트 호출 뒤 변경 제안 호출 전에 DB의 작업 행을 다시 읽는다. 행이 없거나(계정, 프로필, 회차 삭제) `generatingReport`가 아니거나 임대가 끝났으면 `WORKER_LEASE_EXPIRED`, 전사가 지워졌거나 기한이 지났으면 `TRANSCRIPT_EXPIRED`로 멈추고 전사를 다시 보내지 않는다.
- 남은 제한: 이미 보낸 리포트 호출은 되돌리지 못하고, 시작한 호출 하나는 생성 함수 쪽에서 끊을 수 없다. 외부 업체가 받은 요청의 보관과 삭제는 이 코드로 확인하지 않는다.

만료된 전사는 재요청에 사용하지 않는다. 다만 실제 DB 삭제는 worker의 정리 실행이나 상태 전이 때 이뤄진다. worker 중단, 긴 작업 처리나 DB 장애 동안은 삭제가 늦어질 수 있다. DB 자체 TTL이나 별도의 상시 삭제 작업을 구현한 것은 아니다. 처음 작성할 때는 운영 적용 전에 정리 주기와 지연 감시를 정하고 확인해야 한다고 적었다. 현재 구현 (2026-11-09 기준): 만료 전사 정리(`expire_transcripts`)는 speech-worker가 작업을 가져오기 전마다 실행하는 것뿐이고(대기 작업이 없으면 `SAEROK_SPEECH_WORKER_POLL_SECONDS`, 기본 2초 간격으로 다시 실행), 정리 지연 감시는 없다. 11/7 설치한 운영 점검 알림(운영 배포 기록)은 speech-worker가 꺼졌는지는 보지만, 만료 전사가 늦게 지워지는지는 따로 보지 않는다(`runtime_check`에 전사 항목 없음).

### 기기 삭제의 남은 제한

`profile_delete_screen.dart`는 서버 탈퇴 성공 후 `forgetAccount`로 기기 파일 삭제를 시도한다. 파일 삭제 예외를 화면에서 넘기며, 이 삭제를 재시도하는 영속 작업은 없다. 따라서 “탈퇴 완료이면 기기 녹음도 반드시 모두 삭제됐다”고 안내할 수 없다. 기존 동작이며 이번 복구 변경에서 새로 생긴 문제가 아니다. 기기 보관 안내와 삭제 실패 처리는 남은 확인 항목이다(develop `59190ba7`도 같은 동작). 임의로 성공 후 삭제나 24시간 기기 삭제를 추가하지 않는다.

[법률 검토 문서](../../docs/legal/README.md#실패-전사와-기기-녹음-보관의-로컬-수정안)와 [동의안](../../docs/legal/consent-draft.md#녹음과-임시-전사-보관-문구-수정안)의 서버, DB, 기기 구분을 함께 적용한다. 법률 적합성이나 실제 사용자 자료 사용을 승인한 문서가 아니다.

## 적용과 되돌리기

`d73f0b5ca921` migration은 실패 상태에서도 만료 전 전사를 남기도록 제약을 바꾼다. 사진 설명 migration `c62e19a4b308`(#205) 다음에 붙으므로 #204, #214, #205 다음에 병합한다. 같은 부모를 쓰는 다른 migration이 먼저 병합되면 이 파일의 `down_revision`을 다시 맞춘다.

재시도 이력 또는 실패 전사가 있으면 downgrade가 중단된다. 데이터를 삭제해서 강제로 되돌리지 않는다. 백업을 먼저 확보하고 코드와 DB를 함께 되돌릴 범위를 검토한다. 작성 당시에는 운영에서 migration을 실행하지 않았다.

실제로 #204, #214, #205, #213 순서로 병합됐고(2026-11-05), 11/5 운영 배포에서 이 migration을 실행했다([#187의 11/5 운영 배포 기록](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/issues/187#issuecomment-6652039046), `b7e2c4a9d153` → `a4f6c1d83b29` 6단계에 포함). 지금 운영 DB revision은 그 뒤의 `685f243e9f1f`이다(11/9 Deploy run 42568179490의 migration 단계와 사후 점검).

#279와 #280은 migration이 없다(두 PR을 병합한 develop `d9643466`의 migration head도 그 전과 같은 `e7c3a1f94d20`). 다만 #280 PR은 배포 뒤 할 일을 적었다. 배포 전부터 `sttCompleted`로 멈춰 있던 작업은 인계 임대가 없어 이어받지 않으므로, 배포 직후 운영 DB에서 `status = 'sttCompleted' AND retry_of_analysis_id IS NULL AND lease_expires_at IS NULL`인 행 수를 세고, 남은 행이 있으면 그 행의 `lease_expires_at`을 `now()`로 한 번 바꾼다. 운영에 `--stt-only` worker가 없다는 전제다. #280은 11/9 배포(run 42568179490)로 운영에 들어갔지만, 이 단계를 했다는 기록은 팀 운영 기록의 11/9 승인 배포 항목에 없다. 실행 여부는 따로 확인해야 한다.

## 검사 범위

임시 PostgreSQL과 합성 외부 응답으로 중복 클릭, 동시 요청, 타 계정, 동의 없음, 만료, 늦은 응답, 완료 리포트 중복 방지, STT와 S3를 호출하지 않는 리포트 재생성, 회차당 재요청 횟수 한도와 한도 뒤 전사가 만료된 회차의 녹음 재제출을 검사한다. 앱 테스트는 서버 응답과 기기 저장소 대역을 사용한다. 실제 Android 마이크, 운영 S3와 프로젝트 모델 성공 기록이 아니다. 11/9 승인 배포 뒤 실기기(Galaxy S22, develop `59190ba7`로 로컬에서 만든 debug 서명 APK, 시험 계정)에서 15초 동안 방 안 소리만 녹음한 회차는 리포트 실패로 끝났고, 다시 요청하자 앱이 기기 녹음을 다시 보냈으며 그 작업도 실패했다. 말소리가 없어 예상한 결과다(저장소 밖 팀 운영 기록). 말소리 녹음의 정상 리포트는 확인하지 못했고, 재요청 한도는 그때 확인 항목에 없었다.

`tests/test_speech_recovery.py`(#280 추가분)는 전사 저장 직후, 원본 삭제 요청 전과 리포트 시작 전에 worker가 죽은 상황을 만든다. 인계 임대 안에서는 다른 worker가 가져가지 않고, 임대가 끝나면 리포트를 한 번만 저장하며 빠진 원본 삭제 요청을 대기열에 남기는지 검사한다. 늦게 돌아온 원래 worker의 리포트 시작 거절, STT 단독 실행 결과와 만료 전사를 이어받지 않는 것도 확인한다. 실제 프로세스 강제 종료나 운영 DB 장애로 확인한 것은 아니다.

`tests/test_speech_retention.py`는 PostgreSQL에서 최초 STT부터 24시간, 재요청 시 기한 유지와 이전 사본 삭제, 실패와 임대 만료, 새 작업 없는 만료 정리, 성공 시 삭제, 계정과 프로필 삭제를 검사한다. 실패와 임대 만료 처리가 기한 경계에서 시각을 한 번만 읽는지는 시험 DB에만 둔 대역 `clock_timestamp()`로 확인한다. `tests/test_report_transcript_limit.py`(#279 추가분)는 남은 기한이 임대보다 짧은 작업의 생성 미시작과 정리, 두 생성 호출 사이의 삭제, 작업 종료와 전사 만료 때 변경 제안 호출을 하지 않는지 검사한다. `app/test/pending_uploads_test.dart`는 임시 폴더의 합성 파일로 전송 후 보관, 오래된 파일 보관, 계정 격리와 정상 탈퇴 삭제를 검사한다. 실제 휴대폰의 삭제 실패나 OS 제거까지 실행한 검증은 아니다.
