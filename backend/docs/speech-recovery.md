# 녹음 분석 실패 후 수동 복구

운영 적용은 하지 않았다. #184의 실패 회차 재처리를 다룬다. 전사 저장 뒤 리포트 시작 전에 worker가 멈춘 작업의 자동 이어받기도 함께 적는다.

| 상태 | 사용자 동작 | 서버 처리 |
| --- | --- | --- |
| 리포트 완료 | 기존 리포트 열기 | 다시 생성하지 않음 |
| 리포트 생성 실패, 전사 유효 | 홈에서 분석 다시 요청하기 | 새 작업 ID로 전사를 이동해 리포트만 생성 |
| STT 실패 또는 전사 만료 | 같은 버튼 | 서버가 `RECORDING_REQUIRED`로 답하면 기기 WAV 재제출 |
| 전사도 기기 녹음도 없음 | 복구 불가 안내 후 홈으로 | 소감과 회차는 유지. 리포트를 꾸며 만들지 않음 |
| 재요청 통신 실패 | 사용자가 다시 시도 | 자동 반복이나 WAV 우회 제출 안 함 |
| 회차당 재요청 3회를 모두 씀 | 다시 요청하지 않고 안내 | `REPORT_RETRY_LIMIT_EXCEEDED`(409). 새 작업을 만들지 않고 전사도 옮기지 않음 |
| 전사 저장 뒤 리포트 시작 전 worker 중단 | 처리 중 표시를 유지하고 기다림 | 인계 임대가 끝나면 worker가 같은 작업 ID로 리포트만 생성. 실패로 바꾸지 않음 |

## 저장과 중복 방지

- 실패한 작업의 전사는 기존 `transcript_expires_at`까지만 보관한다. 재요청으로 기한을 늘리지 않는다. 다만 기존 develop은 실패 즉시 전사를 지웠으므로, 실패 후 보관은 정책 변경이다. 이 변경은 2026-11-03 PM이 승인했다. 동의 화면 반영은 아래 확인 항목을 따른다.
- 새 작업 ID를 사용하므로 이전 작업의 늦은 모델 응답은 저장되지 않는다.
- 회차 행 잠금과 기존 활성 작업 유일 제약으로 중복 접수를 막는다. `retry_of_analysis_id`는 리포트 재시도의 이전 작업을 가리킨다.
- 리포트 저장 성공 시 전사를 지우는 기존 처리는 유지한다. 원본 녹음 삭제 실패는 별도 대기열에 남긴다.
- 원본을 이미 지운 상태에서 STT를 반복할 수 있다고 가정하지 않는다. 전사가 없으면 사용자가 기기에 남긴 파일을 다시 보낸다.
- 완료한 리포트, 다른 계정, 동의 철회를 재시도로 우회하지 않는다.
- worker가 `sttCompleted`에서 집어 가는 작업은 두 가지다. 재요청한 작업은 바로 가져간다. 리포트까지 이어 가던 worker가 전사 저장 때 둔 인계 임대(`SAEROK_SPEECH_ANALYSIS_LEASE_SECONDS`, 기본 900초) 안에 리포트 생성을 시작하지 못하고 멈춘 작업은 그 임대가 끝난 뒤 가져간다. STT 단독 실행 작업은 인계 임대가 없으므로 리포트 생성에 넘기지 않는다.
- 이어받기는 실패한 작업의 재시도가 아니다. 작업이 `generatingReport`로 바뀐 뒤 다시 `sttCompleted`로 돌아오지 않으므로 작업마다 한 번뿐이다. 이미 이어받은 작업이면 늦게 돌아온 원래 worker는 리포트 생성을 시작하지 못한다. 이어받은 worker는 리포트 생성 전에 S3를 부르지 않고, 원본 삭제 기록이 없으면 삭제 요청만 대기열에 남긴다. 리포트 생성이 실패하면 기존 실패 처리대로 원본 삭제를 다시 시도한다.
- 두 경우 모두 남은 전사 기한이 생성 단계 임대 시간(`SAEROK_SPEECH_ANALYSIS_LEASE_SECONDS`) 이상일 때만 집어 간다. 그보다 적게 남았으면 생성을 시작하지 않고 worker 정리 때 전사를 지우며 `TRANSCRIPT_EXPIRED`로 끝낸다. 이후 재요청은 `RECORDING_REQUIRED`이므로 기기 녹음을 다시 보낸다.
- 수동 재요청(6-5)은 면회 회차당 `SAEROK_REPORT_RETRIES_PER_SESSION`(기본 3)회까지다(2026-11-09 PM 결정). 재요청마다 전사를 외부 ML로 다시 보내기 때문이다. 회차 행을 잠근 뒤 그 회차에서 `retry_of_analysis_id`가 있는 작업 수를 세므로 동시 재요청에도 넘지 않는다. 처리 중인 재요청을 다시 보내 같은 작업을 돌려받는 경우는 세지 않는다. 한도를 넘은 요청은 전사가 남아 있어도 `REPORT_RETRY_LIMIT_EXCEEDED`이며, 남은 전사는 기존 기한 정리로 지운다. 그동안 6-2는 `REPORT_RETRY_AVAILABLE`로 재제출을 받지 않는다. 기기 녹음 재제출을 이 횟수에 넣을지는 정하지 않았다.
- 자동 재시도 횟수, 24시간 밖의 보관 연장, 과거 실패 작업의 일괄 재처리는 추가하지 않는다.

## 실패 전사와 기기 녹음의 보관 대조

상태: 2026-11-03 실패 전사 보관 변경은 PM 승인. 동의 문안의 실제 동의 화면 반영과 운영 적용은 아직이다. 최대 시간 값이 같다는 이유로 보관 정책이 그대로라고 설명하지 않는다.

| 대상 | 보관과 삭제 기준 | 이번 변경 여부 |
| --- | --- | --- |
| 서버의 녹음 사본 | 정상 경로는 STT 직후 삭제 시도. 업로드 후 `data_expires_at`까지 정리하는 기존 기준 유지. 실패한 삭제는 대기열로 처리 | 실패 전사를 보관한다고 녹음 사본의 기한을 연장하지 않음 |
| DB 임시 전사 | 최초 STT 결과 저장 시점 + 24시간을 `transcript_expires_at`으로 저장. 리포트 저장이 먼저 끝나면 즉시 삭제 | 실패 즉시 삭제하던 동작을 남은 기한 동안 재처리에 쓰도록 변경 |
| 기기 앱 전용 폴더의 녹음 | 전송, 분석 성공이나 실패, 경과 시간만으로 삭제하지 않음. 로그아웃 시 유지하고 다른 계정에서는 찾지 못함. 탈퇴 시 삭제 시도, 앱 삭제 시 OS가 앱 전용 자료 제거 | 기존 develop `2f3c141`에도 있던 동작. 이번에는 이미 전송한 파일을 분석 재시도에서 찾는 경로를 추가 |

서버 녹음의 업로드 시각과 DB 전사의 최초 STT 저장 시각은 다르다. 두 기한을 합쳐서 “모두 녹음 후 24시간”이라고 안내하지 않는다. 위 기기 녹음은 갤러리의 사용자 사진 원본과 별개다.

### DB 삭제 경로

- `mark_stt_completed`: 최초 전사 저장 시 `TRANSCRIPT_RETENTION_SECONDS=86400`으로 기한을 정한다. 리포트까지 이어 가는 worker는 인계 임대도 함께 기록한다. 이어받은 작업도 같은 만료 시각을 쓰며, 남은 기한이 생성 단계 임대 시간보다 짧은 전사는 이어받지 않는다.
- `mark_failed`, `expire_leases`: 기한 전이면 실패 전사를 유지한다. 이미 만료된 경우에는 전사와 임대 정보를 정리한다.
- `retry_report`: 원래 STT 시각과 만료 시각을 새 작업에 그대로 옮기고 이전 작업의 전사는 지운다. 재실패와 재요청으로 보관 기한을 늘리지 않는다.
- `complete_job`: 리포트 저장 트랜잭션에서 전사를 지운다.
- `expire_transcripts`: 실패한 작업을 포함해 만료된 전사를 지우고 `TRANSCRIPT_EXPIRED`로 기록한다. 모든 `sttCompleted` 작업(`--stt-only` 결과 포함)은 남은 기한이 임대 시간보다 짧아지면 리포트 생성을 시작할 수 없으므로 같은 방식으로 앞당겨 끝낸다. 실행 중인 `generatingReport`와 실패 작업의 전사는 원래 기한까지 둔다. 새 접수가 없어도 worker의 다음 `run_once`에서 실행한다.
- 계정 또는 프로필 삭제: 외래키 연쇄 삭제로 연결된 회차와 작업 전사도 삭제한다. 백업 사본의 삭제는 이 테스트 범위가 아니다.

### 외부 ML 전송과 기한

- 시작 조건: `claim_next`(재요청과 인계 임대가 끝난 작업)와 `mark_generating_report`(최초 생성)는 남은 전사 기한이 생성 단계 임대 시간 이상일 때만 `generatingReport`로 바꾼다. worker는 생성 제한 시간(기본 600초)이 임대보다 60초 이상 짧을 때만 시작하므로, 생성 중 새 외부 호출은 전사 기한 전에만 시작된다.
- 두 번째 전송 직전 확인: 리포트 호출 뒤 변경 제안 호출 전에 DB의 작업 행을 다시 읽는다. 행이 없거나(계정, 프로필, 회차 삭제) `generatingReport`가 아니거나 임대가 끝났으면 `WORKER_LEASE_EXPIRED`, 전사가 지워졌거나 기한이 지났으면 `TRANSCRIPT_EXPIRED`로 멈추고 전사를 다시 보내지 않는다.
- 남은 제한: 이미 보낸 리포트 호출은 되돌리지 못하고, 시작한 호출 하나는 생성 함수 쪽에서 끊을 수 없다. 외부 업체가 받은 요청의 보관과 삭제는 이 코드로 확인하지 않는다.

만료된 전사는 재요청에 사용하지 않는다. 다만 실제 DB 삭제는 worker의 정리 실행이나 상태 전이 때 이뤄진다. worker 중단, 긴 작업 처리나 DB 장애 동안은 삭제가 늦어질 수 있다. DB 자체 TTL이나 별도의 상시 삭제 작업을 구현한 것은 아니다. 운영 적용 전 정리 주기와 지연 감시를 정하고 확인해야 한다.

### 기기 삭제의 남은 제한

`profile_delete_screen.dart`는 서버 탈퇴 성공 후 `forgetAccount`로 기기 파일 삭제를 시도한다. 파일 삭제 예외를 화면에서 넘기며, 이 삭제를 재시도하는 영속 작업은 없다. 따라서 “탈퇴 완료이면 기기 녹음도 반드시 모두 삭제됐다”고 안내할 수 없다. 기존 동작이며 이번 복구 변경에서 새로 생긴 문제가 아니다. 기기 보관 안내와 삭제 실패 처리는 운영 적용 전 확인 항목으로 남긴다. 임의로 성공 후 삭제나 24시간 기기 삭제를 추가하지 않는다.

## 적용과 되돌리기

`d73f0b5ca921` migration은 실패 상태에서도 만료 전 전사를 남기도록 제약을 바꾼다. 사진 설명 migration `c62e19a4b308`(#205) 다음에 붙으므로 #204, #214, #205 다음에 병합한다. 같은 부모를 쓰는 다른 migration이 먼저 병합되면 이 파일의 `down_revision`을 다시 맞춘다.

재시도 이력 또는 실패 전사가 있으면 downgrade가 중단된다. 데이터를 삭제해서 강제로 되돌리지 않는다. 백업을 먼저 확보하고 코드와 DB를 함께 되돌릴 범위를 검토한다. 운영에서 migration을 실행하지 않았다.

## 검사 범위

임시 PostgreSQL과 합성 외부 응답으로 중복 클릭, 동시 요청, 타 계정, 동의 없음, 만료, 늦은 응답, 완료 리포트 중복 방지, STT와 S3를 호출하지 않는 리포트 재생성, 회차당 재요청 횟수 한도를 검사한다. 앱 테스트는 서버 응답과 기기 저장소 대역을 사용한다. 실제 Android 마이크, 운영 S3와 프로젝트 모델 성공 기록이 아니다.

`tests/test_speech_recovery.py`는 전사 저장 직후, 원본 삭제 요청 전과 리포트 시작 전에 worker가 죽은 상황을 만든다. 인계 임대 안에서는 다른 worker가 가져가지 않고, 임대가 끝나면 리포트를 한 번만 저장하며 빠진 원본 삭제 요청을 대기열에 남기는지 검사한다. 늦게 돌아온 원래 worker의 리포트 시작 거절, STT 단독 실행 결과와 만료 전사를 이어받지 않는 것도 확인한다. 실제 프로세스 강제 종료나 운영 DB 장애로 확인한 것은 아니다.

`tests/test_speech_retention.py`는 PostgreSQL에서 최초 STT부터 24시간, 재요청 시 기한 유지와 이전 사본 삭제, 실패와 임대 만료, 새 작업 없는 만료 정리, 성공 시 삭제, 계정과 프로필 삭제를 검사한다. `tests/test_report_transcript_limit.py`는 남은 기한이 임대보다 짧은 작업의 생성 미시작과 정리, 두 생성 호출 사이의 삭제, 작업 종료와 전사 만료 때 변경 제안 호출을 하지 않는지 검사한다. `app/test/pending_uploads_test.dart`는 임시 폴더의 합성 파일로 전송 후 보관, 오래된 파일 보관, 계정 격리와 정상 탈퇴 삭제를 검사한다. 실제 휴대폰의 삭제 실패나 OS 제거까지 실행한 검증은 아니다.
