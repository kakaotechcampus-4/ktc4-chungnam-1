# 녹음 분석 실패 후 수동 복구

로컬 검증용 변경이다. GitHub 게시와 운영 적용은 하지 않았다. #184의 실패 회차 재처리를 다룬다.

| 상태 | 사용자 동작 | 서버 처리 |
| --- | --- | --- |
| 리포트 완료 | 기존 리포트 열기 | 다시 생성하지 않음 |
| 리포트 생성 실패, 전사 유효 | 홈에서 분석 다시 요청하기 | 새 작업 ID로 전사를 이동해 리포트만 생성 |
| STT 실패 또는 전사 만료 | 같은 버튼 | 서버가 `RECORDING_REQUIRED`로 답하면 기기 WAV 재제출 |
| 전사도 기기 녹음도 없음 | 복구 불가 안내 후 홈으로 | 소감과 회차는 유지. 리포트를 꾸며 만들지 않음 |
| 재요청 통신 실패 | 사용자가 다시 시도 | 자동 반복이나 WAV 우회 제출 안 함 |

## 저장과 중복 방지

- 실패한 작업의 전사는 기존 `transcript_expires_at`까지만 보관한다. 재요청으로 보관 기간을 늘리지 않는다. 장기 전사 보관 정책을 새로 결정하는 변경이 아니다.
- 새 작업 ID를 사용하므로 이전 작업의 늦은 모델 응답은 저장되지 않는다.
- 회차 행 잠금과 기존 활성 작업 유일 제약으로 중복 접수를 막는다. `retry_of_analysis_id`는 리포트 재시도의 이전 작업을 가리킨다.
- 리포트 저장 성공 시 전사를 지우는 기존 처리는 유지한다. 원본 녹음 삭제 실패는 별도 대기열에 남긴다.
- 원본을 이미 지운 상태에서 STT를 반복할 수 있다고 가정하지 않는다. 전사가 없으면 사용자가 기기에 남긴 파일을 다시 보낸다.
- 완료한 리포트, 다른 계정, 동의 철회를 재시도로 우회하지 않는다.
- 재요청한 작업만 worker가 `sttCompleted`에서 집어 간다. 기존 STT 단독 실행 작업을 임의로 리포트 생성에 넘기지 않는다.
- 자동 재시도 횟수, 24시간 밖의 보관 연장, 과거 실패 작업의 일괄 재처리는 추가하지 않는다.

## 적용과 되돌리기

`d73f0b5ca921` migration은 실패 상태에서도 만료 전 전사를 남기도록 제약을 바꾼다. 현재 로컬 의존성은 사진 설명 migration `c62e19a4b308` 이후다. PR을 나눌 때 최종 migration 순서를 다시 맞춘다.

재시도 이력 또는 실패 전사가 있으면 downgrade가 중단된다. 데이터를 삭제해서 강제로 되돌리지 않는다. 백업을 먼저 확보하고 코드와 DB를 함께 되돌릴 범위를 검토한다. 운영에서 migration을 실행하지 않았다.

## 검사 범위

임시 PostgreSQL과 합성 외부 응답으로 중복 클릭, 동시 요청, 타 계정, 동의 없음, 만료, 늦은 응답, 완료 리포트 중복 방지, STT와 S3를 호출하지 않는 리포트 재생성을 검사한다. 앱 테스트는 서버 응답과 기기 저장소 대역을 사용한다. 실제 Android 마이크, 운영 S3와 프로젝트 모델 성공 기록이 아니다.
