# 두 번째 면회까지의 자동 검사

`tests/test_second_visit_flow.py`는 실제 API 라우터와 PostgreSQL, 카드 worker 및
녹음 worker를 연결한다. Google 인증과 S3, STT 서버, 카드와 리포트 생성 함수만
합성 응답으로 대신한다. 운영 서버에는 접속하지 않는다.

## 검사하는 흐름

1. API로 프로필과 세부 정보를 저장하고 첫 카드 생성을 요청한다.
2. 카드 worker가 만든 12장을 저장하고 API로 조회한다.
3. 카드 두 장을 선택해 면회를 만들고 소감과 녹음을 제출한다. 중복 제출은 같은 작업으로 묶이는지 검사한다.
4. 녹음 worker가 전사 결과를 받아 리포트와 이야기 후보를 저장한다. API 인스턴스를 새로 만들어도 같은 리포트를 읽어야 한다.
5. 승인 전 후보는 일대기와 카드 입력에 없어야 한다. 보호자가 고친 내용으로 승인한 뒤 일대기와 다음 카드 입력에 포함돼야 한다.
6. 보호자가 직접 고른 주제 제외와 미사용 카드 평가를 각각 보존해야 한다. 미사용을 제외로 바꾸지 않는다.
7. 다음 회차 카드를 준비한 뒤 일대기 내용을 다시 고친다. API를 다시 띄워도 `needsRefresh`가 유지되고, 갱신 전 카드로 면회를 시작하면 `CARD_SET_NEEDS_REFRESH`로 거절해야 한다.
8. 갱신 요청에서 누적 정정 내용을 생성 함수에 전달하고 새 카드 12장을 저장한다. 갱신이 끝난 카드로 두 번째 면회를 시작할 수 있어야 한다.
9. 별도 실패 사례에서는 생성 함수가 제외된 주제를 다시 반환한다. 기존 BE 검증이 생성 전체를 실패로 처리하고 부분 저장이나 정정 전 카드 사용을 허용하지 않는지 검사한다.

이 검사는 실제 모델이 특정 이야기를 반드시 선택한다고 주장하지 않는다. 합성 생성 함수가
BE의 최신 입력을 받는지와 그 결과의 저장을 검사한다. 실제 모델 평가에서는 승인한 모든
이야기가 카드 문구에 나오는 것을 요구하지 않고, 정정 전 사실의 재사용과 명시적 제외 위반을
확인해야 한다.

## 실행

`backend/`에서 `SAEROK_TEST_DATABASE_URL`을 **생성과 삭제가 허용된 전용 테스트 DB**로
설정하고 실행한다. 기존 fixture가 테스트마다 별도 DB를 만들고 끝나면 제거한다.
환경 변수가 없으면 DB 검사가 건너뛰어진다. 건너뛴 실행은 통과 근거로 쓰지 않는다.

```powershell
uv sync --locked
uv run --locked pytest tests/test_second_visit_flow.py -ra
```

## 별도로 남겨야 하는 검증

배포 API에 합성 녹음을 보내는 별도 도구는 [API 연결 검사](api-cycle-runner.md)에 있다.
기본 실행은 요청을 보내지 않으며 실제 사용에는 전용 시험 계정과 외부 호출 승인이 필요하다.

- 실제 배포 버전, migration과 앱 빌드의 일치 여부
- 실제 Android의 녹음과 화면 잠금, 업로드, 재실행
- S3와 GPU, 실제 모델 호출 및 처리 시간
- 실제 전사에서 이야기 후보가 만들어지고 보호자 확인 후 다음 카드에 전달되는 기록
- 옛 앱 versionCode 3과 새 BE의 호환성

자동 검사 통과를 실제 배포나 실기기 성공으로 기록하지 않는다. 운영 자료 대신 허가된
시험 계정과 자료를 사용하며 실제 계정의 이야기 후보를 자동 승인하지 않는다.
