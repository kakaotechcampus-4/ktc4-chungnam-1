# 프로필 사진 분석 연결

#183. AI 사진 분석 선택 동의(`photoAnalysis`)를 한 계정의 프로필 사진만 분석한다. 11/7 실제 ML API(`gpt-6-luna`)로 공개 저장소의 합성, 예시 사진 4장을 분석해 2~3초 안에 형식에 맞는 설명을 받았다. 실제 사용자 사진은 아직 확인하지 않았다. 11/8 운영 서버에서 공개 사진 43장을 두 번씩 분석한 결과(86건 모두 완료, 중앙값 12.5초)는 `stability-test-20261108.md`에 있다.

운영에서는 11/8 Deploy run 42385596940(develop `9e292149`, #257 포함)에서 `photo-worker`를 처음 띄웠고, 이후 배포에서도 api, card-worker, speech-worker와 함께 교체한다. 현재 운영은 run 42485750502가 배포한 develop `9c2b8276`이다.

## 처리

프로필 사진 업로드 → photos.pending → 사진 worker 임대 → 짧은 S3 조회 주소 → 기존 ML API 공통 호출 → 설명 형식 검사 → AI 설명, 모델과 프롬프트 버전 저장 → 조회 및 다음 카드 입력.

- 면회 사진은 분석하지 않는다. EXIF나 파일명은 입력으로 전달하지 않는다.
- 별도 태그 선택이나 사진 설명 승인 화면을 만들지 않는다. 설명 수정 API는 선택적으로 사용한다.
- 보호자가 고친 설명은 AI 원문과 분리한다. 늦게 받은 AI 결과로 정정을 덮어쓰지 않는다.
- 제한 시간을 넘기거나 삭제된 사진, 임대를 잃은 작업의 결과는 저장하지 않는다. 생성 스레드는 DB 연결을 받지 않는다.
- 분석이 끝난 사진은 새 카드 재료로 보고 다음 카드부터 쓴다. 사진을 새로 올릴 때처럼 이미 만든 카드 묶음을 갱신 필요(`needsRefresh`)로 표시하지 않는다. 온보딩 `마치기`에서 첫 카드를 바로 만들기 때문에, 분석 완료로 표시하면 첫 묶음이 늘 다시 만들 대상이 되기 때문이다. 그래서 첫 카드에는 그때 분석 중이던 사진이 빠질 수 있다.
- 카드 생성 중에 입력에 쓴 사진이 지워졌거나 설명이 바뀌면 갱신 필요로 표시한다. 생성 중에 분석이 끝나 새로 생긴 사진은 표시하지 않는다. 다음 대화 준비에서 카드 12장을 다시 생성하는 기존 규칙을 따른다.
- 현재 구현 (2026-11-09 기준): 위 두 항목은 #275(2026-11-09 develop 병합)의 동작이며 운영에는 아직 배포하지 않았다. 운영(develop `9c2b8276`)은 분석이 끝나면 보호자가 쓴 설명이 없는 사진에 한해 면회에 안 쓴 완료 묶음을 갱신 필요로 표시하고, 카드 생성이 끝날 때도 생성 중에 새로 분석된 사진까지 비교해 갱신 필요로 표시한다. 그래서 운영에서는 온보딩 직후 받은 첫 카드가 갱신 필요로 바뀔 수 있다.
- SDK 자동 재시도는 기존 공통 설정처럼 0회다. 실패한 사진의 재분석 API는 이번 변경에 없다.

## 동의와 실행

- 동의 받기: 가입 동의(`photoAnalysis`, 기본 거부)와 선택 동의 변경 API 1-6에 연결돼 있다(#257). 앱은 동의하지 않은 계정에 "분석 중" 대신 설명 입력칸을 바로 보여 주고(#261), 사진을 올리기 직전에 동의 시트를 띄운다(#272). 시트에서 거절하거나 닫아도 사진은 분석 없이 올라간다. 거절하면 앱이 켜져 있는 동안, "다시 띄우지 않기"를 고르면 이 기기에서 그 계정에는 다시 띄우지 않는다. 앱 변경(#261, #272)은 develop 앱 기준이며 BE 배포와 별개로 새 앱 빌드가 설치돼야 사용자에게 반영된다.
- 사진 자체를 서버에 보관하는 별도 동의(사진 보관 동의)는 구현하지 않았다. 이 문서의 동의는 AI 사진 분석 동의만 가리킨다.
- 가져오기: `pending`인 프로필 사진 중 계정의 현재 동의(`current_consents.photo_analysis`)가 켜진 것만 가져간다. 동의하지 않은 계정의 사진은 `pending`으로 남고, 나중에 동의하면 그때 분석한다.
- 저장 직전에 동의를 다시 확인한다. 분석 중에 동의를 거뒀으면 결과를 버리고 사진을 `pending`으로 되돌린다.
- 이미 저장된 AI 설명을 철회 때 지울지는 법률 문서의 "문안 적용 전 확인" 항목이라 정하지 않았다(PM 확인 필요). 지금 코드는 철회해도 저장된 AI 설명을 지우지 않고, 카드 입력도 동의와 관계없이 완료된 설명을 읽는다(`card_sets.py`). 보호자가 직접 쓴 설명은 동의와 관계없이 카드에 쓴다.
- 운영은 compose의 `photo-worker`(profile `workers`)로 띄우며, 승인 배포 workflow의 기본 교체 대상(`DEPLOY_SERVICES`)에 들어 있다. 로컬에서는 다음 명령을 쓴다.

```sh
uv run python -m app.workers.photo_analysis --once
```

필수 설정은 DB, 등록 사진 버킷과 ML API 키다. 키는 문서나 GitHub에 넣지 않는다.

| 설정 | 기본값 | 용도 |
| --- | --- | --- |
| SAEROK_PHOTO_ANALYSIS_MODEL | 비어 있음 | 비어 있으면 현재 report_generation_model 설정을 사용. 공통 ENDPOINTS에 등록된 모델만 허용 |
| SAEROK_PHOTO_ANALYSIS_TIMEOUT_SECONDS | 120 | URL 발급부터 설명 생성 응답까지의 전체 제한 |
| SAEROK_PHOTO_ANALYSIS_LEASE_SECONDS | 180 | 제한 시간에 저장 여유 60초를 더한 임대 |
| SAEROK_PHOTO_WORKER_POLL_SECONDS | 2 | 대기열 조회 간격 |

위 시간은 코드 기본값이며 실제 사진 성능을 보장하지 않는다. 처음 작성할 때는 모델의 실제 이미지 입력 지원과 처리 시간을 배포 전 확인하기로 했고 운영 Compose 서비스를 추가하지 않았다. 그 뒤 #257에서 `photo-worker`를 compose와 배포 대상에 넣었고, 11/8 운영 시험에서 공개 사진 86건은 모두 완료됐다(중앙값 12.5초). 실제 사용자 사진의 처리 시간은 확인하지 않았다.

## 실제 사용자 자료 적용 전

처음 이 문서를 쓸 때 남긴 연결 항목(가입과 동의 변경 작업에 사진 분석 항목 연결, 대기열에서 최신 동의 확인, 결과 저장 전 철회 재확인)은 #257에서 연결됐다(위 "동의와 실행"). 처음에는 이미 열린 동의 관련 팀원 PR을 수정하지 않고 별도 통합 검토 뒤 운영 제한을 풀기로 했다. 사진과 프로필 삭제 후 늦은 결과가 살아나지 않는 검사도 유지한다.

남은 것:

- 실제 사용자 사진으로 한 확인은 없다.
- 철회 뒤 이미 저장된 AI 설명의 처리(위 PM 확인 항목).
- 별도의 사진 보관 동의는 2026-10-14 PM 결정([ADR-001](../../docs/architecture/decisions/ADR-001-consent-and-temporary-processing.md#사진-보관과-ai-분석-동의-시점과-저장-방식))에 있지만 아직 필드와 API가 없다(구현하지 않음).
- 앱 동의 문구(`consent_terms.dart`의 `photoAnalysis` 처리 방식)는 "AI 설명은 보호자가 확인하기 전까지 사실로 반영하지 않음"이라고 적지만, 지금 코드는 확인 단계 없이 완료된 AI 설명을 카드 입력에 쓴다(`card_sets.py`, 생애 사실로는 저장하지 않음). 문구와 동작이 맞는지, 어느 쪽을 맞출지는 PM 확인이 필요하다.

## 검증

- 임시 PostgreSQL과 합성 사진: 업로드, 작업 처리, 조회, 카드 입력 연결.
- 수정 우선, 삭제 및 임대 만료 후 결과 폐기, 전체 시간 초과와 늦은 스레드 결과 차단.
- 카드 생성 뒤나 생성 중에 분석이 끝나도 묶음을 갱신 필요로 표시하지 않음. 생성 중 입력 사진의 설명이 바뀌면 갱신 필요로 표시함(#275의 테스트, 운영 미배포).
- 위 자동 테스트는 실제 S3와 ML API를 호출하지 않는다.
- 그 뒤 11/7 실제 ML API로 공개 저장소 사진 4장, 11/8 운영 서버에서 공개 사진 43장 두 번씩 86건을 분석했다(`stability-test-20261108.md`의 "사진 설명"). 실제 사용자 사진과 실제 사용자의 동의 흐름은 아직 확인하지 않았다.

이미지 입력 형식은 [LangChain 공식 메시지 문서](https://docs.langchain.com/oss/python/langchain/messages)의 멀티모달 메시지 구조를 따른다.
