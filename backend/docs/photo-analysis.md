# 프로필 사진 분석 연결

#183. AI 사진 분석 선택 동의(`photoAnalysis`)를 한 계정의 프로필 사진만 분석한다. 11/7 실제 ML API(`gpt-6-luna`)로 공개 저장소의 합성, 예시 사진 4장을 분석해 2~3초 안에 형식에 맞는 설명을 받았다. 실제 사용자 사진은 아직 확인하지 않았다. 11/8 운영 서버에서 공개 사진 43장을 두 번씩 분석한 결과는 `stability-test-20261108.md`에 있다.

## 처리

프로필 사진 업로드 → photos.pending → 사진 worker 임대 → 짧은 S3 조회 주소 → 기존 ML API 공통 호출 → 설명 형식 검사 → AI 설명, 모델과 프롬프트 버전 저장 → 조회 및 다음 카드 입력.

- 면회 사진은 분석하지 않는다. EXIF나 파일명은 입력으로 전달하지 않는다.
- 별도 태그 선택이나 사진 설명 승인 화면을 만들지 않는다. 설명 수정 API는 선택적으로 사용한다.
- 보호자가 고친 설명은 AI 원문과 분리한다. 늦게 받은 AI 결과로 정정을 덮어쓰지 않는다.
- 제한 시간을 넘기거나 삭제된 사진, 임대를 잃은 작업의 결과는 저장하지 않는다. 생성 스레드는 DB 연결을 받지 않는다.
- 분석이 끝난 사진은 새 카드 재료로 보고 다음 카드부터 쓴다. 사진을 새로 올릴 때처럼 이미 만든 카드 묶음을 갱신 필요(`needsRefresh`)로 표시하지 않는다. 온보딩 `마치기`에서 첫 카드를 바로 만들기 때문에, 분석 완료로 표시하면 첫 묶음이 늘 다시 만들 대상이 되기 때문이다. 그래서 첫 카드에는 그때 분석 중이던 사진이 빠질 수 있다.
- 카드 생성 중에 입력에 쓴 사진이 지워졌거나 설명이 바뀌면 갱신 필요로 표시한다. 생성 중에 분석이 끝나 새로 생긴 사진은 표시하지 않는다. 다음 대화 준비에서 카드 12장을 다시 생성하는 기존 규칙을 따른다.
- SDK 자동 재시도는 기존 공통 설정처럼 0회다. 실패한 사진의 재분석 API는 이번 변경에 없다.

## 동의와 실행

- 가져오기: `pending`인 프로필 사진 중 계정의 현재 동의(`current_consents.photo_analysis`)가 켜진 것만 가져간다. 동의하지 않은 계정의 사진은 `pending`으로 남고, 나중에 동의하면 그때 분석한다.
- ML 업체를 부르기 바로 전(조회 주소를 만든 뒤)에 동의를 DB에서 다시 읽는다. 가져간 뒤 동의를 거뒀으면 업체를 부르지 않고 사진을 `pending`으로 되돌린다. 저장 때와 같이 프로필 행을 먼저 잠그며, 이 짧은 트랜잭션은 업체를 부르기 전에 끝낸다.
- 결과를 저장하기 직전에 동의를 한 번 더 확인한다. 업체를 부른 뒤 동의를 거뒀으면 결과를 버리고 사진을 `pending`으로 되돌린다. 두 확인 모두 새 상태나 오류 코드를 쓰지 않는다.
- 철회(2026-11-09 PM 결정): 1-6에서 `photoAnalysis: false`를 받으면 같은 트랜잭션에서 그 계정 프로필 사진 중 `completed`인 것의 AI 설명, 모델과 프롬프트 버전을 비우고 `pending`으로 되돌린다(`accounts._discard_ai_photo_descriptions`). 보호자가 쓴 설명(`user_description`)은 지우지 않으며 동의와 관계없이 조회와 카드 입력에 쓴다.
- 지운 사진 중 보호자 설명이 없는 것이 있으면 그 프로필에서 아직 면회에 쓰지 않은 완료 묶음을 갱신 필요(`needsRefresh`)로 표시한다. 카드를 만드는 중이어도 동의 변경은 거절하지 않는다. 그 생성은 철회 전 설명으로 계속되고, 묶음은 저장할 때 입력 뒤 사진 설명이 바뀐 것을 보고 갱신 필요로 저장된다.
- 철회도 그 계정의 프로필 행을 먼저 잠근다. 카드 저장, 분석 결과 저장과 같은 순서라서 철회와 동시에 저장되는 분석 결과가 지운 설명을 되살리지 않는다.
- 다시 동의하면 worker가 `pending`인 사진을 기존 조건대로 다시 가져가 분석한다. `failed` 사진은 설명이 없어 철회 때 그대로 두고, 다시 동의해도 재분석하지 않는다.
- AI 설명에서 이미 만든 대화 주제, 지난 카드 문구와 카드 생성 기록(`card_sets.generation_log`의 `input`)에 남은 설명 사본은 철회 때 지우지 않는다. 이 처리는 정하지 않았다.
- 운영은 compose의 `photo-worker`(profile `workers`)로 띄운다. 로컬에서는 다음 명령을 쓴다.

```sh
uv run python -m app.workers.photo_analysis --once
```

필수 설정은 DB, 등록 사진 버킷과 ML API 키다. 키는 문서나 GitHub에 넣지 않는다.

| 설정 | 기본값 | 용도 |
| --- | --- | --- |
| SAEROK_PHOTO_ANALYSIS_MODEL | 비어 있음 | 비어 있으면 현재 report_generation_model 설정을 사용. 공통 ENDPOINTS에 등록된 모델만 허용 |
| SAEROK_PHOTO_ANALYSIS_TIMEOUT_SECONDS | 120 | URL 발급, 호출 전 동의 확인부터 설명 생성 응답까지의 전체 제한 |
| SAEROK_PHOTO_ANALYSIS_LEASE_SECONDS | 180 | 제한 시간에 저장 여유 60초를 더한 임대 |
| SAEROK_PHOTO_WORKER_POLL_SECONDS | 2 | 대기열 조회 간격 |

위 시간은 로컬 실행 기본값이며 실제 사진 성능을 보장하지 않는다. 모델의 실제 이미지 입력 지원과 처리 시간은 배포 전 확인한다.

## 실제 사용자 자료 적용 전

가입과 동의 변경(1-6)의 사진 분석 항목, 대기열의 최신 동의 확인, 업체 호출 전과 결과 저장 전의 철회 확인, 철회 때 AI 설명 삭제는 들어왔다. 실행 환경으로 막는 장치는 없어 운영에서도 동의한 계정의 사진을 분석한다. 사진과 프로필 삭제 후 늦은 결과가 살아나지 않는 검사도 유지한다. 앱 동의 문구와 약관 버전 반영, AI 설명에서 만든 주제와 지난 카드의 처리 등 실제 사용자 사진에 쓰기 전 남은 조건은 [법률 문서](../../docs/legal/README.md#사진-보관과-분석에-대한-pm-수정안)를 따른다. 시험 통과를 실제 자료 사용 승인으로 보지 않는다.

## 검증

- 임시 PostgreSQL과 합성 사진: 업로드, 작업 처리, 조회, 카드 입력 연결.
- 수정 우선, 삭제 및 임대 만료 후 결과 폐기, 전체 시간 초과와 늦은 스레드 결과 차단.
- 카드 생성 뒤나 생성 중에 분석이 끝나도 묶음을 갱신 필요로 표시하지 않음. 생성 중 입력 사진의 설명이 바뀌면 갱신 필요로 표시함.
- 동의: 동의하지 않은 계정의 사진은 가져가지 않음. 가져간 뒤 업체 호출 전에 철회하면 부르지 않고 `pending`, 그사이 다른 선택 동의만 바뀌면 그대로 부름. 호출 뒤 철회하면 결과를 버림.
- 철회(`tests/test_photo_consent_withdrawal.py`): AI 설명 삭제와 보호자 설명 유지, 미사용 묶음 갱신 표시, 카드 생성 중 철회, 재동의 뒤 재분석, 저장 중인 결과와 겹친 철회의 프로필 잠금.
- 위 시험은 실제 S3와 ML API를 부르지 않는다. 사진을 실제로 이해하는 품질과 실제 앱에서의 철회와 재동의는 확인하지 않았다. 실제 API와 운영 서버에서 확인한 것은 머리말의 11/7, 11/8 기록이다.

이미지 입력 형식은 [LangChain 공식 메시지 문서](https://docs.langchain.com/oss/python/langchain/messages)의 멀티모달 메시지 구조를 따른다.
