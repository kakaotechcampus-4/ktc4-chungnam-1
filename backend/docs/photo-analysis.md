# 프로필 사진 분석 연결

#183. AI 사진 분석 선택 동의(`photoAnalysis`)를 한 계정의 프로필 사진만 분석한다. 11/7 실제 ML API(`gpt-6-luna`)로 공개 저장소의 합성, 예시 사진 4장을 분석해 2~3초 안에 형식에 맞는 설명을 받았다. 실제 사용자 사진은 아직 확인하지 않았다. 11/8 운영 서버에서 공개 사진 43장을 두 번씩 분석한 결과는 `stability-test-20261108.md`에 있다.

## 처리

프로필 사진 업로드 → photos.pending → 사진 worker 임대 → 짧은 S3 조회 주소 → 기존 ML API 공통 호출 → 설명 형식 검사 → AI 설명, 모델과 프롬프트 버전 저장 → 조회 및 다음 카드 입력.

- 면회 사진은 분석하지 않는다. EXIF나 파일명은 입력으로 전달하지 않는다.
- 별도 태그 선택이나 사진 설명 승인 화면을 만들지 않는다. 설명 수정 API는 선택적으로 사용한다.
- 보호자가 고친 설명은 AI 원문과 분리한다. 늦게 받은 AI 결과로 정정을 덮어쓰지 않는다.
- 제한 시간을 넘기거나 삭제된 사진, 임대를 잃은 작업의 결과는 저장하지 않는다. 생성 스레드는 DB 연결을 받지 않는다.
- 첫 카드 작업은 요청 당시 등록된 프로필 사진의 분석을 기다린다. 동의가 없거나 사진이 없으면 바로 카드 대기열로 간다. 첫 묶음이 완성된 뒤 추가한 사진은 다음 카드부터 쓴다. 분석 완료만으로 기존 묶음을 갱신 필요(`needsRefresh`)로 표시하지 않는다.
- 카드 생성 중에 입력에 쓴 사진이 지워졌거나 설명이 바뀌면 갱신 필요로 표시한다. 생성 중에 분석이 끝나 새로 생긴 사진은 표시하지 않는다. 다음 대화 준비에서 카드 12장을 다시 생성하는 기존 규칙을 따른다.
- SDK 자동 재시도는 0회다. 첫 카드 준비 중 실패한 사진은 보호자가 4-7에서 재시도를 고를 수 있다. 첫 카드 준비가 끝난 사진의 일반 재분석 API는 없다.

## 첫 카드의 사진 대기

- 첫 성공 묶음이 없는 프로필만 기다린다. 4-1이 사진 ID 목록과 기한을 `card_sets`에 저장한다. 처음 등록한 사진 5장이 있으면 5장 모두 준비돼야 카드 worker가 가져간다. 대기 중 새로 추가한 사진은 이 목록에 더하지 않는다.
- AI 설명 분석 완료 또는 보호자 설명이 있는 사진을 준비 완료로 센다. 삭제된 사진은 대기 대상에서 뺀다. 사진 worker와 카드 worker가 별도로 돌며, 기다리는 작업이 다른 프로필의 카드 생성을 막지 않는다.
- 분석 실패, 사진 worker 임대 만료, 대기 시간 초과, 동의 철회는 4-2의 `photoPreparation.state=choice`로 알린다. 준비되지 않은 사진을 자동으로 빼고 진행하지 않는다.
- 보호자는 `사진 분석 다시 시도` 또는 `완료된 사진으로 카드 만들기`를 고른다. 준비된 사진이 0장이면 `사진 없이 카드 만들기`다. 재시도는 실패하거나 임대가 만료된 사진만 다시 대기열에 넣는다. 실행 중인 사진은 중복 호출하지 않는다. 카드 작업 ID는 유지한다.
- 앱을 닫아도 사진 worker가 계속 처리한다. 모두 준비되면 카드 worker가 상태를 바꾸고 생성한다. 실패 시 선택은 서버에 남고 앱 재진입 때 복원한다. 앱의 연결 실패가 서버 작업을 취소하지 않는다.
- `SAEROK_CARD_PHOTO_WAIT_TIMEOUT_SECONDS` 기본값은 180초다. 성능 보장 시간이 아니라 재시도 또는 계속 진행 선택을 제시하는 기준이다. 사진 대기 시간은 기존 카드 worker 시작 제한과 실행 임대 시간에 포함하지 않는다.
- 사진이 AI 입력에 들어가는 것과 최종 카드에 반드시 선택되는 것은 다르다. 사진별 카드 할당량, 모델과 프롬프트는 바꾸지 않았다.

### 적용 조건

Migration `a926d137e405` 적용 후 새 API와 카드 worker를 같은 버전으로 실행한다. 구버전 worker는 사진 대기를 모르므로 혼용하지 않는다. FE의 진행률과 선택 UI도 함께 배포해야 한다. 구버전 앱은 추가 필드를 무시하고 선택 없이 기다릴 수 있다.

기존에 생성한 카드와 진행 중인 작업에는 사진 대기를 소급 적용하지 않는다. 이미 사진 없이 만든 카드도 자동 재생성하지 않는다. 운영 배포, 기존 카드 정리와 스토어 업데이트는 별도 작업이다.

## 동의와 실행

- 가져오기: `pending`인 프로필 사진 중 계정의 현재 동의(`current_consents.photo_analysis`)가 켜진 것만 가져간다. 동의하지 않은 계정의 사진은 `pending`으로 남고, 나중에 동의하면 그때 분석한다.
- ML 업체를 부르기 바로 전(조회 주소를 만든 뒤)에 동의를 DB에서 다시 읽는다. 가져간 뒤 동의를 거뒀으면 업체를 부르지 않고 사진을 `pending`으로 되돌린다. 저장 때와 같이 프로필 행을 먼저 잠그며, 이 짧은 트랜잭션은 업체를 부르기 전에 끝낸다.
- 결과를 저장하기 직전에 동의를 한 번 더 확인한다. 업체를 부른 뒤 동의를 거뒀으면 결과를 버리고 사진을 `pending`으로 되돌린다. 두 확인 모두 새 상태나 오류 코드를 쓰지 않는다.
- 철회(2026-11-09 PM 결정): 1-6에서 `photoAnalysis: false`를 받으면 같은 트랜잭션에서 그 계정 프로필 사진 중 `completed`인 것의 AI 설명, 모델과 프롬프트 버전을 비우고 `pending`으로 되돌린다(`accounts._discard_ai_photo_descriptions`). 보호자가 쓴 설명(`user_description`)은 지우지 않으며 동의와 관계없이 조회와 카드 입력에 쓴다.
- 지운 사진 중 보호자 설명이 없는 것이 있으면 그 프로필에서 아직 면회에 쓰지 않은 완료 묶음을 갱신 필요(`needsRefresh`)로 표시한다. 카드를 만드는 중이어도 동의 변경은 거절하지 않는다. 그 생성은 철회 전 설명으로 계속되고, 묶음은 저장할 때 입력 뒤 사진 설명이 바뀐 것을 보고 갱신 필요로 저장된다.
- 철회도 그 계정의 프로필 행을 먼저 잠근다. 카드 저장, 분석 결과 저장과 같은 순서라서 철회와 동시에 저장되는 분석 결과가 지운 설명을 되살리지 않는다.
- 다시 동의하면 worker가 `pending`인 사진을 기존 조건대로 다시 가져가 분석한다. `failed` 사진은 설명이 없어 철회 때 그대로 두고, 다시 동의해도 재분석하지 않는다.
- AI 설명에서 이미 만든 대화 주제와 지난 카드 문구는 철회 때 지우지 않는다. 이 처리는 정하지 않았다. 카드 생성 기록(`card_sets.generation_log`)에는 사진 설명을 복사하지 않고 사진 ID만 남기므로(2026-11-08 PM 결정, 이전 기록은 migration `685f243e9f1f`가 고친다) 철회 때 따로 지울 설명 사본은 없다.
- 설명이 지워진 사진(보호자 설명 없음)은 카드 입력(4-1의 `photos`)에서 빠진다. 근거가 그런 사진뿐인 주제도 제외 여부와 상관없이 다음 카드 생성 입력에서 빠지고, 다시 동의해 분석이 끝나면 다시 들어간다. 주제 행은 지우지 않는다([API 4-1](../../docs/architecture/api-spec.md#4-1-카드-생성-처리)의 `topics`).
- 운영은 compose의 `photo-worker`(profile `workers`)로 띄운다. 로컬에서는 다음 명령을 쓴다.

```sh
uv run python -m app.workers.photo_analysis --once
```

필수 설정은 DB, 등록 사진 버킷과 ML API 키다. 키는 문서나 GitHub에 넣지 않는다.

| 설정 | 기본값 | 용도 |
| --- | --- | --- |
| SAEROK_PHOTO_ANALYSIS_MODEL | 비어 있음 | 비어 있으면 현재 report_generation_model 설정을 사용. 공통 ENDPOINTS에 등록된 모델만 허용 |
| SAEROK_PHOTO_ANALYSIS_TIMEOUT_SECONDS | 120 | URL 발급과 AI 호출의 공통 마감. DB 동의 확인은 남은 시간으로 잠금 및 쿼리 제한을 걸고 트랜잭션 정리 후 마감을 재확인 |
| SAEROK_PHOTO_ANALYSIS_LEASE_SECONDS | 180 | 제한 시간에 저장 여유 60초를 더한 임대 |
| SAEROK_PHOTO_WORKER_POLL_SECONDS | 2 | 대기열 조회 간격 |

위 시간은 로컬 실행 기본값이며 실제 사진 성능을 보장하지 않는다. 모델의 실제 이미지 입력 지원과 처리 시간은 배포 전 확인한다.

## 실제 사용자 자료 적용 전

가입과 동의 변경(1-6)의 사진 분석 항목, 대기열의 최신 동의 확인, 업체 호출 전과 결과 저장 전의 철회 확인, 철회 때 AI 설명 삭제는 들어왔다. 실행 환경으로 막는 장치는 없어 운영에서도 동의한 계정의 사진을 분석한다. 사진과 프로필 삭제 후 늦은 결과가 살아나지 않는 검사도 유지한다. 앱 동의 문구와 약관 버전 반영, AI 설명에서 만든 주제와 지난 카드의 처리 등 실제 사용자 사진에 쓰기 전 남은 조건은 [법률 문서](../../docs/legal/README.md#사진-보관과-분석에-대한-pm-수정안)를 따른다. 시험 통과를 실제 자료 사용 승인으로 보지 않는다.

## 검증

- 임시 PostgreSQL과 합성 사진: 업로드, 작업 처리, 조회, 카드 입력 연결.
- 수정 우선, 삭제 및 임대 만료 후 결과 폐기, 전체 시간 초과와 늦은 스레드 결과 차단.
- 카드 생성 뒤나 생성 중에 분석이 끝나도 묶음을 갱신 필요로 표시하지 않음. 생성 중 입력 사진의 설명이 바뀌면 갱신 필요로 표시함.
- 동의: 동의하지 않은 계정의 사진은 가져가지 않음. 가져간 뒤 업체 호출 전에 철회하면 부르지 않고 `pending`, 그사이 다른 선택 동의만 바뀌면 그대로 부름. 호출 뒤 철회하면 결과를 버림.
- 철회(`tests/test_photo_consent_withdrawal.py`): AI 설명 삭제와 보호자 설명 유지, 미사용 묶음 갱신 표시, 카드 생성 중 철회, 재동의 뒤 재분석, 저장 중인 결과와 겹친 철회의 프로필 잠금, 근거가 설명이 지워진 사진뿐인 주제가 다음 카드 입력에서 빠졌다가 재분석이나 보호자 설명 뒤 다시 들어가는지.
- 위 시험은 실제 S3와 ML API를 부르지 않는다. 사진을 실제로 이해하는 품질과 실제 앱에서의 철회와 재동의는 확인하지 않았다. 실제 API와 운영 서버에서 확인한 것은 머리말의 11/7, 11/8 기록이다.
- 첫 카드 대기 회귀 시험은 `tests/test_first_card_photos.py`, 앱의 상태 복원과 선택 화면 시험은 `app/test/first_card_photos_test.dart`에 있다. 모델 호출 중 시간 초과 외에 동의 확인 DB 잠금이 오래 걸릴 때도 실패가 기록되는지 검사한다.

이미지 입력 형식은 [LangChain 공식 메시지 문서](https://docs.langchain.com/oss/python/langchain/messages)의 멀티모달 메시지 구조를 따른다.

### 첫 카드 대기 변경의 로컬 검증, 2026-11-09 KST

- 별도 작업트리에서 실제 PostgreSQL 17과 합성 자료로 시험했다. 운영 DB, S3와 ML API는 사용하지 않았다. Python 의존성은 현재 `uv.lock`으로 고정 설치했다.
- BE 전체 981개 통과, 배포 이미지나 별도 Docker 설정을 요구하는 운영 시험 3개 건너뜀. 마지막 보완 후 사진 대기, 사진 분석, 카드 API, migration과 API 문서 일치 시험 74개를 다시 실행해 통과했다.
- FE 전체 검사에서 1,019개 통과, 테스트 실행기 로컬 연결 오류로 1개 파일이 시작되지 않았다. 그 파일의 3개 테스트를 별도로 실행해 통과했다. 합계 1,022개 통과이며 한 번의 전체 실행이 성공한 것은 아니다. `flutter analyze`와 `git diff --check`도 통과했다.
- 새 테스트는 BE 18개, FE 28개다. 사진 5장 입력과 카드 근거 저장, 일부 및 전체 실패 후 계속 진행, 재시도, 시간 초과, 동의 철회, 삭제, 늦은 이전 결과, 중복 worker, 다른 프로필 처리, 앱 재진입, 네트워크 오류, 중복 선택을 확인했다. 모델 결과는 대역이므로 실제 사진 이해 품질을 검증한 결과가 아니다.
- 홈은 360×640, 412×917에서 글자 1배와 2배로 확인했다. 큰 글자에서 잘렸던 선택 영역을 스크롤하도록 수정했다. 화면 캡처는 Flutter 렌더링 결과이며 실기기 화면 검증은 아니다.
- 기록: `backend/build/test-results/full-suite.xml`, `photo-wait-final.xml`, `app/build/photo-wait-full-final.json`, `photo-wait-last-recheck.json`. 산출물은 로컬 build 폴더에 둔다.
- 검증 당시 GitHub 게시, 운영 배포와 Play 업데이트는 하지 않았다. 기존에 사진 없이 생성된 카드도 바꾸지 않았다.
