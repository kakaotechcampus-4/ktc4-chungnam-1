# 녹음 원본 삭제 실패와 분석 결과 분리

STT가 성공했는데 S3 삭제가 실패했다는 이유로 전사와 리포트까지 실패 처리하지 않는다.
원본 삭제 의무와 24시간 보관 상한은 바꾸지 않는다. 삭제가 끝났다고 표시하는 조건도 완화하지 않는다.

## 처리 순서

- STT 응답을 검증하고 전사를 임시 저장한다. 이미 임대가 끝난 작업에는 저장하지 않는다.
- S3 원본 삭제 요청을 기존 `storage_deletion_request_queue`에 먼저 저장한다. 키는 작업 행에서 다시 읽지 않고 처리 중인 작업이 알고 있는 값을 쓴다. 업로드 중 임대 만료나 계정, 프로필 삭제로 행이 먼저 지워졌어도 뒤늦게 끝난 업로드의 원본이 대기열 밖에 남지 않는다. 행이 남아 원본 삭제를 기록한 경우만 다시 넣지 않는다.
- S3 삭제 성공 시 `audio_deleted_at` 기록과 대기열 제거를 같은 DB 트랜잭션으로 처리한다.
- S3 삭제 실패 시 요청은 남기고 리포트 생성을 계속한다. 로그에는 작업 ID와 `audio_deletion_pending`만 남긴다.
- STT나 리포트가 실패했다면 해당 오류를 유지한다. 원본 삭제 실패로 오류를 바꾸지 않는다.
- 처리 임대가 끝난 작업도 실패 상태 변경과 삭제 요청 저장을 같은 트랜잭션에서 수행한다.

삭제 요청을 DB에 저장하지 못한 오류는 무시하지 않는다. DB 자체가 사용할 수 없는 상황까지
분석을 정상 완료했다고 간주하지 않는다. S3 삭제 후 DB 기록 전에 종료되면 대기열에 요청이
남아 다시 삭제할 수 있다. 동일 키 삭제는 다시 시도할 수 있어야 한다.

## 완료되지 않은 범위

- 이 변경은 삭제 요청을 남기는 부분이다. 삭제 대기열 실행기와 기한 감시는 별도로 연결해야 한다.
- 실패한 분석의 재제출, 리포트 재생성, 삭제한 녹음 복구를 구현한 변경이 아니다.
- `sttCompleted` 또는 `completed`만으로 원본 삭제 성공을 판단하지 않는다.
- 버킷 버전 관리가 활성화됐다면 `DeleteObject`가 삭제 표시만 만들 수 있다. 모든 버전의 실제 제거는 운영 설정과 별도 검증이 필요하다.
- 실제 S3와 실제 AI를 호출하지 않았다. 자동 검사는 합성 응답, 합성 파일과 격리 PostgreSQL을 사용한다.

## Lifecycle 전제 정정

S3 Lifecycle은 일 단위 만료 계산과 비동기 삭제를 사용하므로 1일 규칙만으로 정확한
24시간 이내 삭제를 보장하지 않는다. 기한 삭제 실행과 지연 감시를 운영하고 Lifecycle은
보조 수단으로 둔다. 운영 버킷 규칙을 이 변경에서 생성하거나 변경하지 않았다.

근거: [AWS Lifecycle 시간 계산](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html),
[만료와 실제 삭제의 차이, 버전 관리](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html).

삭제 실패 후 전사 보존, 리포트 완료, 기존 분석 오류 유지, 삭제 요청 중복 방지,
삭제 완료 기록의 트랜잭션 복원, 임대 만료 시 삭제 요청, 작업 행이 지워진 뒤 끝난 업로드의
삭제 요청을 검사한다.
