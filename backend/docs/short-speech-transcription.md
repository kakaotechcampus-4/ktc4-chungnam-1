# 프로필 세부 정보의 음성 입력

2026-10-18 22:03~22:04 KST의 [#138 BE 답변](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/issues/138#issuecomment-6250248022)을 연결한 구현이다. 작성 당시에는 운영 서버에 반영하지 않았다. 현재 구현 (2026-11-09 기준): #214로 병합(2026-11-05)했고 11/5 운영 배포(develop `6cebcf72`)부터 운영 서버에 있다([#187의 11/5 운영 배포 기록](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/issues/187#issuecomment-6652039046)). 아래 5분 제한의 2초 여유(#267)는 11/8 Deploy run 42485750502(develop `9c2b8276`)로 운영에 들어갔다. 본문을 읽기 전 토큰 확인과 본문 상한(#278), 계정별 동시 2건 제한(#285)은 11/9 Deploy run 42568179490(develop `59190ba7`)으로 운영에 들어갔다.

`POST /api/v1/speech-transcriptions`에 인증 토큰과 multipart의 `audio` 파일 하나를 보낸다. 프로필과 회차 ID는 필요 없다. 응답은 `{"schemaVersion": 1, "text": "..."}`이며 기존 앱의 `ServerSpeechApi` 형식과 같다.

- 필수 동의, WAV/PCM 16-bit/16kHz/mono, 실제 파일 손상, 크기와 5분 제한을 검사한다. 5분 초과는 `AUDIO_TOO_LARGE` 413으로 반환한다. 앱은 녹음을 시작한 뒤 5분 타이머를 켜고 멈추므로 5분을 채운 파일은 늘 300초를 조금 넘는다(11/8 운영 시험에서 300.004초 파일이 거절됨). 그래서 멈추는 데 걸리는 시간으로 2초를 더 받는다(302초까지). 배포 뒤 같은 300.004초 파일은 200으로 처리됐다(운영 배포 기록, 11/8). 이 오류 코드는 #214 PR에서 구현안으로 올렸고 그대로 병합됐다.
- 세션 토큰의 서명과 만료는 본문을 읽기 전에 확인한다. 본문은 짧은 음성 상한(10 MiB와 `SAEROK_MAX_AUDIO_BYTES` 중 작은 값)에 1 MiB를 더한 크기까지만 받고, 넘으면 끝까지 받지 않고 `AUDIO_TOO_LARGE` 413으로 끊는다([요청 본문 크기 상한](../README.md#요청-본문-크기-상한)). 현재 구현 (2026-11-09 기준): 이 본문 전 확인과 상한은 #278의 동작이며 11/9 배포부터 운영에 있다. 그 전 운영(11/8 배포, develop `9c2b8276`)은 본문을 다 받은 뒤 라우트 안에서 크기와 5분 제한을 검사했다.
- 같은 계정의 요청은 동시에 2건(`SAEROK_SHORT_TRANSCRIPTION_CONCURRENCY_PER_ACCOUNT`)까지 처리한다(#285). 한 요청이 STT 응답을 기다리는 동안 DB 연결과 STT 서버를 붙잡기 때문이다(2026-11-09 PM 결정). 앱은 `말씀을 글로 옮기고 있어요` 동안에도 `건너뛰기`로 다음 항목을 녹음해 보낼 수 있어, 1건이면 앞 전사가 끝날 때까지(최대 아래 STT 대기 시간) 다음 녹음이 거절된다. 그래서 기본을 2건으로 둔다. 이미 2건이 처리 중일 때 온 요청은 S3 저장과 STT 호출 없이 `SPEECH_TRANSCRIPTION_IN_PROGRESS` 429(`retryable: true`)로 거절한다. 라우트가 요청의 DB 연결에 세션 수준 advisory lock을 잡아 세며 트랜잭션은 열지 않는다([계정별 사용 한도](../README.md#계정별-사용-한도)).
- 서버 전체의 동시 처리 수는 `SAEROK_SHORT_TRANSCRIPTION_CONCURRENCY_TOTAL`로 제한할 수 있다. 기본은 비워 둔 상태(제한 없음)라 이 설정을 넣기 전까지 동작은 이전과 같다. 넣으면 계정 한도를 통과한 요청만 같은 advisory lock 방식(`server_slot`)으로 세고, 다 차 있으면 S3 저장과 STT 호출 없이 `SPEECH_TRANSCRIPTION_BUSY` 503(`retryable: true`)로 거절한다. STT 앞에 줄 세우면 앱의 2분 제한을 넘겨 실패로 보이고 그동안 DB 연결과 STT를 붙잡기 때문이다. 값은 STT 서버가 동시에 처리하는 수를 확인한 뒤 정한다. 다른 계정 요청도 거절하게 되어 "다른 계정의 요청은 기다리지 않는다"(2026-11-09 PM 결정)와 겹치므로 켜기 전에 PM 확인이 필요하다. 앱은 오류 코드가 아니라 `retryable`로 다시 보내기를 정하므로 앱 변경은 없다.
- 현재 STT 클라이언트를 재사용해 한 명으로 요청한다. 화자 분리를 끄거나 새 모델을 선택하지 않는다. #189에서 병합된 공용 클라이언트(`app.state.ai_server_client`)를 그대로 써서, 기본 STT 서버 연결이 실패하면 면회 분석과 같은 규칙으로 예비 서버에 한 번 전환한다.
- 음성은 기존 비공개 음성 버킷에 암호화해 임시 업로드한다. 원본 키만 정리 대기열에 먼저 저장하고 전사와 개인 식별정보는 DB나 로그에 저장하지 않는다.
- 처리 중에는 대기열의 `not_before`까지 삭제 실행기가 건너뛴다. 요청이 끝나면 즉시 삭제를 시도하고 재확인 대상으로 바꾼다. S3 삭제만 실패해도 전사 성공을 취소하지 않는다.
- 프로세스가 종료돼도 최초 저장한 큐가 남는다. 큐 실행과 S3 Lifecycle은 별도 운영 설정이다. 이 코드만으로 정확한 24시간 내 삭제가 보장된다고 설명하지 않는다. 삭제 실행기(#204) 코드는 운영에 있지만, 운영 배포 기록상 실제 삭제 실행은 11/6 PM 결정으로 보류됐고 정기 실행 설치 기록은 없다.
- 무음에서 STT가 지어내는 알려진 문장은 뺀다(#263, #267, [음성 입력 안전](speech-input-safety.md)). 다 빠지거나 전사 문자열이 비었으면 앱의 직접 입력 안내를 사용한다. 잡음을 알아듣지 못한 것으로 판정하는 새 점수 기준은 만들지 않았다.

STT 대기 상한은 6-6 전용 설정 `SAEROK_SHORT_TRANSCRIPTION_TIMEOUT_SECONDS`(기본 90초)를 쓴다. 이전에는 면회 분석과 같은 `ai_server_timeout_seconds`(기본 600초)를 써서, 앱이 2분에 포기하고 직접 입력을 안내한 뒤에도 서버가 최대 10분 동안 DB 연결과 STT 요청을 붙잡을 수 있었다. 90초는 앱의 2분 제한(업로드 포함) 안에 `504 AI_SERVER_TIMEOUT`(`retryable: true`) 응답이 도착하도록 업로드 여유를 30초 둔 잠정값이다. `ai_server_timeout_seconds`가 더 짧으면 그 값을 쓴다. 서버가 기다리기를 멈춰도 STT 서버 쪽 처리는 이 코드로 멈추지 않는다. 10초, 1분, 5분 실제 처리 시간과 대기열 혼잡을 측정한 뒤 #138의 제한 값을 정해야 하며, 5분 녹음의 STT가 90초를 넘으면 그 녹음은 계속 시간 초과가 된다. 현 설정을 적절한 사용자 대기 시간으로 검증한 것은 아니다.

`e84b1c6da032` migration으로 정리 대기열에 `not_before`를 추가한다. 삭제 기록 migration `a49d71b28c36` 다음이다. 처리 중인 임시 업로드가 남았으면 downgrade를 거절한다. 기존 삭제 실행 코드도 이 열을 확인하는 버전과 함께 배포해야 한다. 두 migration과 삭제 실행기(#204)는 11/5 운영 배포에 함께 들어갔다([#187의 11/5 운영 배포 기록](https://github.com/kakaotechcampus-4/ktc4-chungnam-1/issues/187#issuecomment-6652039046)).

테스트는 합성 WAV, 가짜 S3와 STT, 실제 격리 PostgreSQL을 사용한다. 실제 음성을 외부로 전송하지 않는다. 동시 요청 거절은 같은 테스트 앱에 요청을 겹쳐 보내 확인했고, 실제 앱의 연속 입력이나 운영 서버의 동시 요청으로 확인한 것은 아니다.
